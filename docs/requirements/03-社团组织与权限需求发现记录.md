# RanaMinder 社团组织与权限需求发现记录

> 本文记录社团、部门、职位、角色和跨社团隔离的问答过程；最终事实以《00-需求事实总账》为准。

## 2026-07-27：社团接入方式

### 已确认

1. 不设置专用的“社团根组”。
2. 不根据 Casdoor Group 的层级、名称或类型自动判断其是否为社团。
3. 由平台管理员人工查看现有 Casdoor Group，并选择其中哪些 Group 接入本系统作为社团。
4. 本系统不提供“新建社团”操作，也不创建 Casdoor Group。
5. 管理员拥有的是“接入已有 Group”权限；接入成功后，本系统建立配置和稳定映射。
6. 社团停用时，Casdoor 当前 Group、成员和角色关系保持不变；本系统将该社团置为只读。
7. 停用是可恢复状态，重新启用后可继续使用。

### 接入操作的业务含义

“接入社团”不是创建新的组织身份，而是确认一个现有 Casdoor Group 在本系统中具有社团业务含义。接入后，本系统才能为其建立招新、表单、通知、历史事件和权限配置。

最低约束建议包括：

- 一个 Casdoor Group 同一时刻最多绑定一个本系统社团空间。
- 接入前显示 Group 名称、父级、当前成员数等信息，要求管理员二次确认。
- 接入成功和失败均记录操作人、Group 标识和时间。
- 绑定使用稳定 Group 标识，不只依赖可能变化的展示名称。
- Casdoor Group 被删除或无权访问时，不删除本系统历史，而是进入同步异常状态。

上述约束尚需在后续轮次逐项确认。

### “归档”的最终决定

“停用”已经确认是临时冻结且可恢复。“归档”通常用于社团永久停止运营或永久退出本系统：不再出现在活跃列表、不再恢复日常业务，但历史记录继续保留。它与以下概念不同：

- 停用：临时、可恢复、系统只读、Casdoor 关系保留。
- 解除接入：取消 Casdoor Group 与本系统社团空间的绑定，常用于错误接入或迁移。
- 归档：业务上永久停止运营，但通常仍保留原绑定用于历史追溯。

用户于 2026-07-27 明确取消“归档社团”功能。上述解释只作为需求发现背景，不进入产品范围。

最终规则：

- 社团只有“已启用”和“已停用”两种本系统运行状态；停用可以恢复。
- 不提供归档按钮、归档状态或归档接口。
- 错误绑定、更换 Casdoor Group 或停止接入通过专门的解除接入/重新绑定流程处理，不能借用归档概念。

## 2026-07-27：接入权限与异常解除

### 已确认

1. 只有超级管理员可以接入、启用、停用、解除接入或重新绑定社团 Group。
2. 社团负责人、人事管理员和部门负责人不能修改社团的 Casdoor 映射。
3. 尚未产生任何业务数据时，可以二次确认后直接解除接入。
4. 已有招新、成员或任职历史时，正常情况下只能停用或重新绑定，历史归属保持不变。
5. 已接入 Group 被删除或系统失去访问权限时，社团自动进入同步异常和只读状态。
6. 同步异常时，超级管理员可以修复、重新绑定，也可以选择解除接入。

### 解除接入后的权限边界

如果已经存在历史数据，解除接入不会删除社团空间，而是进入“待重新接入”异常状态。由于系统此时无法从 Casdoor 确认谁仍然是现任负责人或成员：

- 所有普通社团角色立即失去该空间访问权。
- 仅超级管理员可以查看历史、导出必要数据或执行重新绑定。
- 重新绑定成功并完成成员、部门和角色对账后，才能恢复社团角色访问。
- 该状态是可恢复的异常状态，不是已经取消的“归档社团”。

## 2026-07-27：部门与职位接入

### 已确认

1. 社团 Group 的下级 Group 不会自动全部成为部门。
2. 由超级管理员人工选择 Casdoor 中已经存在的 Group，并配置为具体社团的部门。
3. 本系统不创建、改名或删除 Casdoor Group 和 Role。
4. 部门与职位只能从 Casdoor 已有 Group/Role 中选择接入；如需新增，先在 Casdoor 创建。
5. Casdoor 中的 Group/Role 改名自动同步到本系统。
6. 已接入资源被删除、移动或失去访问权限时进入同步异常，相关任免暂停，历史不变。
7. 异常由超级管理员重新绑定或解除接入。

### 需要继续确认

- 部门 Group 是否必须位于社团 Group 的后代层级。
- 同一 Group 或 Role 能否被多个社团重复映射。
- 首次接入部门或职位时，如何把 Casdoor 已有用户转换为本系统历史基线。

## 2026-07-27：Group 唯一映射与 Role 延期

### 已确认

1. 部门 Group 必须是社团 Group 的下级或后代。
2. 同一个 Group 不能跨社团重复映射，也不能同时作为社团和部门。
3. 当前阶段不考虑 Casdoor Role，社团组织接入只处理 Group。
4. 首次接入时，Group 中已有用户导入为“接入时已存在”的当前关系；真实开始日期未知，不能伪造成接入日期。
5. 当前产品不提供业务数据导入；确有客观证据时只能通过事实纠错补充历史日期，且不得改变 Casdoor 当前关系。

### 对前序结论的修正

前序“职位映射为 Casdoor Role”的方案不再是当前基线。Role 集成标记为延期，本系统不会在当前方案中读取或写入 Casdoor Role。

这会产生两个必须继续确认的问题：职位当前状态如何表示，以及社团负责人、人事管理员、部门负责人等系统管理权限从哪里产生。

## 2026-07-27：职位 Group 与权限映射

### 已确认

1. 职位也使用 Casdoor 中已经存在的 Group 表示，不接入 Role。
2. 本系统不独立维护当前职位；用户是否属于职位 Group 决定当前是否任职。
3. 职位 Group 必须位于对应社团 Group 的后代范围内，可以直属社团，也可以位于部门下。
4. 一个 Group 只能配置为社团、部门、职位中的一种；用户可以同时拥有多个职位 Group。
5. 只有超级管理员可以把 Group 配置为职位并映射系统权限。
6. 社团内授权人员在本系统执行任命等操作时，系统后端调用 Casdoor API 修改 Group 成员。

### “通过 API 更改 Group”的当前解释

当前解释为允许本系统通过 Casdoor API 增删 Group 成员，而不是允许本系统创建、改名、移动或删除 Group 定义。这与前序“只允许接入已有 Group”的规则一致。如用户后续明确需要修改 Group 定义，应作为需求变更重新评估。

### 权限模型方向

本系统权限不是来自 Casdoor Role，而是来自“职位 Group → 本地权限模板”的受控映射。普通职位可以没有管理权限；社团负责人、人事管理员和部门负责人等管理职位映射到固定权限模板。任命层级和多职位权限合并规则已在后续访谈中确认。

## 2026-07-27：任命层级与权限叠加

### 已确认

1. 换届时，任一现任社团负责人或人事管理员都可以确认负责人变更，不要求双方共同确认。
2. 超级管理员可以处理所有职位。
3. 社团负责人可以管理人事管理员、部门负责人和普通职位。
4. 人事管理员可以管理部门负责人和普通职位，但不能任命或撤销社团负责人。
5. 部门负责人只能管理本部门普通成员和普通职位，不能影响其他部门，也不能授予社团负责人或人事权限。
6. 多职位权限在同一社团内取并集；不同社团的权限互相隔离。
7. 移出某一职位 Group 后，对应权限立即撤销，其他并行职位和社团身份不受影响。

### 当时待确认（后续均已确认）

- 是否允许在换届或中途离任时暂时没有任何社团负责人。
- 非换届期间，现任负责人能否直接任命或撤销另一名负责人。
- Casdoor 外部直接修改管理职位 Group 成员时，权限和历史如何处理。

## 2026-07-27：负责人连续性与外部变更

### 已确认

1. 启用中的社团至少保留一名负责人；撤销最后一人必须在同一操作中指定继任者。
2. 超级管理员紧急停用社团时，可以暂时没有负责人。
3. 非换届期间，现任负责人可以新增或撤销其他负责人；人事管理员不能这样做。
4. 人事管理员只能在正式换届流程中确认负责人变更。
5. 超级管理员可以紧急处理负责人变更。
6. Casdoor 外部直接修改职位 Group 成员时，以 Casdoor 当前结果为准。
7. 本系统正常情况下在 5 分钟内更新权限，记录外部变更历史；管理职位变化通知负责人、人事和超级管理员。
8. 本系统不会自动撤销或覆盖 Casdoor 外部修改。

### 后续接口约束

“撤销最后负责人并指定继任者”在产品上是一个业务操作。即使 Casdoor 需要多次 API 调用，用户也不能看到一个已成功但社团暂时无人负责的中间结果；具体事务、重试和补偿规则将在接口契约中冻结。

## 2026-07-27：Casdoor 写入生效、社团停用与平台超管

### Group 成员关系变更

1. 部门、职位、负责人等关系变更先进入“处理中”，处理期间维持原关系和原权限。
2. 只有 Casdoor 写入成功并回读确认后，新关系及其权限才正式生效。
3. 同一目标处理中时，禁止发起重复或相互冲突的操作。
4. Casdoor 响应不确定时必须先回读实际状态，再决定成功、失败或重试，不能盲目重复写入。
5. 系统自动重试最长 15 分钟；仍失败则维持原有效状态，通知操作人和超级管理员。
6. 所有尝试和结果均写入审计；失败后允许管理员人工重试。

### 社团停用

1. 仍有进行中招新、有效邀请或审批时，普通停用被阻止，并向超级管理员列出待处理事项。
2. 超级管理员可以执行紧急强制停用；停用后该社团全部业务立即只读。
3. 强制停用期间，系统暂停该社团业务的自动截止、邀请到期和其他超时状态转换。
4. 强制停用和后续重新启用都必须通知受影响人员。
5. 重新启用时，各截止时间按照实际停用时长顺延。
6. 联合活动涉及其他社团，因此单个参与社团强制停用后的联合业务处理仍需在联合面试模块冻结。

### 平台超级管理员来源

1. 平台超级管理员由独立的 Casdoor Group 表示，不属于任何社团组织树。
2. 超级管理员 Group 映射在部署初始化时建立，社团管理员不能修改。
3. 后续对该映射或其成员关系的变更必须严格审计。
4. 系统不得允许任何操作使平台失去全部有效超级管理员。

## 2026-07-27：成员前提、多部门与职位作用域

### 成员关系前提

1. 用户必须先属于社团 Group，才能属于该社团的部门 Group 或职位 Group。
2. 非社团成员不能通过本系统被直接任命到部门或职位。
3. 通过本系统退出社团时，需要在同一业务流程中清除该社团下的全部部门和职位当前关系，历史仍完整保留。
4. Casdoor 外部只移除社团 Group、却残留部门或职位 Group 时，本系统立即撤销该用户在该社团的全部访问和管理权限。
5. 上述残留关系被标记为异常并通知管理员，但系统不自动删除 Casdoor 中的残留关系，防止放大一次可能的外部误操作；由管理员人工核实处理。

### 多部门关系

1. 同一成员可以同时属于同一社团的多个部门。
2. 各部门关系平等，不设置强制性的“主部门”。
3. 部门统计分别计算该成员，社团整体人数按人员去重。
4. 部门负责人仅能在自己所负责部门的范围内查看和管理该成员，不能借助该成员的其他部门关系扩大权限。

### 职位管理范围

1. 位于部门 Group 下的职位是部门级职位，权限范围只覆盖该部门。
2. 直属社团 Group 的职位是社团级职位。
3. 单个职位 Group 不能横跨多个部门；跨部门管理使用社团级职位。
4. 已接入 Group 被移动而导致职位范围变化时，系统进入同步异常，不能据此静默扩大权限。

## 2026-07-27：零部门成员、部门任职前提与权限模板

### 零部门成员

1. 合法社团成员可以暂时不属于任何部门。
2. 典型情形包括刚录取等待分配，以及只参与社团级工作的成员。
3. 社团负责人和人事管理员仍可查看、管理此类成员。
4. 部门负责人不能仅凭其社团成员身份访问；具体业务任务另行授权的除外。

### 部门职位任命前提

1. 部门级职位任命要求被任命人已经属于对应部门。
2. 尚未加入部门时，系统可以展示“加入部门＋任命职位”的复合操作，但操作者必须再次明确确认，不能静默增加部门关系。
3. Casdoor 外部出现只有部门职位、没有对应部门成员关系的异常时，该职位权限立即停用。
4. 系统标记异常并通知管理员，不自动把用户补入部门。

### 权限模板与临时授权

1. 系统内置社团负责人、人事管理员、部门负责人等默认权限模板。
2. 超级管理员可以从固定的权限项目录中创建或调整模板；每个职位 Group 关联一个模板。
3. 部门级模板的权限范围始终受所在部门限制，不能通过模板配置突破范围。
4. 社团权限模板不能产生平台超级管理员权限。
5. 社团管理员不能创建、修改权限模板，也不能改变职位 Group 与模板的映射。
6. 面试官等临时权限由具体业务任务授予，在任务结束后自动回收，不要求对应 Casdoor 职位 Group。

## 2026-07-27：负责人设置下限补充

1. 部门负责人不是每个部门的必设职位，部门可以暂时或长期没有负责人。
2. 部门没有负责人时，其管理、任命和审批事项由社团负责人或人事管理员按既有层级处理，不能形成无人可处理的流程。
3. 社团负责人仍是启用社团的必设职位，任何时候至少保留一名。
4. 此补充不改变部门负责人一旦存在时的部门范围权限，也不改变最后一名社团负责人的交接约束。

## 本模块内部冻结结论

社团、部门、职位与权限的产品行为已经内部冻结。后续不再由业务模块重新定义这些规则；Casdoor API 原子性、幂等、重试、权限缓存和模板版本迁移等实现约束进入 SRS、接口契约及第一批正式验证代码。
