# RanaMinder 身份与 Casdoor 需求发现记录

> 本文记录问答过程和未决问题；最终业务事实以《00-需求事实总账》为准。

## 2026-07-27：第一轮

### 已确认

1. 所有申请人必须先通过学校统一身份认证登录。
2. 学号就是 Casdoor 账号，是唯一明确只读的个人资料字段。
3. 其他个人资料有误时，修改入口应在本系统提供。
4. 本系统和 Casdoor 应支持资料的双向更改。

### 对历史草案的修正

PRD v0.2 中“姓名、学院、年级与上游冲突时以上游为准”的规则不再有效。后续需要重新定义双向同步的冲突处理，不能沿用“Casdoor 永远覆盖本地”的单向规则。

### 尚未推定的内容

- “双向更改”目前只确认了业务目标，尚未确认实时性、冲突优先级、审核和失败恢复。
- 尚未确认姓名、学院、年级、邮箱、手机号是否都允许学生直接修改。
- 尚未确认本系统修改资料后是否必须等待 Casdoor 回写成功，才能继续报名等业务。
- 尚未确认 Casdoor 被停用、学校统一身份信息缺失或两边同时修改时的处理方式。

## 2026-07-27：第二轮

### 已确认

1. 姓名和学号均不可由学生修改。
2. 学院、年级、邮箱、手机号等其他个人资料允许学生直接修改，无需审核，并在本系统立即生效。

### 关于并发修改的分析

“最后修改者生效”只有在不发生静默覆盖时才合理。建议使用以下产品规则：

1. 用户打开资料页面时取得当前资料版本。
2. 保存时如果资料已经被另一处修改，拒绝这次基于旧版本的保存，并提示资料已变化。
3. 用户查看最新内容、重新修改并确认后，该次明确确认的保存成为最终值。

这可以称为“最后一次经确认的修改生效”，而不是无条件的“最后写入覆盖”。前者可以避免用户在不知情的情况下覆盖别人或另一终端刚刚完成的修改。

### 关于 Casdoor 一致性的分析

“最终两边一致”是合理目标，但“两个独立系统在任何时刻都一致”无法作为可靠承诺：Casdoor 更新成功后本地可能故障，本地成功后 Casdoor 也可能超时。若要求外部失败时把整次修改显示为失败，就不能同时承诺本地立即生效。

当前建议是：

- 本系统保存成功后，新值立即成为业务有效值。
- 页面分别显示“已保存，Casdoor 同步中”“已同步”或“同步失败”。
- 同步失败不丢弃修改，由后台重试；超过阈值后进入人工处理并通知相关人员。
- Casdoor 侧发生修改时，通过更新事件进入本系统；系统仍使用版本冲突规则，不静默覆盖更新期间产生的新修改。
- 定期读取两侧值进行对账，发现遗漏事件或长期不一致时修复或转人工处理。

Casdoor 官方资料显示，用户接口支持按字段部分更新，用户更新事件可以通过 Webhook 通知应用；Webhook 自带有限次数重试和手动重放。这些能力可以作为双向同步基础，但不能代替本系统自己的幂等、重试和定期对账。

参考：

- [Casdoor 用户属性与部分更新](https://casdoor.ai/docs/user/overview/)
- [Casdoor Webhook、投递记录与重试](https://casdoor.ai/zh/docs/webhooks/overview/)

### 确认结果

用户于 2026-07-27 确认采用上述两项建议：

1. 检测到并发时拒绝旧版本，用户查看最新值并重新确认后，最后一次确认的修改生效。
2. 本地修改立即生效；Casdoor 同步状态明确可见；失败由后台重试、对账和人工处置实现最终一致。

## 2026-07-27：第三轮

### 已确认

1. Casdoor 账号被禁用或删除后，立即终止其登录和已有会话，但完整保留历史业务记录。
2. Casdoor 不可用时禁止新登录；既有会话获得最多 15 分钟降级使用时间。降级期间只允许普通资料查看和已保存表单编辑，敏感业务操作全部禁止。
3. 用户首次由 Casdoor 登录本系统时，必须检查邮箱和手机号；存在缺失项时立即进入资料补充流程。

### 仍需确定

- 资料补充流程是否不可跳过，以及补全前是否只能退出登录或查看帮助。
- 联系方式只做格式检查，还是必须分别通过邮箱、短信验证码验证。
- 联系方式的字段级可见范围。

## 2026-07-27：第四轮

### 已确认

1. 首次登录资料不完整不会限制用户浏览其本来有权访问的页面。
2. 资料补全前，用户处于“仅可浏览”状态：除补充个人资料和退出登录外，不得执行其他业务操作。
3. 首次登录需要补充的资料不只包括邮箱和手机号，还会包含其他个人信息。
4. 本轮当时曾确认邮箱和手机号均不需要验证码验证；该规则中的邮箱部分已于后续通知需求访谈中被用户明确修正，手机号部分继续有效。

## 2026-07-27：邮箱验证规则修正

1. 邮箱新增验证要求，手机号继续不要求短信验证码。
2. 首次填写邮箱后立即发送验证邮件；验证前用户只能浏览、补充或修改个人资料、重发验证邮件和退出登录，不能执行其他业务写操作。
3. 修改已有验证邮箱时，旧邮箱及其验证状态继续有效，新邮箱作为待验证值保存；新邮箱验证成功后才正式替换旧邮箱并进入 Casdoor 同步。
4. 新邮箱验证失败、链接过期或长期未完成时不改变当前旧邮箱。
5. 验证链接有效期为24小时，重复发送需要频率限制。
6. 验证邮件使用超级管理员配置的平台级发信账号；该账号不可用属于影响用户资料完成的运维故障。
7. 邮箱验证状态由本系统管理，是否能够同步到 Casdoor 取决于实际字段能力验证；手机号继续只做格式校验。
5. 普通面试官不需要被专门排除在基础联系方式查看权限之外。其实际可见范围跟随被分配的面试任务和候选人访问范围。
6. 社团负责人、人事管理员、部门负责人和超级管理员的联系方式查看范围采用上一轮建议；超级管理员特权查看必须审计。

### 新产生的设计问题

- 首次登录补充的其他资料是否由平台级动态表单统一定义。
- 当平台后来新增必填字段时，既有用户是否重新进入“仅可浏览”状态。
- 只有 Casdoor 已知字段适合双向同步；大量自定义资料是否应仅保存在本系统。

## 2026-07-27：第五轮

### 已确认

1. 资料采用平台公共资料、社团成员资料和招新报名资料三层动态表单模型。
2. 学号不提供变更能力。
3. 姓名不能直接编辑；学生必须提交姓名更正申请。
4. 只有经过平台预先配置的固定字段白名单可以与 Casdoor 双向同步；其他动态资料只保存在本系统。

### 边界说明

- 平台公共资料是跨社团复用的个人主档扩展，但不等于所有社团都能查看全部字段；查看仍受字段级权限控制。
- 社团成员资料属于具体社团，其他社团不能因为同一学生同时加入而读取。
- 招新报名资料属于具体批次；只有联合活动等明确授权场景可以突破单社团边界。
- 社团管理员不能把自定义字段映射到 Casdoor，避免覆盖身份平台中的未知字段。

### 仍需确定

- 姓名更正申请的处理人、处理结果、历史显示和 Casdoor 同步规则。
- 平台新增公共必填字段时，既有用户何时进入资料不完整状态。
- Casdoor 侧直接出现姓名或学号变化时的处理方式。

## 2026-07-27：第六轮

### 已确认

1. 姓名更正采用申请和超级管理员审批流程；结果通知学生，审计保留旧姓名。
2. 部门、职位等当前社团成员关系应从 Casdoor 获取，不作为平台补充资料或独立的本地主数据维护。
3. Casdoor 侧直接发生姓名或学号变化时，以 Casdoor 为准。

### 对系统边界的影响

此前“三层动态资料”中的“社团成员资料”表述需要修正。部门、职位属于强类型组织关系，不属于动态表单资料；Casdoor 成为当前关系的权威来源。平台公共补充资料和招新报名资料仍由本系统的动态表单管理。

Casdoor 官方模型显示：用户可加入多个组并拥有多个角色；组公开属性包括类型、父组和更新时间，角色公开属性包括用户与子角色。公开文档没有直接描述届次、任职起止时间、调岗原因、离任原因或完整历史。因此需要进一步区分“当前组织状态”和“人力资源历史事实”。

参考：

- [Casdoor Organization tree 与 Group 属性](https://casdoor.ai/docs/organization/organization-tree/)
- [Casdoor User roles 与 Role 属性](https://casdoor.ai/docs/user/roles/)

### 仍需确定

- 本系统是组织关系的操作入口并写入 Casdoor，还是只读展示 Casdoor 管理结果。
- 任期、调岗、换届和中途离任历史是否仍在本系统保存。
- 部门、职位分别如何映射到 Casdoor Group、Role。
- 普通学生是否能在 Casdoor 页面直接修改姓名或账号，从而绕过本系统姓名申请规则。

## 2026-07-27：第七轮

### 已确认

1. 本系统是录取、调岗、任命和离任等操作入口，并负责把结果写入 Casdoor；社团管理员不需要重复进入 Casdoor 操作。
2. Casdoor 保存当前组织关系的权威状态；本系统以不可变事件保存任期、调岗、换届和离任历史。
3. 使用一个学校级 Casdoor Organization；社团映射为顶层 Virtual Group，部门映射为下级 Virtual Group，职位映射为带社团范围的 Role。
4. 一个学生可以同时属于多个社团、多个部门，并同时拥有多个职位。

### 已形成的数据边界

| 数据 | 当前权威 | 本系统是否保存 |
|---|---|---|
| 当前社团成员关系 | Casdoor Group | 只缓存或对账，不作为独立可编辑主数据 |
| 当前部门 | Casdoor Virtual Group | 只缓存或对账，不作为独立可编辑主数据 |
| 当前职位 | 已接入的 Casdoor 职位 Group | 只缓存或对账，不作为独立可编辑主数据 |
| 任期、调岗、换届、离任、退出历史 | 本系统历史事件 | 长期保存并审计 |
| 平台补充资料 | 本系统 | 保存；固定白名单字段与 Casdoor 同步 |
| 招新报名表及附件 | 本系统 | 按批次、社团或联合活动授权保存 |

## 2026-07-27：第八轮

### 已确认

1. Casdoor 普通学生不能自行修改姓名和账号；受信任的 Casdoor 管理变更仍以 Casdoor 为准。
2. 新增平台公共必填字段支持生效日期；生效前提醒，生效后按资料所属范围限制写操作。
3. 普通资料同步目标为 5 分钟内完成。
4. 连续 24 小时同步失败时，用户端恢复到修改前的有效值并提示失败，平台管理员收到人工处理通知。

### 失败回退的必要保护

执行回退前必须主动读取 Casdoor 当前值。只有确认 Casdoor 确实没有接受新值时才能回退；如果 Casdoor 已更新但回调或响应丢失，应将任务标记为同步成功，避免把两边重新制造成不一致。

回退不删除修改尝试。系统继续保留拟修改值、旧值、提交时间、重试过程、最终核验结果和处理人，以便人工排查。

### 身份模块内部冻结结论

身份模块的产品行为已经形成内部基线。Casdoor 真实版本、字段名、Webhook、服务账号权限、姓名/账号自助编辑限制仍属于第一批正式代码的强制验证项；验证不通过时必须修订本基线，且不得使用真实学生数据继续试点。
