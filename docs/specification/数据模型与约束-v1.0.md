## 1. 文档定位、权威顺序与编号规则

### 1.1 文档定位

本文把已经确认的产品行为、SRS 约束和架构边界转换为第一轮可评审的数据设计草案。本文不是新的需求来源，不得改变角色权限、状态转换、通知对象、故障行为、保留规则或非目标。

发生冲突时，严格按以下顺序处理：

1. `requirements/00-需求事实总账.md`；
2. `product/PRD-v1.0.md`；
3. `specification/SRS-v1.0.md` 及其两份规范性明细；
4. `architecture/系统架构总览-v1.0.md` 与已接受 ADR；
5. 本文；
6. 后续接口、安全、测试、迁移和运维设计；
7. 框架、ORM、数据库工具或代码默认行为。

任何低优先级产物都不能反向把实现便利写成产品事实。若本文与上游冲突，本文对应设计立即失效并回到上游澄清。

### 1.4 现状审计结论

`DATA-GEN-001`：本轮开始前未发现已有物理数据模型、SQL DDL、迁移或与当前权威顺序竞争的数据表定义。上游已经明确固定 PostgreSQL、数据权威、作用域、关系骨架＋JSONB、任务、文件、Casdoor、搜索缓存和恢复边界，但有意把具体 Schema、表、字段、Policy、索引和迁移顺序留给数据规格。

已确认且不得重开的边界包括：

- 每个社团独立数据库已由 ADR-005 排除；
- PostgreSQL 是首版本地权威主数据库；
- 当前成员、部门和职位关系以 Casdoor Group 当前事实为权威，本地保存稳定映射、业务意图和不可变历史；
- 联合活动使用独立联合协作域，不得退化为一个普通 `club_id`；
- 缓存、搜索、统计和读模型不是授权或业务权威；
- 对象存储保存文件字节，PostgreSQL 保存文件元数据、引用和状态；
- 首版后台任务权威持久化在 PostgreSQL，按租约和至少一次语义执行。

第一轮数据技术问题集中在第 20 节，现已全部确认。`DATA-Q-001` 已于 2026-07-30 确认采用单数据库和统一应用业务 Schema，并由 [ADR-014](../architecture/ADR-014-单数据库与统一应用业务Schema.md) 固化；`DATA-Q-002` 已确认统一 UUIDv7 标识规则；`DATA-Q-003` 已确认模块强类型历史与统一业务命令关联契约；`DATA-Q-004` 已确认通用任务执行信封与模块强类型业务意图分离；`DATA-Q-005` 已确认联合域专用作用域隔离型 RLS；`DATA-Q-006` 已确认单目标与冻结集合只读双模式上下文；`DATA-Q-007` 已确认规范化 JSONB 答案、稳定重复项、强类型引用和证据驱动投影；`DATA-Q-008` 已确认默认普通表、保持可迁移并由表级证据门控分区；`DATA-Q-009` 已确认 PostgreSQL 18、扩展准入、排序、名称搜索和物理证据门禁；`DATA-Q-010` 已确认显式 `READ COMMITTED`、约束优先、对象版本、固定顺序定向行锁、登记式 `SERIALIZABLE` 例外，以及统一当前人员时间占用约束面和 `btree_gist` 时间/范围约束方向；`DATA-Q-011` 已确认版本化保留策略、正式数据不自动删除、临时与技术数据分层清理、高风险策略发布和失败最终收敛；`DATA-Q-012` 已确认每个隔离部署环境使用待检查、权威原件和临时派生三个私有 Bucket，以服务端高熵随机对象键、只写一次、应用级不可变版本、在线 Bucket 无原生版本和数据库权威清理/删除任务形成边界；`DATA-Q-013` 已确认以学校既有 Casdoor `v3.108.0` 为精确兼容基线，正确性路径采用周期全量对账、写后定向读回和高风险实时读回，Webhook 只允许作为默认关闭、非权威的刷新提示；`DATA-Q-014` 已确认按数据类别分层保护，数据库托管秘密采用服务端应用层 `AES-256-GCM`、数据库外版本化密钥环和强类型秘密引用，恢复旧备份后必须重新录入或轮换应用秘密，且首版不安装 `pgcrypto`。

## 2. 通用标识、版本、时间与引用规则

### 2.1 稳定对象标识

`DATA-GEN-002`：每个权威业务对象、不可变版本、业务命令、通知事实、文件版本、任务和删除清单都必须具有稳定且不可复用的内部标识。页面序号、名称、学号、Casdoor Group 名称、对象存储键、数据库行位置和客户端生成的工作空间提示均不能替代稳定标识。

第一轮字段类别如下。`DATA-Q-002` 已确认：所有需要独立稳定标识的权威对象、不可变版本、业务命令、通知事实、文件版本、持久任务和删除清单统一使用 PostgreSQL `uuid` 类型，值采用 UUIDv7。纯关联行或仅在父对象内部按序存在的历史、尝试和步骤记录，可以使用“父对象 UUID＋稳定局部序号/双方对象 UUID”等可由数据库约束的复合标识，不强制创建无业务用途的代理 UUID，也不按对象类别混用 bigint 代理主键。

`DATA-Q-009` 的版本与生成责任子项已确认：所有由 RanaMinder 创建的权威 UUIDv7 统一由 PostgreSQL 18 内置 `uuidv7()` 生成。普通记录可由数据库默认生成；业务命令或多表事务需要在首次写入前取得标识时，由服务端先向同一数据库申请一个或一批 UUIDv7，再在事务内复用。浏览器、客户端、Casdoor 或其他外部系统不得决定内部权威 UUID；外部稳定标识、业务幂等键和追踪编号继续使用独立字段。ORM、框架或运行时不得改成应用侧 UUIDv7、UUIDv4、其他 UUID 版本或整数。

UUIDv7 只提供稳定标识和较好的时间局部性，不是业务时间、严格创建顺序证明、业务编号、秘密或授权凭据；业务时间仍以显式时间字段为准，所有引用仍须满足作用域、外键、版本和授权约束。数据库不可用时不得在客户端、缓存或应用内预生成将来可能成为权威的替代 UUID；原请求是否重试仍由独立幂等键和 `SRS-FAIL-005` 决定。

| 字段类别 | 强制语义 |
|---|---|
| 对象标识 | 稳定、唯一、不可复用；跨模块引用只传稳定标识 |
| 外部映射标识 | 明确外部系统、外部对象类型、外部稳定标识和映射版本；名称只作显示快照 |
| 作用域标识 | 由对象类型显式携带普通社团、联合活动/协作域或平台域，不使用客户端工作空间代替 |
| 状态 | 当前主状态与正交标志分离；状态码属于对应状态机，不建立全系统任意状态字符串 |
| 对象版本 | 每次会影响竞争判断的成功写入单调推进；命令声明期望版本 |
| 时间 | 保存绝对时间点和必要的业务时区/来源；截止与区间使用服务端可比较值，不信任客户端时钟 |
| 创建与修改主体 | 引用稳定 `subject_id`；审计另保存当时角色、任务和作用域快照 |
| 追踪与幂等 | 追踪编号、业务幂等键、外部请求号分别保存，三者不得互相替代 |

### 2.2 当前行、版本快照和不可变历史

`DATA-GEN-003`：权威聚合必须区分以下三层数据：

1. 当前行：服务当前命令和查询，保存当前状态、正交标志、对象版本和当前有效引用；
2. 不可变业务版本或快照：保存发布、正式提交、邀请、决定、确认、关系意图等可还原事实；
3. 追加式历史：保存状态转换、修改前后必要差异、操作者、命令、时间和结果。

普通编辑不得覆盖不可变版本或历史。事实纠错追加新记录或新展示版本；正式删除按第 16 节执行，不把通用“软删除”当作归档、纠错或正式删除的替代方案。

### 2.3 作用域完整引用

`DATA-GEN-004`：所有普通社团对象之间的强关联必须能在数据库约束中同时证明对象标识和 `club_id` 一致；所有联合对象之间的强关联必须能证明 `joint_activity_id` 或等价联合协作域标识一致。只按全局对象标识建立外键、再依赖应用代码检查作用域，不足以通过隔离验收。

跨域引用只允许以下已确认类型：

- 平台主体、资料或稳定 Casdoor 映射被社团/联合对象引用；
- 联合活动通过正式参与社团关系引用多个社团；
- 权威业务对象引用平台通知、任务、审计、文件或派生记录的稳定标识；
- 纠错、删除和恢复清单引用其被授权处理的源对象。

不允许普通社团对象直接引用另一社团的普通业务对象；联合共享不能通过放宽普通社团外键实现。

## 3. 12 个领域模块与 3 个平台模块的数据所有权

`DATA-OWN-001`：每个权威对象只有一个写入责任模块。跨模块事务可以在同一 PostgreSQL 事务中协调多个所有者完成已确认的原子副作用，但不能让任意模块直接改写其他模块的当前状态或历史。

| 模块 | 类型 | 拥有的权威数据 | 只读或受控引用边界 |
|---|---|---|---|
| 身份与资料 | 领域 | 本地主体、Casdoor 账号稳定绑定、资料版本、邮箱验证、资料写入限制、资料同步意图与冲突 | 引用 Casdoor 可信观测；不拥有社团成员关系 |
| 组织与授权 | 领域 | 社团空间、部门/职位映射、关系命令、预约管理命令、当前映射版本与映射历史 | 引用主体和 Casdoor 当前关系；不拥有成员经历历史 |
| 普通招新 | 领域 | 普通活动、报名通道、申请、部门路径、轮次、时段、面试记录、普通评价与结论 | 引用表单版本、文件、邀请和成员任务；不直接授予 Group |
| 联合活动 | 领域 | 联合活动、确认轮次、参与社团关系、联合通道、联合申请、共享面试、参与社团结论 | 通过独立联合协作域引用社团；不复用普通招新对象 |
| 邀请与成员激活 | 领域 | 普通/联合录取或加入邀请、不可逆接受事实、邀请竞争结果、成员激活意图 | 成员关系最终生效交给成员生命周期和 Casdoor 关系任务 |
| 成员生命周期 | 领域 | 成员经历、部门/职位关系经历、关系申请、常规入社邀请、任期与实际起止历史 | 当前 Group 关系以 Casdoor 为权威；本地不反向覆盖外部当前值 |
| 动态表单 | 领域 | 表单根、草稿、不可变发布版本、稳定字段定义、提交修订、答案快照和资料快照 | 附件与对象选择使用独立受控引用；不拥有业务主状态 |
| 文件 | 领域 | 文件逻辑记录、不可变文件版本、对象键、检查版本、预览派生物、业务引用和删除状态 | 文件字节位于对象存储；访问服从所属业务对象和字段权限 |
| 通知 | 领域 | 通知事实、收件人快照、站内呈现、渠道意图、渠道尝试和投递结果 | 当前办理状态回读源业务对象；不改变业务状态 |
| 纠错、审计与数据生命周期 | 领域 | 纠错申请、业务审计、归档事件、正式删除清单/步骤、最小删除审计 | 引用源对象；不能用纠错直接改当前成员关系 |
| 统计与导出 | 领域 | 导出申请快照、生成任务业务状态、产物引用、统计定义与可验证结果 | 源业务保持权威；下载时重新授权 |
| 配置与发布 | 领域 | 平台/社团配置版本、权限模板、表单相关发布指针、数据使用说明版本、安全开关和发布历史 | 秘密的明文不进入普通版本或审计；配置失败保留旧发布版本 |
| 派生入口与读模型 | 平台 | 公开目录、个人中心、管理工作台、搜索文档、统计投影和可重建缓存元数据 | 只从权威源重建；不得参与授权判定或回写源状态 |
| 后台任务与批量编排 | 平台 | 持久任务、租约、尝试、幂等结果、批次编排、过期/截止任务和重建任务 | 单项业务结果仍由对应领域所有者提交 |
| 运维与可观测性 | 平台 | 应用版本/启动状态、依赖最近结果、积压摘要、恢复运行记录和脱敏运行证据索引 | 只读呈现技术事实；不拥有业务结论或权限 |

### 3.1 跨模块写入规则

`DATA-OWN-002`：

- 状态当前行和状态历史由同一责任模块拥有；
- 通知模块拥有通知事实，但需要通知的领域命令必须通过同一事务创建通知事实和收件人快照；
- 审计模块拥有审计信封和保留规则，领域模块提供最小必要差异，秘密和正文不得进入；
- 任务平台拥有执行记录，领域模块拥有业务意图和最终业务结果；
- 派生模块只能消费已提交事实或版本，失败不得回写权威源；
- 配置模块发布的当前指针可以被领域引用，但领域对象必须保存其使用的不可变配置/表单/说明版本快照。

物理上按 ADR-014 采用单个 PostgreSQL 数据库和统一应用业务 Schema；逻辑表仍按唯一写入责任模块组织，统一 Schema 不能改变上述所有权，也不允许绕过模块访问规则直接改写他模块权威数据。

## 4. 29 个状态机的权威数据映射

### 4.1 统一状态持久化约束

`DATA-STA-001`：29 个状态机都必须映射到一个且仅一个责任模块和一个明确权威聚合。每个聚合至少可表达：稳定对象标识、作用域、当前主状态、正交标志、状态版本、最近转换时间和当前有效版本引用。

`DATA-STA-002`：每次成功转换必须形成一条可追踪历史，至少包含聚合标识、转换序号、原主状态/正交标志、目标主状态/正交标志、期望版本、新版本、命令或触发来源、业务幂等键、操作者或系统来源、原因/证据引用、发生时间和审计/通知引用。拒绝命令不得伪造成功转换历史；是否记录失败尝试按 SRS 和审计规则执行。

历史逻辑上按权威聚合一对多保存。`DATA-Q-003` 已确认采用模块拥有的强类型追加式历史表：每个状态机的历史正文由其责任模块保存，使用真实聚合外键和作用域一致约束，不建立全系统统一权威历史表，不使用无法验证引用的任意字符串对象类型、EAV 或通用 JSONB 事件仓库替代。

所有模块历史表必须实现同一语义契约，即完整承接 `DATA-STA-002` 的公共字段，并为每次成功转换保存稳定业务命令 UUID。同一数据库事务内由一个业务命令产生的多个聚合历史、通知事实、审计和任务意图共享该命令 UUID；后续异步事务使用新的命令 UUID，并通过强类型触发来源引用原命令或源事实，不得把多次事务伪装成一次原子提交。跨模块统一查询通过受控联合视图或可重建读模型完成，不形成新的业务权威。

### 4.3 正交状态不能压成单一通用枚举

`DATA-STA-003`：以下内容必须独立版本化，不能只拼接成一个不可查询的状态字符串：

- 活动主阶段与暂停标志；
- 账号主状态与 Casdoor 不可确认降级区间；
- 申请主状态与身份异常、补救窗口、个人恢复窗口；
- 部门路径主状态与部门暂停标志；
- 联合结论/邀请主状态与面试作废待复核标志；
- 通知事实、各渠道投递和本人已读/已处理/隐藏；
- 任务业务状态、租约状态和单次尝试结果。

状态组合必须由对应状态机允许集合约束；不得因数据库可存任意字符串而形成表外状态。

## 5. 普通社团、联合协作、平台与派生数据隔离

### 5.1 作用域模型

`DATA-SCP-001`：首版逻辑数据域分为普通社团域、联合协作域、平台/个人域、技术运行域和派生域。平台超级管理员是当前授权结果，不是把任意行改成“平台行”的作用域值。

| 数据域 | 权威作用域来源 | 结构性隔离 | 典型对象 | 数据库保护方向 |
|---|---|---|---|---|
| 普通社团数据 | 权威对象的 `club_id` | 对象、父子关系、唯一性和引用均携带同一社团作用域 | 普通招新、社团成员/部门/职位、普通邀请、社团表单/配置 | 应用逐请求授权＋作用域外键/唯一性＋选择性 RLS |
| 联合活动数据 | `joint_activity_id` 及其正式参与社团关系 | 联合对象不归属单一社团；访问由活动状态、参与关系、任务和作者边界共同决定 | 联合申请、共享面试、参与社团结论、联合邀请 | 独立联合授权模型；专用 RLS 是否启用须单独证明 |
| 平台/个人数据 | 单校平台域与稳定 `subject_id` | 不通过当前工作空间改变归属；个人资料可被业务快照引用但不复制为当前权威 | 账号、资料、邮箱、平台配置、安全限制 | 服务端主体/平台特权授权＋强引用；不套用普通 `club_id` Policy |
| 技术运行数据 | 来源业务意图、任务类型和冻结作用域 | 每个任务、尝试、外部调用、恢复运行都引用来源对象和版本 | 任务、租约、对账、删除步骤、运行状态 | 独立数据库角色与最小访问路径；用户无通用读写入口 |
| 派生数据 | 权威源标识、源版本、水位和作用域 | 必须可定位重建来源；缓存键不得遗漏社团/联合/主体/字段范围 | 搜索、统计、目录、个人中心、工作台、缓存 | 当前授权后读取；不能作为权限或业务事实来源 |

### 5.2 联合协作域的强约束

`DATA-SCP-002`：

1. 联合活动在成立前已有稳定活动标识，但跨社团资料访问只有在全体确认成功、正式参与关系建立后开放；
2. 参与社团名单、确认轮次和首次公布锁定快照分别保存，不依赖可变名称；
3. 联合申请、共享面试和社团结论使用 `joint_activity_id` 作为共同域键；参与社团结论再携带 `participant_club_id`；
4. 跨社团作者记录同时保存作者主体、作者所属社团和当时职能/任务来源；
5. 单一参与社团停用只改变该参与关系的访问和期限区间，不删除联合对象或改写锁定名单；
6. 任何联合表都不得只检查一个 `club_id` 就开放完整联合资料。

### 5.3 平台特权作用域

`DATA-SCP-003`：超级管理员访问不是数据所有权。高风险命令保存目标作用域、影响范围快照、重新认证时间/证据引用、当前 Group 可信确认、原因、确认版本和审计，但不得在业务表上保存一个可被客户端切换的“超级管理员作用域”。

`workspace_hint`、社团名称、角色标签和客户端对象列表均为不可信输入。数据库作用域上下文只能由服务端在认证、对象加载和当前授权完成后建立。

## 6. 选择性 RLS、连接上下文与数据库身份

### 6.1 候选表族

`DATA-RLS-001`：第一轮按逻辑表族评估 RLS；数据库与 Schema 布局已由 ADR-014 冻结，联合域专用 RLS 方向已由 `DATA-Q-005` 冻结，单目标/集合只读上下文已由 `DATA-Q-006` 冻结。后续安全、物理表与迁移设计必须据此形成具体表级清单、Policy 文本、例外说明和负向测试；本文仍不编写 SQL DDL。

| 逻辑表族 | 普通社团 RLS 方向 | 约束与例外说明 |
|---|---|---|
| 普通活动、通道、申请、部门路径、轮次、时段、面试、评价和结论 | 候选启用 | 直接保存单一社团受保护事实，必须同时有作用域外键和唯一性 |
| 成员经历、部门/职位关系、关系申请、普通/常规邀请 | 候选启用 | 当前 Casdoor 关系权威不取消本地社团作用域和历史隔离 |
| 社团表单定义/提交、社团配置版本和社团发信配置元数据 | 候选启用 | 秘密值另走受控存储；字段权限仍由应用求交 |
| 文件业务引用 | 候选启用 | 文件全局元数据不能单独授予访问；应从当前有效业务引用和字段权限进入 |
| 社团范围通知呈现 | 独立评估 | 收件人本人和事件社团可能同时参与作用域；不能只靠 `club_id` |
| 联合活动、参与关系、联合申请、共享面试和社团结论 | 启用联合域专用作用域隔离型 RLS | 基础对象至少限制服务端冻结的 `joint_activity_id`；参与社团私有数据再限制 `participant_club_id`；不复用普通 `club_id` Policy，不在 Policy 中复制完整角色、任务、作者、字段和状态授权 |
| 平台身份/资料、稳定映射、平台配置 | 不适用普通 RLS | 使用主体/平台授权、唯一映射和受控服务路径 |
| 业务审计、任务、对账、删除、恢复运行 | 不适用普通 RLS | 不代表可通用访问；使用专用数据库身份、来源作用域和只读/写入路径 |
| 公开目录和可重建派生数据 | 不作为权威 RLS 来源 | 公开范围由源对象发布状态决定；受保护详情仍回源授权 |

任何普通社团表不启用 RLS，必须在后续表级清单记录：数据域、作用域来源、不启用原因、所有访问路径、等效数据库约束、负向测试和重新评估条件。

联合域 RLS 不硬编码参与社团名单或数量。当前正式参与关系由一对多关系行及其状态/版本表达；服务端只有在对应状态机允许且正式参与关系有效时，才能为请求建立联合活动或参与社团上下文。参与关系新增、停用或失效提交后，新请求按新版本重新授权；旧版本写入、后台任务和长链路操作必须重检关系/对象版本。确认轮次、首次公布名单、作者归属和其他锁定快照保持不可变，不因当前参与关系变化而改写。

### 6.2 连接上下文

`DATA-RLS-002`：RLS 上下文契约至少表达：

- 已认证稳定 `subject_id`；
- 请求/事务追踪编号；
- 已由服务端解析的单一目标社团、联合协作域，或经冻结的授权作用域集合；
- 当前操作类别和必要的授权版本/重新认证证据引用；
- 后台任务时的来源业务意图、固定作用域、对象版本和任务标识。

上下文必须在事务本地或等价的安全边界设置，受保护查询与写入完成后不得泄漏到连接池下一位使用者。上下文缺失、格式无效、对象与作用域不匹配或无法唯一解释时失败关闭。具体 PostgreSQL 会话变量、函数、Policy 语法和连接池产品不在本文选择。

`DATA-Q-006` 已确认上下文采用双模式：所有命令、状态转换、详情读取、文件访问、高风险操作和后台任务单项执行使用单目标模式；只有个人中心、管理工作台、跨社团只读待办和受控统计等登记过的聚合查询可以使用服务端冻结的有限授权集合只读模式。集合模式禁止写入，批次任务按冻结目标逐项建立单目标上下文，不获得通用多作用域绕过。

普通社团集合保存已按当前操作授权的 `club_id`；联合共享范围保存获准的 `joint_activity_id`，参与社团私有范围必须保存完整 `(joint_activity_id, participant_club_id)` 元组，禁止把两个独立集合自由组合。集合由服务端按当前用户、操作类别、角色、任务和权威关系计算，客户端不得提供；集合载体、规模阈值与查询计划必须在物理 Policy 设计和 `DATA-Q-009` 保留的部署/查询证据门禁中确定。

普通视图只负责连接、裁剪和组织已允许数据，不得以视图所有者、表所有者或绕过身份规避基础表 RLS。物化视图和持久派生表必须显式携带主体/社团/联合域、源对象、源版本或水位，并在读取时重新授权；刷新身份读取全量源数据不能转化为普通用户的全量访问。所有跨作用域视图只读，不能作为命令写入口或授权事实来源。

### 6.3 数据库身份与绕过边界

`DATA-RLS-003`：

| 数据库身份类别 | 允许能力 | 明确禁止 |
|---|---|---|
| HTTP 普通应用身份 | 在服务端建立的当前上下文内读写已授权业务表 | `BYPASSRLS`、表所有者式通用绕过、客户端自设上下文 |
| 后台任务身份 | 按单个已领取任务的冻结作用域和来源版本执行 | 因“系统任务”获得全库通用业务访问；跨项复用上下文 |
| 派生/重建身份 | 读取明确源表并写可重建投影；全程记录任务与水位 | 回写源业务、生成权限事实、绕过正式删除清单 |
| 迁移身份 | 按受控迁移版本执行结构变更 | 承担普通应用流量或成为产品超级管理员后门 |
| 备份/恢复身份 | 读取/恢复规定材料并执行恢复门 | 恢复后跳过删除重放、附件一致性或 Casdoor 对账 |

产品超级管理员和数据库高权限是两个不同概念。产品角色不能自动映射为数据库绕过身份；迁移、备份和恢复凭据必须与普通业务连接分离并受运维控制。

## 7. 8 类事务边界的数据落点

`DATA-TX-001` 至 `DATA-TX-008` 对应 ADR-003 的 8 类事务边界。表内“同事务”仅指 PostgreSQL 本地权威提交；Casdoor、对象存储、邮件、文件检查和导出生成均不伪装为分布式原子事务。

| 数据编号 | 事务边界 | 同一数据库事务必须保存 | 提交后可恢复执行 | 失败与恢复责任 |
|---|---|---|---|---|
| `DATA-TX-001` | 本地业务状态转换 | 当前状态/版本、业务结果、追加历史、关键审计、上游要求的通知事实 | 非必要派生刷新 | 任一必需项保存失败则整体回滚；重复命令返回同一幂等结果 |
| `DATA-TX-002` | 直接权益事件与通知 | 权益结果、通知事实、收件人快照、逻辑去重键、关键审计 | 站内呈现和各渠道投递 | 通知事实或收件人快照失败时权益业务回滚；渠道失败不回滚已提交业务 |
| `DATA-TX-003` | Casdoor 身份/Group 外部写入 | 本地业务意图、原关系/值快照、目标、当前处理状态、幂等键、任务、审计 | 外部写、可信回读、重试、补偿和对账 | 响应不确定先回读；未确认不授新权限；部分成功按状态机补偿或异常收口 |
| `DATA-TX-004` | 文件上传、检查与绑定 | 文件元数据、版本、业务引用意图、检查版本、处理任务和当前状态 | 对象字节上传/删除、扫描、预览生成 | 字节与数据库无跨存储假事务；旧任务按文件/检查版本失效；绑定与清理竞争单胜者 |
| `DATA-TX-005` | 通知渠道投递 | 通知事实、收件人、渠道资格结论、渠道任务、模板/发件身份快照 | 站内信生成、邮件发送、查询结果和重试 | 渠道消息 ID 幂等；不重复业务或通知事实；永久失败保留证据 |
| `DATA-TX-006` | 受控批量操作 | 预览条件、固定目标 ID/版本、参数、影响摘要、批次状态和单项意图 | 每个单项在独立事务执行，之后汇总 | 成功项不回滚；失败项保留结构化结果；重试只包含原失败项 |
| `DATA-TX-007` | 正式删除 | 删除命令、范围快照、删除清单、最小审计、步骤状态和幂等依据 | 数据库/对象/缓存/索引/导出逐步删除与核验 | 已完成步骤不补偿复原；未完成步骤重试；恢复备份后先重放清单 |
| `DATA-TX-008` | 搜索、统计、读模型与缓存 | 源对象版本/变更事实、重建意图、任务和派生水位 | 派生刷新、索引、统计重算和缓存失效/重建 | 派生失败不改源业务；旧版本结果不得覆盖新水位；可全量回源重建 |

覆盖结果：8/8 类事务边界均具有数据事实、任务意图、幂等、历史、通知/审计以及失败恢复落点。

## 8. 并发、唯一性、容量、时间与租约约束

### 8.1 约束分层

`DATA-CON-001`：约束必须区分四类执行位置，不能把所有规则都假装成单行 `CHECK`：

| 约束类型 | 适用手段方向 | 示例 |
|---|---|---|
| 行内合法性 | 非空、类型、枚举/状态集合、时间先后、数量非负等检查 | 结束时间晚于开始时间；剩余有效时长严格大于零 |
| 跨行唯一性 | 普通/组合/条件唯一约束 | 一名学生在同一活动只有一份申请；同一关系最多一段当前有效经历 |
| 引用与作用域 | 主外键、携带作用域的组合引用 | 普通申请及活动 `club_id` 一致；联合结论属于同一联合活动和参与社团 |
| 事务谓词 | 锁定聚合、期望版本、约束索引或同一提交内重新校验 | 最后负责人连续性、容量不超卖、邀请接受竞争、批量单项当前授权 |

ORM 校验、TypeScript 类型和客户端校验只能提前提示，不能替代数据库可证明的唯一性、引用和提交竞争约束。

### 8.2 唯一性清单方向

`DATA-CON-002`：至少冻结以下逻辑唯一性；具体索引名和 SQL 留待迁移设计。

| 业务约束 | 逻辑唯一键或单胜者边界 |
|---|---|
| 主体与 Casdoor 账号绑定 | 外部身份提供方/组织＋外部稳定账号标识唯一；一个当前本地主体绑定关系不得冲突 |
| 社团与 Casdoor Group 映射 | Group 稳定标识在同一用途下只能有一个当前映射；旧映射进入历史 |
| 普通申请 | `activity_id + subject_id` 唯一；退出后恢复仍在同一申请对象内增加修订 |
| 联合申请 | `joint_activity_id + subject_id` 唯一 |
| 普通部门路径 | `application_id + department_id` 唯一，正式志愿与调剂来源另存 |
| 联合参与关系 | `joint_activity_id + club_id` 唯一；每个确认轮次每社团一份有效确认 |
| 联合社团结论 | `joint_activity_id + joint_application_id + participant_club_id` 唯一 |
| 当前面试记录/尝试 | 普通按申请＋轮次最多一份当前有效记录；联合按联合活动＋申请人最多一份当前有效尝试 |
| 当前成员/部门/职位经历 | 对同一主体、社团和关系种类最多一段当前有效经历；历史段不被覆盖 |
| 待处理邀请 | 按强类型邀请的已确认业务键限制冲突待处理邀请；不同邀请类型不得靠字符串改型 |
| 表单字段 | 表单版本内稳定字段标识唯一；不兼容类型变化创建新字段标识 |
| 通知 | 逻辑事件＋收件人唯一；逻辑事件＋收件人＋渠道唯一 |
| 外部事件 | 外部来源＋事件稳定 ID 唯一；无稳定 ID 时使用经验证的复合去重依据并保留原载荷摘要 |
| 幂等结果 | 命令类型＋作用域＋业务幂等键唯一；同键不同规范化请求摘要必须拒绝复用 |
| 首邀与发布指针 | 联合活动首份成功邀请事件唯一；每个配置/表单根只有一个当前发布指针版本 |

### 8.3 对象版本和竞争命令

`DATA-CON-003`：所有会改变状态、期限、当前指针、容量、关系或有效引用的命令必须提交期望对象版本。成功命令推进版本并写入幂等结果；旧版本拒绝且不产生业务副作用。相同幂等键和相同规范化输入返回原结果，相同键但输入不同必须拒绝，不能覆盖原结果。

邀请接受/拒绝/撤回/到期、申请撤回/审批、预约取消/执行租约、最后名额、活动发布/取消/完成、资料同步冲突选择和正式提交/截止等竞争都使用同一权威版本边界，只允许一个结果成功。

### 8.4 容量与时间冲突

`DATA-CON-004`：面试时段必须保存容量版本和当前有效占用。取得、释放和换时必须在同一事务内同时校验旧安排版本、新时段容量、申请人全局时间占用和明确面试官任务时间占用；失败时旧安排保持。

时间区间按 SRS 使用半开区间 `[start, end)`。第一轮 PostgreSQL 方向是把当前有效占用规范化为可比较的绝对时间范围，并评估：

- B-tree 约束/索引承载主体、时段、状态等相等条件；
- GiST 排斥约束或等价数据库约束阻止同一主体的重叠有效区间；
- 条件唯一/部分索引只约束“当前有效、占用中”的记录；
- 时段聚合行或等价原子计数防止 `active_occupancy > capacity`。

时间冲突采用 `DATA-Q-010` 已确认的统一当前人员时间占用约束面：普通活动和联合活动的有效面试安排必须在同一事务内为申请人及明确面试官取得或释放占用，由 PostgreSQL 18 时间范围不重叠约束形成跨模块数据库竞争边界。容量仍由时段聚合边界独立约束，不能只“先查再插”。

### 8.5 邀请期限、冻结与恢复

`DATA-CON-005`：邀请和窗口分别保存当前截止版本、旧截止版本、失效原因、冻结区间和结算状态。恢复使用新截止时，必须引用原冻结区间且每个区间最多结算一次。旧截止任务携带截止版本，版本失效后只能记录幂等忽略结果，不能关闭新窗口。

### 8.6 任务租约

`DATA-CON-006`：任务领取数据至少表达任务状态、可执行时间、租约持有者脱敏标识、租约令牌、租约开始/到期、尝试号和任务版本。领取必须原子跳过已被有效租约占用的任务；到期可重领，但旧执行者用旧令牌提交结果必须失败。

PostgreSQL `FOR UPDATE SKIP LOCKED` 是第一轮候选领取方向，不是产品规则。任务最终仍以业务幂等键、源对象版本和当前前置条件防止至少一次执行产生重复业务结果。

### 8.7 分层并发控制基线

`DATA-CON-007`：`DATA-Q-010` 已于 2026-07-30 确认方案 A 的总体基线。RanaMinder 首版使用显式 `READ COMMITTED` 普通事务、数据库可声明约束、期望对象版本和固定顺序的定向行锁组成默认并发控制层；只有已登记且无法由这些手段可靠证明的剩余事务谓词，才允许对该类完整业务命令使用 `SERIALIZABLE`。这是一条显式数据合同，不得把 PostgreSQL、NestJS、ORM、连接池或迁移工具的默认事务行为冒充结论，也不把 `REPEATABLE READ` 作为独立基线层。

| 竞争类型 | 第一轮总体落点 | 仍须专项证明的内容 |
|---|---|---|
| 单对象状态、邀请和当前指针竞争 | 期望对象版本、条件写入、当前唯一性和同事务历史 | 业务冲突错误映射、零行更新和同幂等键重放 |
| 容量与最后名额 | 锁定时段/容量聚合锚点，原子更新当前占用并校验非负和上限 | 锁粒度、热点、等待上限和最坏并发计划 |
| 最后负责人连续性 | 锁定社团/连续性锚点及受影响当前关系；同事务完成替代或拒绝 | 多关系固定锁序、死锁和 Casdoor 意图恢复 |
| 人员与面试官时间冲突 | 统一当前人员时间占用约束面＋PostgreSQL 18 时间范围不重叠约束；来源安排与占用同事务提交 | 多人固定处理顺序、最坏并发计划、约束错误映射和备份恢复复现 |
| 持久任务租约 | 原子领取、租约令牌/版本和旧持有者条件失败 | `SKIP LOCKED` 查询、积压公平性、租约与执行超时 |
| 批量命令 | 冻结目标集合，按单项事务、单项幂等和单项结果执行 | 批次并发度、重试上限和失败聚合 |

约束与事务规则如下：

1. 行内合法性、跨行唯一性、作用域引用和“当前唯一”优先由非空/检查、唯一或条件唯一、外键/复合外键等数据库约束表达；应用预查只能改善提示，不能替代提交竞争边界。人员时间范围重叠由本节统一占用约束面承载。
2. 改变状态、关系、容量、期限、当前指针或有效引用的命令必须携带期望版本或使用可证明等价的条件写入；条件未命中视为并发冲突，不得追加成功历史、任务意图、通知或审计结果。
3. 已知聚合竞争使用最小必要范围的定向行锁。容量命令先锁时段或容量锚点；最后负责人命令先锁社团或连续性锚点，再锁受影响关系。一次命令涉及多个同类对象时按稳定 UUID 顺序取得同等级锁，并先取得约束该命令的共同锚点；普通业务路径不得依赖表级锁。
4. `SERIALIZABLE` 只允许用于“约束＋版本＋定向锁”仍不能可靠表达的已登记事务类型。登记项必须给出被保护谓词、读写集合、冲突结果、完整事务重试条件和代表性并发测试；不得为了省略约束设计而把所有写事务统一提升隔离级别。
5. PostgreSQL `40001` 必须从授权、当前状态、版本和业务前置条件开始重试整个业务命令，不能只重放最后一条数据库语句。`40P01` 只有在同样满足完整命令重试和幂等条件时才允许受限重试；`23505`、`23P01` 等约束失败默认映射为已登记的业务竞争/输入错误，只有约束合同明确证明属于瞬时竞争时才可重试，禁止盲目重试持续非法输入。
6. 每次重试复用同一业务幂等键和规范化请求摘要；同键异参必须拒绝。最大尝试数、退避、锁等待和语句超时属于后续版本化配置与测试证据，不得依赖驱动或 ORM 隐式默认。
7. Casdoor 调用、对象存储写入、邮件/通知渠道发送、文件检查和其他数据库外副作用不得放入可重试数据库事务。事务只提交本地权威事实与强类型意图；提交后由后台任务按幂等、回读和恢复规则执行外部动作。
8. 接口、迁移和测试设计必须为每个并发敏感命令登记：隔离级别、数据库约束、锁定目标和固定顺序、期望版本、可重试错误、幂等范围、外部意图以及业务错误映射。未登记的框架默认事务不具备开工资格。

统一当前人员时间占用约束面遵守以下补充规则：

1. “组织与授权”模块拥有当前人员占用约束记录，承接其既有预约管理命令责任；普通招新和联合活动继续分别拥有面试安排、状态和历史。跨模块命令只在已确认的同一 PostgreSQL 事务内协调双方，不改变状态机唯一责任。
2. 当前占用至少表达稳定占用标识、`subject_id`、非空半开绝对时间范围 `[start, end)`、来源模块/类别、来源安排稳定标识、来源版本和创建命令。来源类别使用封闭强类型，来源关联使用模块拥有的强类型外键/关联，不允许自由表名、任意对象字符串或 JSONB 多态引用。
3. 约束面只保存当前有效占用；取消在同一事务内释放占用，换时在同一事务内校验旧安排版本并替换占用。任一新占用、容量或来源安排写入失败时事务整体回滚，旧安排和旧占用保持不变。业务历史仍追加在来源模块，不能靠保留失效占用代替历史。
4. 同一 `subject_id` 的当前占用以 PostgreSQL `tstzrange` 或经迁移证明等价的带时区绝对时间范围表达，使用 PostgreSQL 18 `WITHOUT OVERLAPS` 或等价排斥约束禁止范围重叠；范围必须非空且统一为 `[start, end)`。具体约束名和 SQL 语法留待迁移设计，不得改变该逻辑语义。
5. `btree_gist` 获批为首版第二个必要的 PostgreSQL 官方随附扩展，仅为 UUID/封闭标量相等与时间范围重叠的 GiST 约束提供运算类；不得扩张为搜索、排序、授权或任意索引默认。部署预检、迁移、最小权限、备份恢复和大版本升级必须验证该扩展及约束可复现。
6. 多人安排按稳定 `subject_id` 顺序处理占用；数据库约束是最终竞争裁决。冲突只返回当前人员在该时段不可用的最小结果，不能借统一约束面向无权调用者泄露另一社团、联合活动、申请或面试官任务详情；详细来源只能按其权威对象重新授权后读取。
7. 统一占用不是普通视图、物化视图、缓存或可重建搜索投影，因为它参与业务事务成功判定；也不是独立产品日历、可用性偏好、场地/设备占用、课程表、循环日程或自动排期功能。未来纳入这些资源或能力必须先回到产品事实和数据评审。

本选择不改变现有 8 类事务原子边界，不选择 ORM 或迁移框架，也不编写 SQL DDL。`DATA-Q-010` 已关闭；具体列、约束名称、强类型来源关联形式、查询计划和并发参数仍须在迁移与测试设计中形成证据，不能重开已确认的逻辑边界。

## 9. 关系骨架与 JSONB 动态答案

### 9.1 逻辑实体边界

`DATA-FRM-001`：动态表单采用以下逻辑分层。具体表名和 JSONB 文档结构待后续物理模型确认。

| 逻辑实体 | 关系骨架 | JSONB 允许内容 | 明确禁止 |
|---|---|---|---|
| 表单根 | 所有者层级、业务表单族、作用域、稳定标识、当前发布指针 | 无需保存答案 | 把当前发布内容覆盖在根记录上 |
| 表单版本 | 来源版本、版本号、状态、发布/停用时间、发布人、适用业务范围 | 可保存不可变定义快照、布局和条件表达式 | 原地修改已发布或已停用版本 |
| 稳定字段定义 | 稳定字段 ID、版本引用、字段类型、必填、对象类型、权限和排序 | 可保存类型专属安全配置 | 用标题作为标识；原地进行不兼容类型变更 |
| 表单提交骨架 | 提交者、业务对象、作用域、表单版本、提交状态、对象版本、正式修订指针 | 无权威身份/状态字段 | 用答案替代申请、审批、邀请、关系或时间 |
| 提交修订 | 修订号、表单版本、资料快照版本、说明版本、提交时间、锁定状态 | 以稳定字段 ID 为键的动态答案快照 | 客户端任意 JSON 直存；覆盖旧正式修订 |
| 对象选择引用 | 修订、字段、对象类型、对象稳定 ID、作用域和显示快照 | 非权威展示补充可随修订保存 | 只在 JSONB 中保存一个对象 ID 而没有可校验引用 |
| 附件引用 | 修订、字段、文件版本、顺序和访问类别 | 不保存文件字节 | 把对象存储地址当永久授权或答案正文 |
| 可重建查询投影 | 源修订、字段、规范化值、源版本和重建水位 | 仅保存派生查询需要的值 | 反向成为正式答案或字段权限来源 |

用户、学号、姓名、社团、部门、职位、活动、业务状态、审批结果、关系、邀请、任期、权限、窗口和关键时间必须位于关系骨架。动态答案只能扩展资料，不能成为这些事实的替代真相。

### 9.2 不可变版本、迁移与快照

`DATA-FRM-002`：

1. 已发布和已停用表单版本内容不可更新；复用必须基于来源版本建立新草稿并发布新版本；
2. 草稿迁移保存源草稿版本、目标表单版本、字段迁移结果和无法迁移项；
3. 每次正式提交保存表单版本、固定业务骨架引用、资料快照、动态答案、附件版本和数据使用说明确认；
4. 历史提交按当时版本还原，不能随当前个人资料、字段标题或表单当前指针变化；
5. 条件隐藏字段不进入当前正式修订，但旧正式修订的旧答案继续按旧版本和当前权限还原；
6. 对象选择在提交时重新验证存在性、作用域和当前有效性，显示名称只作快照。

### 9.3 运行时校验

`DATA-FRM-003`：动态答案进入权威修订前，服务端必须按不可变表单版本执行结构、类型、范围、必填、条件、对象引用、字段读写、秘密字段和附件检查校验。TypeScript 类型、NestJS DTO、ORM JSON 映射和客户端组件都不能替代该运行时校验。

数据库至少保证修订与表单版本、稳定字段、对象选择引用、文件版本和所属业务对象之间的强引用；是否引入数据库端 JSON Schema 扩展不由上游决定，不作为首轮假设。

### 9.4 JSONB 索引方向

`DATA-FRM-004`：

- 关系骨架的相等、关联、状态、当前指针和时间查询优先使用普通 B-tree/组合索引；
- 只有经查询样本证明需要包含、键存在或不稳定字段集合筛选时，才评估 GIN；
- 稳定且高频的单字段筛选、排序或范围统计可评估表达式索引；
- 需要稳定类型、范围、排序或容量保障的动态字段，可建立受控关系投影或可重建读模型；
- 不为每个社团、每个表单或每个自定义字段自动创建物理列或永久索引；
- 索引命中不能绕过对象授权、字段权限、RLS 或正式删除。

`DATA-Q-007` 已确认 JSONB 快照采用稳定字段 UUID 键控对象；重复组采用带 UUIDv7 `item_id` 的有序项目数组，每项内部仍以稳定子字段 UUID 键控。新重复项首次被服务端接受进入权威草稿修订时，由服务端向 PostgreSQL 预取 `item_id` 后完成规范化；客户端临时引用只允许在该保存命令内关联新项目，不能持久化为权威标识，也不能替换已经分配的 `item_id`。字段标题、类型、布局、条件、权限和选项目录来自绑定的不可变表单版本，不复制进每份答案。

缺失 key 表示当前修订未包含该答案；JSON `null` 仅在版本化字段类型目录明确允许“已确认为空”时使用；空字符串和空数组是否有意义由字段类型规则决定并由服务端规范化，客户端不得自由选择多种表示表达同一语义。条件隐藏字段不进入当前正式修订，旧正式修订仍按旧表单版本和当前字段权限还原。

对象选择和附件在 JSONB 中只保存必要稳定引用以还原答案，同时必须在强类型关系表保存提交修订、字段 UUID、必要重复项 `item_id`、目标对象/文件版本、作用域和显示快照；JSON 文本不能替代真实外键、文件检查或字段权限。只有存在持续筛选/排序/统计需求、字段语义稳定、查询计划或容量证据不足、权限/删除可证明且投影可按源修订和水位重建时，才允许建立关系查询投影；不自动建立 EAV、物理列、表达式索引或 GIN。

该结构支持不同社团自由配置既有字段类型、页面/区块、选项、条件、重复组、对象、附件、版本和草稿迁移，不要求每次表单变化执行数据库迁移。它不允许表单创建者定义新的业务状态机、权限角色、任意 SQL/脚本、外部 API 调用或用动态答案替代固定业务骨架；若未来扩张为低代码工作流平台，必须回到产品与架构评审。

## 10. Casdoor 稳定映射、当前权威、写入与对账

### 10.1 数据权威分层

`DATA-CAS-001`：Casdoor 集成数据必须分为以下层次：

| 层次 | 数据内容 | 权威边界 |
|---|---|---|
| 稳定主体映射 | 本地 `subject_id`、Casdoor 组织/账号经验证定位标识、映射状态和版本 | 负责稳定关联，不以姓名、邮箱或学号代替经验证的外部定位标识 |
| Group 稳定映射 | 本地社团/部门/职位、Casdoor `owner`＋`name` 定位元组、用途、层级、显示快照、映射状态和版本 | `v3.108.0` 不假定 Group 存在独立不可变 UUID；名称/路径变化视为身份歧义，须经对账、定向读回或人工异常处置确认，不得静默重绑 |
| 当前可信观测 | 账号/Group 当前值、观测时间、来源、可选外部版本/更新时间、规范化摘要和可信状态 | 是对 Casdoor 当前事实的本地可信观测，不成为独立第二权威；外部更新时间仅作观测证据，高风险命令仍按 SRS 实时回读 |
| 本地业务历史 | 任期、调岗、任免、退出、换届、外部变更和纠错事件 | 本地权威且不可由 Casdoor 当前值覆盖 |
| 本地业务意图 | 目标关系/资料值、原值快照、命令版本、幂等键和处理状态 | 先持久化后执行；意图不等于外部已生效 |
| 外部尝试与读回 | 请求号、步骤、响应类别、读回快照、补偿、错误和最终结果引用 | 外部响应成功仍须按上游需要可信回读；结果不确定不宣称成功 |
| 事件收件 | 本地收件 UUID、来源实例、可选外部事件 ID、认证/验证结论、接收时间、可选源时间、载荷摘要、对象线索、处理状态和去重/合并结果 | `v3.108.0` 兼容模式允许外部事件 ID、签名、时间戳和版本为空；事件只作非权威刷新提示，不能直接改变关系、状态或权限 |
| 对账运行 | 本地运行 UUID、目标范围、能力/配置版本、开始/结束、分页位置、页摘要、已见对象集合、差异候选和收口状态 | 周期正确性路径；只有完整成功运行才可形成缺失候选，仍须定向读回确认；差异不得直接覆盖本地历史 |

### 10.2 写入意图、回读和补偿

`DATA-CAS-002`：每个资料或 Group 写入命令必须关联一个稳定业务意图、一个或多个外部步骤和独立尝试。每次尝试保存唯一外部请求号、目标版本、发起时间、结果类别和脱敏错误。响应超时或未知时先创建/复用读回任务；回读明确后才成功、重试、回退、补偿或进入异常。

复合关系命令必须保存步骤依赖、每步预期关系、读回结果和补偿目标。部分成功不能写成整体成功；补偿未可信确认时保持处理中或高优先级异常，不能授予新增权限。

### 10.3 第三值同步冲突

`DATA-CAS-003`：普通可编辑资料读回第三值时，冲突快照至少保存修改前有效值、本地目标值、Casdoor 第三值、外部可验证版本、读回时间、目标同步版本和冲突版本。用户选择前再次回读；“保留本地值”创建新资料/同步版本，“接受 Casdoor 值”更新本地当前版本；管理员不得代选。姓名、学号等只读权威字段按 SRS 收敛到 Casdoor 当前值。

### 10.4 能力验证门

`DATA-CAS-004`：首版必须兼容学校既有 Casdoor `v3.108.0`；当前源代码核验基线精确固定为官方标签 `v3.108.0`、提交 `a4a5184d0b5c4a570f0cd07283ff928f56d81548`，不把“任意 v3”或更高版本写成已支持范围。启动/部署验收须保存通过 `/api/get-version-info` 取得的运行版本、提交标识和偏移；若学校构建未暴露该端点，则保存经管理员确认的构建来源与制品摘要。实际指纹与本行不一致时，必须作为学校补丁版或新版本建立独立兼容矩阵行并重新验证，不得静默套用本结论。

官方源码能力核验不等于学校真实实例已经通过验收。Claims、UserInfo/账号状态、Group 层级与读写、服务账号最小权限、写后可见性、禁用/删除、MFA、`auth_time`、分页并发变化、限流和人工修改仍须在学校实例执行只读优先、最小写入范围的强制验证。字段设计不得假定未验证的外部事务号、稳定 Group UUID、单调版本或快照游标存在；证据必须进入独立 Casdoor 集成契约。学校补丁、升级或实测结果改变 ADR-009 的权威、失败关闭或恢复边界时，才建立补充/替代 ADR。

### 10.5 `v3.108.0` 事件提示兼容约束

`DATA-CAS-005`：官方 `v3.108.0` 源码提供可配置 Webhook 事件、对象字段、静态请求头、事件投递记录、自动重试和人工重放，但未建立接收方可验证的逐次消息签名、时间戳、nonce 和稳定外部事件 ID 契约；投递体中的记录 ID 也不得被数据模型假定为已持久化且稳定的事件标识。因此首版兼容基线默认关闭 Webhook 提示，不能把它计为 ADR-009 所称“经真实性校验的事件”，更不能用它直接变更账号、资料、Group、状态或权限。

若部署方选择启用低延迟刷新提示，必须同时使用 HTTPS、独立高熵静态请求头秘密、来源/目标固定配置、载荷上限、速率限制、秘密轮换和脱敏日志；收件后只按本地收件 UUID、规范化载荷摘要和对象线索进行有界合并，再创建定向读回。重复、乱序、迟到、伪造或无法验证的提示最多增加一次受限读回，不得重复产生业务结果；提示入口失效时，周期对账和高风险实时读回继续独立成立。

### 10.6 全量对账、写后读回与缺失确认

`DATA-CAS-006`：`v3.108.0` 兼容模式不把 `updatedTime` 当作单调版本、乐观锁或增量游标，也不假定偏移分页提供跨页快照。每次全量对账运行须冻结来源实例、对象类型、组织/范围、页大小、能力/配置版本和运行开始时间，逐页记录页号/偏移、返回数量、规范化页摘要和错误，并以经验证定位键在本地“已见集合”中去重。任一页面失败、越权、限流未收口或运行被取消时，整次运行不得据此推断删除或失权。

完整成功运行可以形成新增、变化和缺失候选，但不能直接覆盖本地历史或收回/授予权限。缺失、禁用、删除、Group 改名/移动等高风险候选必须再执行定向读回；读回仍不可判定时保持陈旧/异常并失败关闭。RanaMinder 发起的每次外部写入都按 `DATA-CAS-002` 定向读回目标对象；登录、增强认证、高风险操作和权限敏感请求按 SRS 实时读回，不等待 Webhook 或周期运行。对账频率、页大小、限流、超时和积压阈值留给集成/运维规格，但必须以目标规模证明确认的发现时延和恢复能力。

## 11. 后台任务、租约、尝试、重试与过期任务

### 11.1 权威任务模型

`DATA-JOB-001`：持久任务至少包含以下逻辑字段类别：

| 类别 | 必须表达的内容 |
|---|---|
| 来源 | 来源模块、业务意图、源对象、源对象版本、事务边界类型和父追踪编号 |
| 作用域 | 普通社团、联合活动、平台或技术运行域；后台执行时重新建立最小上下文 |
| 类型与载荷 | 版本化任务类型和最小载荷；跨信任边界执行运行时结构校验 |
| 状态 | 待执行、可领取、执行中、成功、可重试失败、永久失败、取消/失效等技术状态；不得制造新业务状态 |
| 调度 | 可执行时间、截止/过期时间、优先级方向、当前调度版本 |
| 租约 | 租约令牌、持有者、取得时间、到期时间和任务版本 |
| 尝试 | 尝试号、开始/结束、结果类别、脱敏错误、外部请求号和下次可执行时间 |
| 幂等 | 业务幂等键、规范化请求摘要、源版本和既有结果引用 |
| 结果 | 最终业务结果引用、外部确认、文件/通知结果或结构化失败；大正文不复制到任务表 |

`DATA-Q-004` 已确认组合模式：通用任务执行信封与通用尝试记录保存任务类型/版本、来源模块、作用域、业务命令 UUID、调度、租约、技术状态、尝试、幂等和脱敏执行结果；模块拥有的强类型意图/结果表保存源对象、目标状态、原始快照、预期版本、专项约束和最终业务结果。任务载荷只允许保存版本化、最小化、经过运行时结构校验的执行参数，不能成为未建模的业务事实仓库。

业务事实、模块任务意图和必要通用任务信封必须按对应事务边界原子创建，禁止只有通用信封而缺少必要强类型意图的孤儿任务。纯技术重建或维护任务可以不拥有领域意图，但必须属于显式允许的版本化技术任务类型，且只能影响可重建派生数据或技术运行事实。完整任务详情允许连接模块意图表；通用任务表不得复制 Casdoor 原关系快照/目标关系、文件业务引用、通知收件人正文、导出权限快照或删除清单正文。

### 11.2 至少一次执行与结果幂等

`DATA-JOB-002`：任务可以因租约到期、进程终止或恢复而重复领取，因此每次执行必须在产生副作用前重检：当前授权/系统身份、源对象状态、源对象版本、任务调度版本、安全开关、删除状态和既有幂等结果。已成功结果返回原引用；旧任务不得覆盖更新业务版本。

重试退避算法、最大尝试、租约时长和轮询批量不由上游唯一决定，必须成为可观测、可测试的配置或任务类型策略，不得隐藏在任务库默认值中。

### 11.3 截止、到期和过期任务

`DATA-JOB-003`：每个截止任务携带目标对象、截止/窗口版本和预期状态。执行时若版本已失效、对象已终态、活动处于冻结区间或最后一项竞争命令先成功，任务只保存幂等忽略结果，不推进状态。

任务记录自身的清理期限不能删除仍被业务历史、删除清单、故障验收或审计保留所引用的尝试。任务数据保留期按第 16 节分类，不能默认跟随普通运行日志 90 天总期或其在线/归档分层。

### 11.4 批次数据

`DATA-JOB-004`：受控批次分别保存预览、冻结目标项、逐项意图、逐项结果和汇总。目标项至少包含源对象稳定 ID、预览时版本、操作类型、业务/邀请类型和单项幂等键。批次执行不得重新查询筛选结果；汇总由逐项终态派生，不能覆盖单项历史。

## 12. 文件元数据、对象存储、检查与删除状态

### 12.1 逻辑模型

`DATA-FIL-001`：

| 逻辑实体 | 关键字段类别 | 权威与约束 |
|---|---|---|
| 文件逻辑记录 | 稳定文件 ID、上传者、创建作用域、业务类别、当前状态/版本 | 表示业务文件，不等于某个对象存储地址 |
| 不可变文件版本 | 文件版本、权威原件定位记录、声明/检测类型、声明/实际大小、内容摘要、创建时间 | 检查结果绑定具体版本；重新上传建立新文件/版本，不覆盖危险版本 |
| 对象定位记录 | Bucket 角色、键格式版本、高熵随机定位符、对象类别、实际大小、可信 SHA-256、存储并发令牌、生命周期状态 | 只负责定位和核验，不是业务身份、权限、文件版本或内容去重键 |
| 上传会话 | 上传会话 ID、隔离对象定位记录、目标文件版本、允许大小/类型、到期、封存与完成状态 | 不能成为永久下载凭据或业务引用；客户端不得指定对象键 |
| 检查版本 | 文件版本、检查规则/引擎版本、状态、开始/结束、脱敏结果和重试状态 | 任一必需检查未通过都不能标记可用 |
| 派生预览 | 源文件版本、派生类型、临时派生对象定位记录、生成版本、状态和删除状态 | 可重建且不能扩大原文件权限 |
| 业务引用 | 业务对象、作用域、字段/附件槽位、文件版本、引用状态和版本 | 正式提交引用与提交修订同事务建立；访问从当前业务授权进入 |
| 删除/清理步骤 | 文件版本、对象副本类别、删除清单项、步骤状态、尝试和核验 | 任一在线副本未确认删除时不得宣称正式删除完成 |

### 12.2 对象存储键与内容边界

`DATA-FIL-002`：`DATA-Q-012` 已确认每个相互隔离的 RanaMinder 部署环境使用三个专用私有 Bucket。这里的“部署环境”指开发、测试/验收或生产等具有独立数据、凭据和备份边界的一套部署，不是社团租户、学校部门、应用节点、后台任务节点或对象存储服务器。开发、测试/验收和生产不得共用 Bucket、对象键命名空间、访问凭据或备份集；同一环境内的所有普通社团和联合活动共享下表三个存储区，不按社团、用户、业务模块或文件格式增建 Bucket。

| Bucket 角色 | 保存内容 | 权威与访问边界 | 备份/恢复边界 |
|---|---|---|---|
| 待检查隔离区 | 未完成上传、待自动技术安全检查、检查中、检查失败及等待清理的字节 | 只允许上传签发、检查/晋升和清理职责访问；不能生成普通预览/下载地址或满足正式提交 | 不属于正式业务恢复集；故障后上传会话明确失败或要求重传，不伪装已恢复 |
| 权威原件区 | 检查通过、完成晋升核验且可被应用级文件版本引用的原件 | 只允许晋升写入、受控读取签发、正式删除、对账和备份职责访问；任何文件替换都写入新键 | 必须与 PostgreSQL、删除清单及必要配置一同进入独立故障域备份和恢复验收 |
| 临时派生区 | 安全预览、水印、转码、临时导出及其他可重建或限时字节 | 按派生类型和源版本受控生成、访问和清理；不能反向成为原件或业务事实 | 默认不进入权威备份集；恢复后按源版本重建、重新生成或按到期状态清理 |

三个 Bucket 默认私有且使用分离的最小权限职责；“三个 Bucket”是同一 S3 兼容对象存储中的三个逻辑容器，不要求三套服务、三台服务器或三倍存储。官方单机和拆分部署使用相同逻辑边界，具体 Bucket 名称由部署配置提供，不写入业务数据或源码常量。

对象键采用版本化技术前缀和由服务端密码学安全随机源生成的不少于 128 位有效熵的随机定位符，例如 `v1/upload/{random}`、`v1/object/{random}`、`v1/preview/{random}` 和 `v1/export/{random}`。环境由 Bucket 隔离，键中不编码数据库 UUIDv7、学生姓名、学号、邮箱、社团、联合活动、原始文件名、扩展名、权限或内容摘要；客户端不得提交或复用对象键。原始文件名只在受权限控制的 PostgreSQL 元数据中保存必要显示值。

每个对象键严格只写一次、永不覆盖和永不复用。单段上传、完成分段上传及隔离对象向权威原件区/临时派生区的复制都必须采用经目标实现验证的 create-only/目标不存在条件或等价防覆盖能力；只依赖随机碰撞概率、SDK 默认覆盖语义、上传会话状态或写前 `HEAD` 检查不足以通过。预签名上传即使在有效期内被重放，也只能命中原隔离键并因只写一次条件失败，不能改变已检查或已晋升对象。

PostgreSQL 的应用级不可变文件版本是唯一业务版本。三个在线 Bucket 首版均不得启用对象存储原生 Versioning 或 Object Lock；部署预检必须验证 Bucket 当前状态及不存在历史非当前版本，曾启用后仅“暂停”版本控制不能视为满足。备份仓库可以在不改变在线访问、删除和恢复门的前提下使用独立版本、快照或不可变保护，但恢复材料在开放业务前仍须重放正式删除清单。若部署必须对在线 Bucket 启用原生 Versioning、对象锁、法定留置或 WORM，须重开本问题，并补齐版本 ID 权威记录、全版本删除核验、留置冲突、成本和恢复规则。

可信内容摘要由文件检查/处理流程对实际字节计算并保存 SHA-256；对象存储 ETag、分段 ETag、对象键或供应商 Version ID 只可作为存储并发/诊断证据，不得冒充全文件内容摘要、业务版本、授权或去重依据。

同一内容摘要不代表同一业务引用；未经明确设计不得用内容去重把不同用户、不同作用域或不同删除生命周期合并为一个不可分离对象。

### 12.3 检查、预览和业务绑定

`DATA-FIL-003`：扩展名、实际类型、大小、恶意内容和安全预览分别记录检查结果及规则版本。这里的检查是自动技术安全检查，不授予管理员人工阅读或内容审核他人附件的新权限。检查中、失败或隔离的文件不可预览、下载或进入正式提交。

检查通过只允许创建晋升意图，不等于权威原件已经就绪。晋升任务必须固定本次已检查的隔离对象状态，以只写一次的新键复制到权威原件区，核对目标对象大小和可信 SHA-256，并在 PostgreSQL 中原子收口对象定位记录、文件版本状态和必要审计；源对象在复制期间变化、目标已存在、内容核验失败或数据库结果未知时不得放行。业务绑定必须引用已经完成晋升核验的确定文件版本，并与提交修订/引用版本竞争；孤儿清理与正式绑定只允许一个成功。任何仍有效的上传地址只指向隔离键，即使被重放也不能覆盖或改变已晋升原件。

下载和预览每次根据当前主体、业务对象、字段、任务、社团/联合关系、文件检查和删除状态重新授权。短时地址只保存最小生成/失效证据，不成为长期授权事实。

### 12.4 跨存储恢复

`DATA-FIL-004`：数据库先保存元数据、业务引用意图和任务，再异步完成对象操作。对象操作成功但数据库状态未知、数据库引用存在但对象缺失、预览缺失或删除部分失败，都必须在恢复/一致性任务中形成真实差异，不得自动伪造可用或删除完成。

数据库权威任务负责上传会话到期、孤儿清理、临时派生到期和正式删除，执行前必须重新检查对象定位记录、业务引用、文件/源版本、到期版本和删除清单。对象存储 Lifecycle 只可在已验证兼容能力下作为终止长期未完成分段上传和清理超过业务最大期限及安全缓冲期的技术兜底，不得决定产品到期时间、跳过引用检查、直接推进业务状态或替代审计。权威原件区不得配置会脱离数据库任务自行到期删除正式附件的规则。

正式删除清单必须枚举权威原件、仍关联的隔离副本、全部在线派生物和未过期导出，逐项执行删除并回读核验；任何在线副本未确认消失时保持未完成。恢复只把权威原件区视为附件字节恢复源；隔离区会话明确失败或重新上传，临时派生区按当前源版本重建或按到期状态清理。数据库—对象存储差异、删除清单重放和派生重建未收口前，不得宣称附件恢复完成。

## 13. 通知事实、渠道状态、审计与运行证据分离

### 13.1 通知模型

`DATA-NTF-001`：

| 记录 | 必须保存 | 不能保存或替代 |
|---|---|---|
| 通知事实 | 逻辑事件 ID、来源业务对象/版本、事件类型、事件时间、最小摘要、当前办理对象引用 | 完整报名表、内部评语、附件正文、联系方式全集、令牌或业务当前状态副本 |
| 收件人快照 | 通知事实、收件人主体、当时收件原因、社团/联合/平台范围和去重键 | 通过当前角色动态反算而丢失原收件责任 |
| 站内呈现 | 通知事实、收件人、投递状态、已读/处理/隐藏和呈现版本 | 物理删除通知事实；通过已读推进业务状态 |
| 渠道意图 | 收件人、渠道、资格结论、发件身份、模板版本、目标地址版本和任务 | 把邮件资格失败解释为业务失败 |
| 渠道尝试 | 渠道消息 ID、尝试号、响应类别、时间、脱敏错误和最终结果 | 覆盖旧投递证据或把“发送成功”写成“用户已读” |

站内信紧急关闭只暂停对应渠道呈现/投递；新通知事实和收件人仍创建。恢复按原事件时间补投，并以逻辑事件＋收件人去重。

### 13.2 业务审计

`DATA-AUD-001`：业务审计至少保存操作者稳定主体或系统来源、当时角色/任务/作用域快照、目标对象、命令/事件、旧值与新值的必要脱敏差异、原因、请求/任务追踪、结果和发生时间。高风险业务结果与关键审计同一事务；审计保存失败时原命令回滚。

业务审计不得保存密码、令牌、验证码、邮件密钥、附件正文、完整报名正文、完整联系方式或正式删除后不应继续存在的正文。审计记录正常情况下追加式保存；事实纠错和正式删除按上游规则追加处理结果或最小化，不覆盖原责任链。

### 13.3 脱敏运行证据

`DATA-AUD-002`：运行日志/运行证据与业务审计分离。运行证据保存请求/任务追踪编号、技术步骤、脱敏错误类别、必要版本和时间；普通脱敏运行日志默认共保留 90 天，其中 30 天在线、后续 60 天压缩归档。其存储介质是否全部位于 PostgreSQL 不由上游决定，但内置状态页只读取规范化当前状态、最近结果/异常和更新时间，不展示学生业务正文。

业务审计不能因运行日志到期而删除；运行日志也不能因共享追踪编号替代业务审计。完全不可用时不承诺系统外发现或告警。

## 14. 配置版本、当前指针与秘密引用

`DATA-CFG-001`：平台/社团配置、权限模板、数据使用说明、字段映射、邮件模板和安全阈值采用“配置根＋不可变发布版本＋当前指针＋发布历史”逻辑模型。发布事务要么完整切换当前版本并记录审计/通知，要么继续完整使用旧版本；不能部分对象使用新版本。

配置版本保存适用范围、来源版本、内容摘要、测试/预览结果、发布人、发布时间和状态。业务对象需要历史还原时保存所用配置版本或发布快照。回滚通过创建和发布新版本表达，不覆盖旧发布版本。

邮件密钥、Casdoor 服务凭据和其他秘密只保存受控秘密引用、密钥版本、测试/启用状态和轮换历史；普通配置、通知、审计、任务载荷和错误中不得出现明文。`DATA-Q-014` 已确认部署秘密继续通过 ADR-010 的数据库外受控配置入口或未来秘密提供器加载，数据库托管秘密使用服务端应用层 `AES-256-GCM` 和数据库外版本化密钥环；具体配置字段名、秘密提供器产品、文件路径、运维角色和自动化工具仍由安全与部署设计决定。

## 15. 13 条故障规则的数据保存、失败与恢复责任

`DATA-AUD-003`：每条 `SRS-FAIL-*` 都必须有权威状态、失败证据和恢复收口，故障记录不能只存在于短期日志。

| 故障规则 | 必须保存的数据责任 | 失败关闭责任 | 恢复与核验责任 |

覆盖结果：13/13 条故障规则均有数据保存、失败关闭和恢复责任。

## 16. 归档、正式删除、恢复重放与数据保留

### 16.1 归档不是删除

`DATA-DEL-001`：普通/联合活动终态、轮次关闭、任务撤销和业务锁定通过状态与归档事件关闭普通写入，不删除正式提交、评价、邀请、关系、作者、附件引用或历史。归档后每次读取仍按当前主体、对象、作用域、字段和归档规则授权；历史角色和旧任务不继承访问。

### 16.2 正式删除清单

`DATA-DEL-002`：正式删除必须建立稳定删除命令和逐项清单。清单至少表达：

- 删除范围、来源对象/版本、执行前活跃关系检查和影响预览版本；
- 操作者、最近认证证据引用、原因、确认时间和命令幂等键；
- 数据库正文/关系、对象存储原件/预览、缓存、搜索索引、统计投影和未过期导出等步骤；
- 每步状态、尝试、最近脱敏错误、完成时间和核验结果；
- 只保留范围、步骤、结果和责任所需且不含被删正文的最小删除审计。

执行开始后立即撤销业务访问。已经完成的删除步骤不得为了补偿而恢复个人数据；未完成步骤持续重试。系统外已发送邮件和已下载副本不可召回，清单必须记录此边界但不能用它拒绝删除系统内副本。

### 16.3 备份恢复后重放

`DATA-DEL-003`：恢复运行在开放普通写入前必须：

1. 确认恢复点和事务日志覆盖；
2. 重放恢复点后仍应生效的正式删除清单；
3. 核对数据库文件引用与对象存储原件/预览；
4. 对账 Casdoor 当前账号和 Group 关系；
5. 把无法确认的差异进入同步异常或保持高风险写关闭；
6. 保存恢复门各项结论、责任人/系统来源、时间和开放写入决定。

删除清单和最小删除审计必须被纳入恢复链并可定位；如何保证恢复点后删除清单可获得，进入部署运维与备份方案，不在本文假定单一存储技巧。

### 16.4 数据保留分类、计时起点与配置范围

`DATA-DEL-004`：正式业务长期保留与临时/技术数据自动清理必须分开；所有自动清理都由本系统的权威任务执行，不能跟随框架、对象存储或日志组件默认值。除正式删除外，首版没有自动删除正式业务数据的能力，也没有以争议、申诉、调查或诉讼为理由暂停正式删除的数据保全能力。

| 数据类别 | 默认规则与计时起点 | 可配置范围 | 到期与访问边界 |
|---|---|---|---|
| 正式业务、历史修订、正式附件、通知事实/收件人/呈现、业务审计、任务业务意图和正式结果 | 长期保留；不启动自动删除时钟 | 不适用 | 只读归档不扩大访问；仅正式删除可移除 |
| 未提交草稿及其附件 | 最后一次成功的内容编辑后 30 天；提前 7 天通知草稿所有人 | 14 至 60 天 | 继续编辑重新计时；到期前重验草稿和文件引用 |
| 未关联上传、扫描失败文件和孤儿预览 | 确认不存在有效引用或扫描最终失败后 24 小时 | 12 至 48 小时 | 文件实体清理；文件摘要、扫描结果和脱敏失败原因保留 30 天 |
| 成功导出 | 生成完成后 24 小时 | 6 至 48 小时 | 申请人可提前删除；每次下载重验当前权限，失权、停用或正式删除命中时立即撤销访问 |
| 失败、取消或中断导出的部分文件 | 任务进入终态后 1 小时 | 15 分钟至 2 小时 | 不提供下载；保留脱敏任务结果，不保留文件实体 |
| 终态任务技术执行信封和尝试 | 终态后 180 天 | 120 至 240 天 | 仅技术执行记录到期；业务意图和正式结果继续长期保留 |
| 普通脱敏应用运行日志 | 事件时间后共 90 天：最近 30 天在线可检索，后续 60 天压缩归档 | 总期 60 至 120 天；在线期 14 至 30 天且不得超过总期 | 不得包含业务正文、附件内容、完整联系方式、令牌或密钥 |
| 网络运行和安全事件日志 | 事件时间后 6 个月 | 6 至 12 个月 | 与普通运行日志、业务审计分离；不得配置到 6 个月以下 |
| 备份恢复点 | 创建完成后 30 天 | 30 至 60 天 | 只决定可选恢复点，不决定当前正式业务数据是否保留；恢复仍重放删除清单 |
| 搜索、统计和缓存派生数据 | 不独立形成保留期限 | 不适用 | 源范围、权限或删除变化即失效；允许回源重建 |

上游没有匿名化入口；本文不创建匿名化替代正式删除。

### 16.5 版本化保留策略与高风险发布

`DATA-DEL-005`：保留策略采用“策略根＋不可变发布版本＋当前指针”模型，发布版本至少保存数据类别、默认期限、允许上下限、计时起点、在线/压缩层、提醒规则、适用范围、影响预览摘要、发布原因、操作者、重新认证证据、发布时间和状态。首版仅允许平台级统一策略，社团、部门和普通管理员不能创建局部覆盖。

每次发布都必须由当前有效超级管理员在最近 10 分钟重新认证后完成；执行时再次确认其当前 Group，并要求填写原因、查看影响预览和二次确认。认证过期、Casdoor 不可用、当前 Group 无法可信确认、版本已变化或操作者失权时，发布被拒绝且不产生副作用。

新发布版本同时适用于新旧数据：延长期限立即生效；缩短期限不会立即批量删除，已有数据至少获得 7 天缓冲。直接关联用户的草稿和仍可下载导出在缓冲期内收到到期通知；没有个人责任人的任务、日志、备份和文件技术记录，只在超级管理员影响预览、审计和内置状态中呈现。范围外值被拒绝，学校政策确需突破范围时必须重开 `DATA-Q-011`。

### 16.6 清理执行、失败收敛与可观测性

`DATA-DEL-006`：到期清理先撤销访问并转为“待物理清理”，再由权威任务按引用、版本和正式删除状态重新核验后执行各存储步骤。任何仍有有效业务引用、被正式删除流程接管或在核验期间发生新引用的数据都不得被临时清理。

跨数据库、对象存储、缓存、索引和导出存储的某一步失败时，不得把清理记为成功，也不得恢复已经撤销的访问。任务记录脱敏错误、已完成步骤和未完成步骤，按退避策略自动重试；连续 24 小时未完成时，在内置状态页显示高优先级异常，之后每日重试直至成功并审计。临时清理失败不额外通知普通用户；正式删除失败继续遵循 `AUD-009` 通知相关申请人和超级管理员的规则。

## 17. 搜索、筛选、统计、个人中心、工作台与缓存派生模型

### 17.1 派生模型通用信封

`DATA-DER-001`：每个可持久化派生记录至少保存派生类型、源对象/源版本、源作用域、派生版本或水位、生成任务、生成时间、失效/删除状态和重建依据。派生记录不能产生源对象不存在的状态、权限或历史。

| 派生模型 | 来源 | 必须携带的隔离信息 | 失效/重建要求 |
|---|---|---|---|
| 公开发现入口 | 公开社团字段、已发布普通/联合活动；“找社团”和“找活动”分别投影社团展示名称与活动名称及其规范化派生键 | 搜索模式、公开状态、社团或联合活动、源名称/发布版本 | 两种名称条件不得混合；源名称、活动状态或公开范围变化后失效；详情仍回源 |
| 名称搜索投影 | 人员当前姓名/学号/账号；社团展示名称、活动名称、部门名称、职位名称和 Casdoor Group 名称/稳定标识 | 对象类型、稳定对象标识、源作用域、源名称版本、字段分类、投影格式版本 | 权威名称或范围变化后失效；人员禁用错别字候选；非人员可受控近似；不包含拼音或首字母字段；必要派生数据可全量重建且不能用于授权或唯一性 |
| PostgreSQL 搜索文档 | 已授权范围内的权威关系字段和已明确允许的动态投影 | 普通 `club_id`、联合域、对象类型、源版本和字段分类 | 权限/字段/删除变化触发失效；可全量重建；未确认的正文不得进入全文搜索 |
| 统计投影 | 申请、路径、邀请、成员等权威状态 | 数据域、统计口径版本、源水位 | 失败不发布新结果；旧水位不得覆盖新结果 |
| 个人中心 | 主体相关申请、日程、邀请、待办和成员经历 | `subject_id`＋每个源对象真实作用域 | 聚合查询不扩大各源对象权限；不形成全局角色快照 |
| 管理工作台 | 当前角色型待办、异常、批次和任务 | 目标角色类型、社团/联合域、源对象/版本 | 打开/执行时重新授权；旧待办不得继续处理 |
| 应用缓存 | 已提交查询结果或不可变配置 | 主体/社团/联合/字段范围、源版本和配置版本 | 可丢失重建；多实例失效失败可见；禁止缓存权威写状态 |

`DATA-Q-009` 的扩展准入子项已确认：首版只允许 PostgreSQL 官方随附扩展进入受控候选，且必须由具体约束或查询证据逐个批准；官方随附身份不构成自动安装理由。`pg_trgm` 已于 2026-07-30 获批为首版第一个必要扩展，用于非人员名称的中文连续子串和受控错别字近似候选；首版近似阈值显式固定为 `0.6`。索引采用按表证据门控，不预设全部非人员名称统一使用 GiST 或 GIN，也不因扩展已安装而强制每张候选表建立 trigram 索引；具体表可以选择 GiST、GIN 或暂不建立 trigram 索引。每项选择仍须以代表性样本、真实查询形态、查询计划、读写成本和恢复重建证据确认。`btree_gist` 已由 `DATA-Q-010` 批准为首版第二个必要扩展，专用于统一当前人员时间占用的 UUID/封闭标量相等与范围重叠约束；`DATA-Q-014` 已确认服务端应用层加密并明确不批准首版安装 `pgcrypto`，其他扩展须重新评审 `DATA-Q-009`。

同一问题的排序子项已确认采用“稳定权威默认＋显式展示排序”：数据库编码为 UTF-8，默认使用 PostgreSQL 18 确定性的 `pg_unicode_fast`；权威相等、唯一性、关系、授权和索引语义不得依赖 ICU 或非确定性排序。只有明确需要中文友好顺序且不改变业务结果的派生列表/展示查询可以显式使用经部署验证的 ICU 中文排序；ICU 不可用、版本不符或未验证时使用稳定码点顺序，不得导致写入、授权或业务失败。中文分词和搜索匹配不由排序规则承担。

`DATA-DER-003`：需要持久化名称搜索投影时，至少保存对象类型、稳定对象标识、权威源及源名称版本、适用作用域、原始显示名称、投影格式版本、生成时间、失效状态和重建水位；Casdoor Group 另保存可直接检索的原始名称与精确匹配的稳定 Group 标识。人员投影另保存学号/账号精确检索键并明确禁用错别字候选；非人员投影可以包含受控近似匹配所需的规范化形式。首版不得建立全拼、拼音片段、首字母、拼音字典或拼音生成器版本字段。首版近似阈值固定为 `0.6`；搜索规范化值采用 NFC、Unicode 大小写折叠、再次 NFC、首尾 Unicode 空白清理和内部连续 Unicode 空白压缩，不执行 NFKC、标点、简繁体或全角/半角折叠。规范化值统一由 PostgreSQL 中的显式版本化函数生成，应用、任务和导入提供的同名派生值不得被信任；默认不统一持久化，具体表按证据选择查询时计算、表达式索引、存储生成列、普通可重建派生列或集中投影。第三层固定按相似度降序、规范化名称和 UUID 排序；第一/第二层沿用对应领域列表的明确排序，没有明确排序时按规范化名称和 UUID 稳定兜底，不增加子串位置、名称长度或其他搜索分数。所有派生键都不是对象身份、业务唯一性、作用域或授权依据，失效或丢失时只能从权威名称重建；若最终查询可直接安全使用权威名称字段，则不得仅为形式统一强制建立独立投影表。

### 17.2 权限与删除

`DATA-DER-002`：派生数据只能在当前服务端授权之后读取。缓存命中、搜索文档存在、个人中心曾显示、工作台旧待办或导出申请时有权，都不能跳过当前对象、状态、字段、社团/联合和安全开关检查。

正式删除清单必须覆盖所有持久派生记录和未过期导出；缓存/索引删除失败保持清单未完成。派生记录丢失时回源重建，不得反向从缓存恢复业务事实。

### 17.3 搜索、筛选、排序与分页的能力边界

`DATA-FLT-001`：首版查询必须区分下列能力，不得因为它们常出现在同一个页面或查询中，就用一个不受控的通用查询表达式替代。

| 能力 | 本文定义 | 不能替代 |
|---|---|---|
| 名称搜索 | 对已授权候选集合执行稳定标识/名称精确、中文连续子串及已确认对象类型的近似候选匹配 | 作用域、授权、资格、业务状态或对象绑定 |
| 结构化筛选 | 对服务端登记的强类型字段、关系或时间范围应用确定性谓词 | 正文全文检索、任意 JSONPath、任意 SQL 或权限判断 |
| 系统候选约束 | 服务端先依据当前用户、操作、社团/联合/任务作用域、对象状态和业务资格缩小可见/可选集合 | 用户可关闭的筛选条件或客户端可信范围 |
| 分区/视图 | 上游明确的“待我处理/进行中/历史记录”“当前/历史活动”等固定产品分区 | 任意状态字符串或可独立改变权威状态的副本 |
| 排序 | 对已经授权并筛选后的结果给出可复现顺序 | 推荐、自动优先级、人员排名或业务结论 |
| 分页 | 在同一授权、筛选和排序合同下稳定继续读取 | 跨页冻结业务事实、跳过详情鉴权或长期快照 |

筛选只会缩小已经通过当前授权和作用域约束的候选集合，永远不能扩大集合。客户端传入的社团、联合活动、角色、对象类型、字段名、操作符、排序字段、JSONPath 或分页游标都属于不可信输入；服务端必须从登记查询入口、目标对象和当前授权重新构造实际查询合同。

| 查询入口 | 已确认筛选维度或固定分区 | 权威字段/关系来源 | 结构性候选约束 | 事实与 SRS 来源 |

| 受保护对象选择器 | 用户主动输入的名称搜索；候选集合必须先按当前范围、权限和业务资格过滤 | 主体、社团、部门、职位和 Casdoor Group 的稳定标识与当前关系 | 当前用户＋操作＋普通/联合/任务作用域＋对象状态/资格；保存时按稳定标识重验 | `ORG-012`、`FORM-006`；SRS 6.3、7.6 |
| 管理工作台与批次预览 | 工作台按当前权限聚合七类已确认事项；批次保存实际使用的筛选与预览快照 | 各领域权威对象、当前可处理性、关键期限、异常和批次目标 | 固定当前社团；只含当前仍有权查看/处理的对象；预览后新命中对象不得进入批次 | `ORG-040`；`SRS-INV-024`；SRS 6.5、9.2 |

“找社团”当前只有社团展示名称搜索和当前/历史公开活动入口，不得擅自增加活动类型、报名状态或截止时间筛选。成员、申请、面试、邀请、部门、职位、文件、表单提交和任务列表虽然需要内部作用域/状态谓词，但上游尚未普遍承诺面向用户的任意组合筛选器；接口设计只能为有明确来源的页面登记筛选键，不能从数据库字段倒推出新产品功能。

### 17.5 服务端筛选目录与类型合同

`DATA-FLT-003`：每个允许筛选的查询入口必须拥有版本化的服务端筛选目录。目录是接口、安全、迁移和测试共同使用的下游合同，至少登记：

- 稳定的查询入口和筛选键，不暴露物理表名、列名或 JSONPath；
- 值类型、允许操作符、单值/多值、空值语义、最大值数和允许组合；
- 映射的权威字段、关系或可重建投影，以及其数据所有模块和作用域；
- 访问角色、字段分类、RLS 模式、是否允许导出/批次快照及重新鉴权点；
- 排序键、稳定次级键、分页合同、查询版本和失效/重建规则；
- 需求事实、SRS、性能目标、候选索引和负向测试来源。

未知筛选键、未登记操作符、类型不匹配、越界值、无权维度、损坏或跨查询复用的游标必须失败关闭并返回可区分的输入错误；不得静默忽略后返回更宽结果。普通应用连接不得根据客户端输入拼接列名、排序表达式、运算符、SQL 片段、JSONPath 或函数名。ORM 或 NestJS 的查询参数绑定、默认分页和空值处理不能代替该目录。

目录可以由接口实现中的强类型登记和迁移版本共同承载，本轮不决定具体 API 形态、代码生成方式或 ORM。目录只登记已经有上游来源的查询行为；新增筛选键若改变用户可见能力，先回到需求事实/PRD/SRS，纯物理映射变化则进入数据迁移与测试评审。

### 17.6 作用域、RLS 与关系筛选

`DATA-FLT-004`：受保护筛选查询的执行顺序在逻辑上固定为“认证与安全限制→登记查询入口→冻结允许作用域→RLS/数据库作用域约束→对象资格和字段权限→用户筛选→排序与分页→响应字段投影”。数据库可以在不改变语义的前提下优化执行计划，但任何优化不得让未授权行先进入可被计数、排序、聚合、错误信息、耗时差异或缓存键观察的候选集合。

- 普通社团列表使用权威 `club_id` 及作用域完整外键；当前工作空间提示不是筛选权威；
- 联合活动基础共享记录使用 `joint_activity_id`，参与方私有记录还须使用 `participant_club_id`；不能把参与社团集合降为普通 `club_id IN (...)`；
- 个人中心等登记聚合查询可以使用 `DATA-Q-006` 的冻结有限集合只读上下文，但每个源对象仍携带真实作用域，且不得形成全局角色快照；
- 对象选择器的候选资格属于服务端强制谓词，客户端隐藏禁用项、搜索命中或曾经选择成功都不能替代保存时重验；
- 平台特权查询使用独立入口和数据库身份边界，完整记录特权作用域与审计，不与普通筛选参数共用隐式绕过。

若 RLS 上下文缺失、集合/元组为空或不完整、连接池上下文残留、查询版本不匹配或源对象作用域无法解析，查询必须返回空/拒绝或明确失败，不能退回“不过滤”。

### 17.7 强类型、时间、空值与关系集合语义

`DATA-FLT-005`：筛选值必须先按登记类型验证和规范化，再进入查询。不同筛选键之间的 AND/OR 组合、同一键多值语义、是否允许排除条件及空值行为，必须由该入口的筛选目录显式定义；PostgreSQL 的三值逻辑、ORM 对空数组/`null` 的处理或客户端省略字段都不能成为产品规则。

第一轮数据语义如下：

- 状态和类型使用对应状态机/领域的受控代码集合，不接受自由文本，也不建立全系统通用状态枚举；
- 报名状态中的“正在报名”是查询时派生筛选值，不是持久状态。候选必须仍满足公开条件、报名通道当前状态为“开放”、没有活动整体暂停或终态覆盖，并且当前有效截止严格晚于服务端查询时刻；任何条件不成立都失败关闭。自动截止任务短暂延迟不得让已过期活动继续命中；该筛选也不能替代提交时的账号、资料、邮箱、成员关系和个人资格校验；
- 社团、活动、部门、职位、主体和业务对象使用稳定内部标识；名称只参与搜索或显示，不作为关系筛选键；
- 当前关系、历史关系和“在某时间有效”必须分别映射当前权威关系或带起止边界的历史事实，不能用一张当前表的存在性冒充历史；
- 用户界面的日期/日期时间范围必须由接口契约声明平台/活动时区、端点包含性和精度，再规范化为可比较的绝对时间。数据库内部优先用明确的半开区间表达连续时间窗口，避免相邻区间重复或遗漏；
- 未提供筛选键、显式选择“全部”、筛选 `NULL`/未知、空字符串和空集合是不同输入。只有目录明确登记后才允许相互等价；
- “报名截止时间”筛选已确认同时提供今日截止、3 日内、7 日内三个快捷范围和自定义起止日期。自定义日期按平台时区自然日解释且起止日均包含，服务端规范化为 `[开始日 00:00, 结束日次日 00:00)` 的绝对时间区间；设发起查询时的平台日期起点为 `D`，快捷范围分别规范化为 `[D, D+1 日)`、`[D, D+3 日)`、`[D, D+7 日)`，即覆盖当天、当天及随后两天、当天及随后六天。当天早些时候已经截止的活动仍可命中日期范围，报名通道是否仍开放由报名状态独立判断。两类入口都筛选权威当前有效截止版本，不能保存界面标签代替截止事实，也不能依赖客户端时钟；
- 容量剩余、当前可报名、当前可处理等条件只能用权威容量、状态、期限和资格计算候选；筛选结果是读取快照，不能替代提交事务中的容量、版本或资格竞争校验。

### 17.8 JSONB 动态答案与筛选边界

`DATA-FLT-006`：首版没有“对所有动态答案任意筛选、排序或聚合”的产品事实。客户端不得提交字段 UUID、任意 JSONPath、比较符或表达式直接查询 `answers` JSONB；表单设计者也不能因创建了一个字段就自动获得跨提交筛选、排名或统计能力。

只有同时满足以下条件，某个动态字段才可成为后续登记筛选键：

1. 上游产品行为或经确认的管理查询明确需要该维度，并说明可见角色和业务范围；
2. 字段具有稳定 UUID、固定字段类型、适用的表单版本集合和明确的缺失/空值/多值语义；
3. 字段级权限、原提交者回看、普通/联合域和正式删除边界可在候选、计数、排序和导出中一致执行；
4. 查询只使用已发布版本及其权威提交修订，不能把草稿、隐藏旧答案或不兼容字段版本混成同一语义；
5. 代表性数据证明查询时 JSONB 访问可接受，或批准由权威答案重建的强类型投影；投影携带源提交/修订、字段/表单版本、作用域、格式版本和重建水位。

动态字段投影只是筛选和统计加速层，不改变原答案、字段含义、状态、资格、权限或业务唯一性。字段删除、类型不兼容变更、权限收紧、修订、纠错和正式删除必须使相关投影失效或重建。GIN 只在已登记的包含/键查询有证据时评估；稳定的数字、日期、枚举或对象关系路径优先评估强类型投影和 B-tree/范围索引，而不是建立覆盖整个答案正文的通用 GIN。

### 17.9 批次、导出与可复现筛选快照

`DATA-FLT-007`：筛选页面本身通常读取当前事实，不因翻页形成长期冻结快照；但上游明确要求的受控批次预览和异步导出必须在发起时形成可复现输入。

| 场景 | 必须保存 | 重试/执行语义 |
|---|---|---|
| 管理工作台批次 | 查询入口/目录版本、规范化筛选条件、当前社团、固定目标对象 ID、每项预览版本、操作参数、确认内容和预览时间 | 执行只遍历冻结目标；新增命中项不加入；逐项重新鉴权、校验状态/版本/容量/资格；只重试原失败项 |
| 异步导出 | 导出类型、申请时授权范围、规范化筛选/选择条件、字段与附件选择、源版本或固定目标集合、申请时间和数据快照边界 | 内容固定为申请时快照；生成失败不改业务；下载时仍重新鉴权；正式删除使相关文件失效 |
| 统计重算 | 统计口径版本、作用域、规范化筛选条件、源水位/快照边界、任务与结果版本 | 失败不发布半成品；旧水位不得覆盖新结果；下钻回到当前有权明细 |

保存筛选快照不等于保存原始 SQL、任意客户端表达式或永久授权；快照必须能由版本化目录解释。目录版本被删除、不能重放或权限范围已经收紧时，任务失败关闭或按明确迁移规则重建，不能以旧快照扩大数据范围。

### 17.10 排序、分页、计数与派生一致性

`DATA-FLT-008`：每个列表查询必须在目录中登记总顺序，并以稳定对象标识补足唯一次级键。名称搜索继续遵守 `DATA-Q-009` 已确认的分层和层内顺序；普通筛选不得临时引入搜索分数、热度、点击量、历史选择次数、人员优先级或个性化信号。

- 游标必须绑定查询入口/版本、规范化筛选摘要、授权作用域版本或安全等价标识、完整排序键及稳定对象标识；筛选、作用域或排序变化后旧游标无效；
- 首版逻辑基线使用稳定游标分页承接可能增长的受保护列表；小型固定目录是否允许页码/偏移由接口和性能证据决定，但数据库物理行顺序永远不是合同；
- 翻页期间源事实变化可以使后续页反映新事实；需要冻结集合的批次/导出必须转入 `DATA-FLT-007` 的快照模型，不能把普通分页游标当作批次清单；
- 总数、分面计数和“零结果”同样可能泄露作用域、成员、申请或状态事实，必须使用与结果行相同的授权、RLS、字段和删除谓词。除上游已确认的统计外，当前不新增通用分面计数或小样本展示规则；
- 缓存键必须包含足以区分查询入口/版本、规范化筛选、排序、分页、访问者类别、普通/联合作用域及字段投影的信息；无法证明安全失效的受保护筛选结果不得缓存。

### 17.11 索引证据、失败关闭与测试输入

`DATA-FLT-009`：筛选索引仍遵守 `DATA-PERF-001` 的查询路径证据门。候选组合索引通常优先排列作用域和高选择性等值条件，再排列状态、关系、范围和稳定排序键，但必须以授权/RLS 后的真实选择率和执行计划证明；不能为每个可见控件、枚举字段或 ORM 条件自动建立单列索引。

可评估方向包括：当前有效关系或待处理状态的部分 B-tree 索引、作用域＋类型/状态＋时间/稳定排序的组合 B-tree、已登记时间区间的范围索引、大型追加审计/历史的时间相关 BRIN，以及 `DATA-Q-009` 已批准对象上的证据化 trigram 索引。每项证据必须覆盖空结果、宽范围、多值、最差组合、深分页/游标继续、总数查询、RLS、500 并发混合负载、写放大、重建和备份恢复。

筛选投影、统计投影、缓存或索引缺失/滞后时不得返回比权威查询更宽的数据。系统只能回源执行仍满足质量目标的权威查询，或返回明确的暂不可用/转异步结果；不得静默去掉筛选、作用域、字段权限或删除谓词。正式删除、授权收紧、社团停用、联合参与失效、对象状态变化和字段权限变化必须进入失效与重建测试。

本节向后续测试至少强制传递：未知键/操作符、空值/空集合、越权 ID、跨社团与跨联合元组、连接池残留、状态/截止边界、时区与夏令时（如适用）、多值组合、选择器保存时失权、批次预览后变化、导出快照、分页漂移、计数泄露、JSONB 任意路径拒绝、投影滞后、缓存失效和正式删除恢复重放。

## 18. 容量、索引、查询路径与未来分区证据

### 18.1 查询路径先于索引

`DATA-PERF-001`：每个候选索引必须关联一个经过授权的查询路径，并记录：调用场景、源事实/SRS、目标逻辑表、作用域条件、相等条件、范围条件、排序/分页、预计/实测基数、选择率、响应目标、RLS 影响、索引方向和验证证据。不能因为 ORM 生成某字段或 PostgreSQL 支持某索引就自动建立。

第一轮索引方向：

- 主外键、当前发布指针和稳定映射使用 B-tree 唯一/引用索引；
- 组合索引通常把社团/联合域和其他相等条件置于范围/排序条件之前，但以实际计划和查询为准；
- 待处理邀请、当前成员关系、可领取任务、未完成删除步骤等高选择性当前子集评估部分索引；
- 时间冲突评估 GiST 范围约束/索引；
- 动态答案只在有证据的包含/键查询使用 GIN，稳定路径使用表达式索引或投影；
- 大型追加历史、任务尝试、审计和运行记录在有时间相关扫描证据时评估 BRIN；
- 覆盖索引只在能证明减少关键 I/O 且写放大可接受时采用。

### 18.2 容量与性能证据

`DATA-PERF-002`：数据设计验证必须使用 `SRS-NFR-001` 的标准规模：单校至少 100 个社团、5 万学生账号、单个普通活动 2,000 份申请、单个联合活动 20 个参与社团，并在 500 并发代表性混合负载下验证普通查询/保存 P95≤2 秒、复杂统计/搜索 P95≤5 秒或转为可追踪异步任务。

证据至少包括 PostgreSQL 版本/配置、数据分布、表/索引规模、查询文本或规范化指纹、执行计划、缓冲区/I/O、锁等待、RLS 条件、样本时延、写放大、任务积压和测试环境。未经这些证据，只能把索引或容量结论标为候选。

### 18.3 未来分区

`DATA-PERF-003`：首轮不因“可能增长”预先把所有表分区。只有当表规模、保留清理、索引维护、查询裁剪或恢复证据表明普通表不能满足目标时，才评估分区。候选优先是按时间追加且生命周期明确的历史、审计、任务尝试、通知投递和运行证据；权威当前行、强跨表引用和高竞争聚合不自动分区。

分区必须证明唯一性、外键、RLS、正式删除、恢复重放和跨分区查询仍正确。只有满足 `DATA-Q-008` 的表级证据门后，分区键、周期和维护方式才进入专项物理设计；归档介质仍由数据保留和存储设计决定，不因分区自动确定。

| A. 单库＋统一应用业务 Schema（已确认） | 最贴合模块化单体、8 类本地事务、单机开源部署、统一迁移/备份/恢复；跨模块外键和作用域约束最直接 | 物理命名空间较大；模块边界主要依赖命名、访问规则、所有权评审和测试，不能依赖 Schema 权限兜底 |
| B. 单库＋按模块分 Schema | 仍保留本地事务；命名和权限边界更显式；模块资产盘点较清楚 | 跨 Schema 外键、迁移顺序、连接权限、搜索路径和共享平台表更复杂；Schema 仍不是业务授权边界 |
| C. 按领域模块分数据库 | 物理故障与访问边界最强，可独立扩容 | 破坏或显著复杂化 8 类原子事务、联合活动、通知/审计、迁移、备份恢复和首版单机部署；需要重开多项 ADR，不建议首版采用 |

每个社团独立数据库不是本轮有效候选，因为 ADR-005 已明确不采用；只有出现新的法规、学校级物理隔离或规模证据时，才可通过替代 ADR 重开。

该问题影响数据库布局、模块访问规则、RLS/连接上下文、迁移、备份恢复和运维；不影响当前 236 个需求事实、40 个用户故事、27 条不变量、29 个状态机、306 条转换、13 条故障规则、54 条 NFR、角色权限、通知行为或代码开工门。

### 20.3 `DATA-Q-002` 关闭记录

2026-07-30 第一轮数据设计评审确认方案 B，并按“统一代理标识类型，但不机械地为每行创建代理键”精确定义：

1. 所有需要独立稳定标识的权威对象、不可变版本、业务命令、通知事实、文件版本、持久任务和删除清单使用 PostgreSQL `uuid`，值采用 UUIDv7。
2. 纯多对多关联可以使用双方稳定 UUID 形成复合标识；只在父对象内部按序存在的历史、尝试和步骤记录可以使用父对象 UUID 与稳定局部序号形成复合标识。
3. 不为没有独立寻址、引用或生命周期需要的记录机械创建代理 UUID；也不以“内部表”为由另建 bigint 代理主键体系。
4. 业务编号、页面序号、学号、Casdoor 外部标识、对象存储键、幂等键、状态版本、转换序号和显式业务时间保持各自语义，不得与 UUID 主键合并。
5. UUIDv7 不能代替唯一业务约束、逐请求授权、RLS、作用域一致外键或显式时间字段；是否公开任何内部标识由后续接口设计决定。
6. 本结论只冻结物理类型与标识规则；`DATA-Q-009` 已进一步确认 PostgreSQL 18 和数据库内置 `uuidv7()` 为统一生成权威。具体列默认值、预取调用和批量方式仍由迁移与实现设计表达，不选择 ORM、迁移框架或具体依赖。

该问题属于表级数据设计，没有改变数据库布局、模块边界、事务边界、部署拓扑或产品行为，因此不新建 ADR。若容量与索引测试证明 UUID 键造成无法通过现有 NFR 的明确瓶颈，重新评审 `DATA-Q-002`；只有影响系统级数据库布局或模块边界时才升级为新 ADR。

### 20.4 `DATA-Q-003` 关闭记录

2026-07-30 第一轮数据设计评审确认方案 C：状态与业务历史采用“模块拥有的强类型追加式历史表＋统一业务命令关联契约”。

1. 29 个状态机的历史正文分别由唯一责任模块拥有；当前状态行、状态历史和专项记录保持强类型聚合外键及普通社团、联合域或平台作用域完整性。
2. 所有历史表必须采用统一公共字段语义，至少包含聚合标识、转换序号、原/目标主状态与正交标志、期望/新对象版本、稳定业务命令 UUID、业务幂等键、操作者或系统来源、原因/证据引用、发生时间及审计/通知引用。
3. 同一数据库事务内由一个业务命令产生的各模块历史、通知事实、审计和任务意图共享同一业务命令 UUID，以验证八类事务的完整提交；一个异步重试或后续处理事务使用自己的命令 UUID，并保存强类型触发来源，不能冒充原事务的一部分。
4. 不建立承载全部状态正文的统一历史信封或中央事件表；不采用 `object_type＋object_id＋JSONB`、EAV 或无法建立真实外键的多态弱引用。
5. 全局历史、个人中心、管理工作台、恢复查询和统计通过受控联合视图或可重建派生读模型获取；这些入口不能修改领域历史或成为当前状态权威。
6. 状态历史、业务审计、通知事实和脱敏运行证据继续分离。统一命令 UUID只提供关联，不把四类数据合并。
7. 当前状态行仍是当前状态权威，历史用于追踪、恢复和验证；首版不采用事件溯源，也不要求通过重放全部历史取得当前状态。

该问题属于表级数据组织，没有改变模块责任、状态机、事务边界或部署拓扑，因此不新建 ADR。若未来改为统一事件存储、事件溯源或跨数据库分布式历史，应建立新 ADR 并重评 ADR-001、ADR-003、ADR-005 与 ADR-014。

### 20.5 `DATA-Q-004` 关闭记录

2026-07-30 第一轮数据设计评审确认方案 C：持久任务采用“通用技术执行信封/尝试记录＋模块强类型业务意图与结果”。

1. 通用任务执行信封拥有任务 UUID、任务类型与版本、来源模块、作用域类别、业务命令 UUID、调度/截止、优先级方向、技术状态、租约、当前尝试号、幂等引用和最小执行参数；它不拥有业务目标或业务结论。
2. 通用尝试记录按任务 UUID＋尝试序号保存领取者、开始/结束时间、结果分类、脱敏错误、外部请求号、可信读回摘要和下次可执行时间；尝试记录不能改变源业务对象。
3. Casdoor 关系目标与原/执行前/写后关系快照、文件版本与检查策略、通知事实与收件人、导出范围与权限快照、删除清单与步骤、到期对象与预期版本等保存在对应模块的强类型表，通过真实外键和作用域约束关联任务。
4. 需要领域意图的任务必须与业务事实、强类型意图和必要通知/审计按对应事务边界原子创建；只有信封没有意图、只有意图没有必要任务或载荷与意图版本不一致都属于完整性失败。
5. 纯技术派生重建/维护任务可以不关联领域意图，但任务类型必须在版本化允许目录中，且不得写入权威业务状态、授权或业务结论。
6. JSONB 只允许承载最小、版本化、运行时校验的执行参数或脱敏技术结果，不得复制完整业务正文、秘密、外部原始响应或用作未建模对象仓库。
7. 工作器领取后必须按 `DATA-JOB-002` 重检作用域、源状态/版本、安全开关、删除状态和既有幂等结果；任务技术成功不能代替 Casdoor 写后可信回读、文件检查结果、通知渠道结果或其他领域最终事实。
8. 通用执行模型统一租约、领取、重试和积压统计；模块表保持业务所有权、专项保留/RLS/删除和强类型查询。二者共同组成完整任务详情，但通用信封不是领域事实的第二权威副本。

该问题属于 ADR-004 已接受边界内的表级组织，不新建 ADR。若未来引入独立消息队列作为权威任务源、改变至少一次执行边界或把任务拆入独立数据库，应建立补充或替代 ADR。

### 20.6 `DATA-Q-005` 关闭记录

2026-07-30 第一轮数据设计评审确认方案 C：联合协作域采用“动态参与关系＋专用作用域隔离型 RLS＋服务端完整授权”。

1. 联合活动与参与社团保持一对多强类型关系，参与数量不进入固定列、JSONB 名单或 Policy 常量；`(joint_activity_id, club_id)` 唯一，当前参与状态、关系版本、有效/受阻区间和历史分别保存。

5. 新增、退出、停用或失效参与社团只改变当前关系和版本，不要求修改表结构或 Policy。新请求使用新关系重新授权；旧版本写入和后台任务重检后失败关闭或按既有规则收口。

8. 跨多个联合活动、多个普通社团和个人中心/工作台的授权集合与查询方式已由 `DATA-Q-006` 确认为冻结集合只读模式；本问题继续只负责单目标联合域及参与社团私有域的隔离方向。

### 20.7 `DATA-Q-006` 关闭记录

2026-07-30 第一轮数据设计评审确认方案 C：RLS 连接上下文采用“单目标操作＋冻结集合只读”的双模式。

1. 单目标模式用于所有业务命令、状态转换、详情读取、文件访问、高风险操作和后台任务单项执行，只允许一个普通社团、一个联合活动及必要参与社团私有域，或一个明确平台/主体目标。
2. 集合只读模式仅用于登记过的个人中心、管理工作台、跨社团只读待办和受控统计/目录查询；数据库身份、事务属性和应用入口必须禁止在该模式执行写入。
3. 普通社团集合由服务端按当前操作冻结已授权 `club_id`；联合共享范围冻结 `joint_activity_id`，联合私有范围冻结完整 `(joint_activity_id, participant_club_id)` 元组，不能以独立数组产生未授权笛卡尔组合。

5. 批次任务保存冻结目标项并逐项建立单目标上下文；后台任务、派生重建身份和超级管理员产品角色都不获得通用集合写入或 `BYPASSRLS`。
6. 上下文必须与稳定主体、请求/事务追踪号、模式、操作类别和必要授权版本绑定，并在事务结束时清理；缺失、格式非法、模式不匹配、集合超限或连接残留时失败关闭。
7. 普通视图位于基础表 RLS 之上，只负责连接、投影、分类和聚合，不得以执行者/所有者权限绕过基础表隔离；具体 PostgreSQL 视图执行语义须通过 `DATA-Q-009` 保留的 PostgreSQL 18 部署与安全证据门禁验证。
8. 物化视图和持久派生表显式保存主体/社团/联合域、源对象、源版本或水位，读取时重新授权；刷新时的高权限不能传递给普通查询，派生结果不能成为授权或业务状态权威。
9. 冻结集合的 PostgreSQL 载体、最大规模、索引和查询拆分阈值不由 ORM 默认决定，必须以缺失/污染负向测试、查询计划和 500 并发证据关闭物理设计。

该问题位于 ADR-005 的逐请求授权、数据库作用域约束和无普通绕过边界内，不新建 ADR。若未来允许多作用域写入、持久化长期授权集合替代当前关系，或用高权限视图绕过基础表 RLS，应建立补充或替代 ADR。

### 20.8 `DATA-Q-007` 关闭记录

2026-07-30 第一轮数据设计评审确认方案 C：动态表单采用“规范化字段对象＋稳定重复项＋强类型对象/文件引用＋证据驱动可重建投影”。

该问题属于 ADR-006 已接受的关系骨架＋JSONB 边界内的表级设计，不新建 ADR。若未来扩张为低代码工作流平台、允许用户自定义可执行逻辑或把动态字段提升为业务状态权威，应新增产品事实并建立补充或替代 ADR。

### 20.9 `DATA-Q-008` 关闭记录

2026-07-30 第一轮数据设计评审确认方案 C：当前物理基线不预建分区，所有逻辑表默认采用普通表；表设计必须保持可迁移，只有单表证据证明普通表方案不足并通过专项评审后，才允许以受控迁移启用 PostgreSQL 分区。当前没有已批准的分区表、分区键或分区周期。

1. “保持可迁移”要求大型追加事实具有明确且稳定的业务时间、发生时间和创建时间语义，稳定对象标识不得由物理分区名称或行位置构成；候选分区时间不能替代业务时间、状态版本或幂等顺序。
2. 应用、后台任务、视图和派生重建逻辑只引用逻辑表与稳定数据契约，不直接访问、拼接或授权具体分区子表；分区不能成为社团、联合域或平台权限边界。
3. 启用分区前必须形成表级证据包，至少覆盖保留策略下的容量与增长预测、主要查询路径和查询计划、写入与维护压力、清理模式、备份恢复时间、迁移窗口，以及唯一性、外键、RLS 和正式删除的正确性证明。
4. 不设置适用于所有表的任意行数阈值。表大小本身不是充分理由；只有普通表索引、查询、维护、清理或恢复已无法在确认的质量目标内工作，且分区能够针对该瓶颈提供可验证收益时，才进入物理方案评审。
5. 若上线前容量模型或压测已经提供充分证据，可以在首次正式迁移冻结前为该表启用分区；若证据来自上线后运行观测，应在数据仍可控且可安全回退时迁移，不能等到严重退化后抢修。
6. 每次实际分区迁移必须明确源表到目标表映射、数据完整性校验、并发写处理、切换窗口、幂等重试、失败回退、索引与约束重建、RLS 负向测试以及备份恢复演练；不得宣称应用代码必然零修改。
7. 分区方式、分区键、周期、预建/清理策略和 PostgreSQL 版本能力属于届时的表级物理设计；不得由 ORM、迁移工具或 PostgreSQL 默认行为提前决定。若依赖特定版本或扩展能力，必须同时满足 `DATA-Q-009` 已冻结合同及其保留的部署证据门禁。
8. 分区不会改变 236 个需求事实、29 个状态机、模块所有权、UUIDv7、8 类事务语义、数据保留规则或 RLS 安全语义；它只改变取得证据后某张逻辑表的物理组织、约束实现、迁移与运维方式。

该问题没有改变 ADR-006 的 PostgreSQL 主数据库选择、ADR-014 的单数据库和统一应用业务 Schema，也没有改变模块或故障域边界，因此不新建 ADR。若未来分区方案演变为按租户物理隔离、跨数据库分片、独立故障域或模块独立生命周期，应建立补充或替代 ADR。

### 20.10 `DATA-Q-009` 关闭记录

1. PostgreSQL 16、17 不属于首版官方兼容矩阵；社区或部署方自行适配低版本不构成 RanaMinder 对迁移、RLS、搜索、恢复或扩展的兼容承诺。

9. 扩展采用方案 B：只有 PostgreSQL 官方随附扩展可以进入首版候选，且每个扩展必须具备明确需求来源、不可由核心能力合理替代的证据、PostgreSQL 18 兼容验证、对象与权限边界、迁移和卸载影响、备份恢复复现、升级回归及缺失时失败方式。扩展不能成为业务权威、授权绕过或未经编号的数据行为来源。

13. 普通应用连接和后台任务连接不得拥有创建、更新、删除扩展或改写扩展对象的权限；扩展安装只能由受控部署/迁移身份完成。扩展对象的具体 Schema、版本固定和验证命令仍由后续迁移与部署设计确定，不依赖默认 `search_path`。
14. 数据库编码确认为 UTF-8，默认排序规则采用 PostgreSQL 18 内置、确定性的 `pg_unicode_fast`。它负责可复现的权威文本比较和码点顺序，不承诺中文拼音、笔画或其他自然语言排序。
15. 稳定标识、外部映射、状态码、类型码、幂等键、作用域键、唯一约束、外键辅助文本和授权条件不得使用 ICU 非确定性相等，也不得把大小写/重音折叠后的“看似相同”作为对象身份；需要业务唯一性的名称必须另有规范化规则和显式作用域约束，不能只依赖默认排序。
16. 只有个人中心、公开目录、管理工作台等不改变业务结果的派生展示列表，才能在需求明确且样本验收通过后显式使用确定性的 ICU 中文排序；对应查询必须提供稳定次级排序键，避免同序值分页漂移。
17. ICU 提供者、Locale 和版本属于部署能力矩阵。ICU 不可用、版本不一致或升级未完成索引重建验证时，不使用本地化排序路径，回到 `pg_unicode_fast` 稳定顺序；不得静默改变唯一性、授权或权威索引语义。
18. 排序规则不承担中文分词、名称派生键、同义词、模糊匹配、搜索权重或权限过滤；这些继续由名称搜索子项和派生搜索模型决定。
19. 名称搜索能力确认采用简化通则：人员姓名支持任意连续汉字子串（含单字），学号或账号精确匹配；社团展示名称、活动名称、部门名称、职位名称和 Casdoor Group 名称支持中文任意连续子串。
20. 首版所有对象均不提供拼音或首字母搜索，不建立拼音生成器、拼音字典、全拼/拼音片段/首字母派生字段，也不承担相应回填和版本升级。未来重新引入必须先回到产品事实和 `DATA-Q-009` 评审。
21. 人员选择器不得提供姓名错别字候选；社团、活动、部门、职位和 Casdoor Group 等非人员名称可以提供受控错别字近似候选。人员与非人员策略不得因复用同一搜索组件或数据库函数而被静默统一。
22. Casdoor Group 原始名称可直接检索，稳定 Group 标识只能精确匹配。搜索命中不得修改 Group 定义、替代层级/唯一映射检查或成为当前 Group 关系权威。
23. 受保护选择器必须先按当前用户、操作、社团/联合/任务作用域和候选资格限制返回集合；最终命令或动态表单引用必须提交稳定对象标识并重新校验。同名或近似命中不得自动绑定对象。
24. 已确认名称搜索不扩张为动态答案正文、评价、附件内容、通知正文、审计差异或其他业务正文全文检索，也不新增个性化推荐、自动匹配或个性化排名。
25. 必要的名称搜索派生采用 `DATA-DER-003` 的可重建模型；派生字段和索引不得参与权威名称相等、业务唯一性、外键、RLS、授权、状态机或事务成功判断。能够直接安全查询权威名称字段时不强制复制一份搜索投影。
26. `pg_trgm` 与 `word_similarity()` 已获采用，首版近似阈值显式固定为 `0.6`，三层内部排序、搜索文本规范化语义、PostgreSQL 单一执行权威和物理载体按表证据门控策略已冻结；具体表级载体/索引仍须在迁移和测试阶段用代表性样本和查询计划逐项证明，不能由 NestJS、ORM 或 PostgreSQL 排序规则默认行为决定。
27. 非人员名称结果采用方案 A 的固定分层：稳定标识或名称精确命中为第一层，中文连续子串命中为第二层，`pg_trgm` 错别字近似候选为第三层；第三层的相似度分数不得使任何近似候选越过第一或第二层。查询和读模型必须携带显式匹配层级；第三层使用第 35 项的确定性顺序，第一和第二层使用第 36 项的领域排序与稳定兜底，不得临时引入搜索分数。三层不得直接混入一个不透明总分。
28. 短输入采用方案 A：先按第 32 项生成最终规范化查询值，再按其中的汉字、字母和数字合计有效字符数；不足 3 个有效字符时不得执行 `pg_trgm` 近似匹配，只运行稳定标识/名称精确和中文连续子串路径，达到 3 个有效字符后才允许追加第三层。该门槛不限制短名称的直接命中，也不得通过标点、空白或其他被排除字符绕过。
29. 第三层相似度采用方案 A：统一使用 `word_similarity()`，以规范化后的用户输入作为查询片段、权威名称或其经批准的规范化搜索值作为被搜索文本，寻找名称中最相似的连续范围；不得交换参数方向，不得改用完整字符串 `similarity()`，也不得组合两者形成未经评审的总分。该函数只负责第三层候选与层内分数，不得参与第一、第二层判定、人员选择器或业务授权。
30. 首版近似阈值采用方案 B，数值固定为 `0.6`。这是 RanaMinder 的显式搜索合同，即使该值与 PostgreSQL 当前 `pg_trgm.word_similarity_threshold` 默认值相同，也不得仅依赖连接或会话中的隐式默认；HTTP 应用、后台任务、修复和重建路径必须得到同一判定。具体实现可在后续迁移与查询设计中选择显式数值比较，或选择能证明连接池隔离并在事务结束后可靠清理的事务局部设置，但不得把可跨请求残留的会话级修改作为普通业务路径。未来调整数值必须重新执行版本化数据设计评审和代表性样本回归，不作为运行时管理员任意调参项。
31. 首版索引策略采用方案 A：不为社团、活动、部门、职位和 Casdoor Group 等全部非人员名称预设统一 GiST 或 GIN，也不把 trigram 索引作为 `pg_trgm` 功能正确性的前置条件。具体目标表、权威名称列或可重建规范化投影必须分别保存证据包，至少覆盖代表性数据量与名称分布、实际精确/子串/第三层查询形态、授权和作用域过滤后的查询计划、延迟与回表、索引体积和写维护成本、创建/重建时间及备份恢复影响；据此可以选择 GiST、GIN 或暂不建立 trigram 索引。任何后续新增或变更仍是受控迁移，不能由 ORM 自动同步或生产环境临时建索引代替评审。
32. 搜索文本规范化采用方案 A。权威显示名称保持原始值；查询输入和被搜索名称使用同一版本化管线，顺序固定为 NFC、按 `pg_unicode_fast` 语义执行 Unicode 大小写折叠、再次 NFC、去除首尾 Unicode 空白、把连续内部 Unicode 空白压缩为一个 U+0020 空格。再次 NFC 是必要步骤，因为大小写折叠可能不再保持原规范化形式。首版保留标点、简繁体和全角/半角差异，不执行 NFKC、同义词、异体字、拼音或其他兼容折叠；例如拉丁字母大小写和多余连续空白可以得到同一搜索值，全角拉丁字母与半角拉丁字母仍不同。最终规范化查询值同时用于精确层、子串层、第三层和有效字符门槛；算法及依赖的 PostgreSQL/Unicode 能力必须携带投影格式版本，规则改变时先重建派生值和索引并执行样本回归，不改写权威显示名称或业务唯一性。
33. 规范化执行权威采用方案 A：PostgreSQL 中受控迁移创建的显式版本化函数是唯一正式实现。HTTP 应用、后台任务、批量导入、修复、对账和派生重建只传入原始文本并调用同一数据库能力；浏览器、客户端、NestJS 或其他运行时计算的规范化值最多用于非权威预览，数据库不得直接信任、持久化或据其判定匹配层级。函数必须显式绑定已确认的 UTF-8、`pg_unicode_fast` 和规范化格式版本，不依赖连接 `search_path`、会话 Locale 或其他可漂移设置；普通应用和任务身份无权替换函数。是否以生成列、普通派生列、表达式索引或查询时计算承载，继续按表级查询、函数易变性、写入和重建证据决定；在没有证明全部依赖真正不可变前，不得为满足生成列或索引要求错误声明 `IMMUTABLE`。PostgreSQL/Unicode 能力升级先以黄金样本比较新旧输出；发生差异时建立新格式版本并受控重建，不就地静默改变既有派生值。
34. 规范化物理载体采用方案 A：默认不为所有可搜索对象统一持久化规范化列或建立集中搜索表。每个目标表先以查询时调用权威函数为正确性基线，再根据数据量、查询频率、函数成本、授权/RLS、索引计划、写放大、重建和恢复证据，独立选择继续查询时计算、建立表达式索引、使用存储生成列、保存普通可重建派生列或接入集中搜索投影；小表可以不持久化、不建 trigram 索引，同一首版允许不同表采用不同载体。普通视图只组织查询且不保存结果；集中投影只有存在真实跨权威表查询或独立重建收益时才允许建立，并必须携带对象类型、稳定对象 ID、作用域、源版本、格式版本和水位。任何持久派生值均由 PostgreSQL 权威函数产生，不能反向成为名称、唯一性或授权权威。
35. 第三层内部排序采用方案 A：先按同一版本化规范化值计算的 `word_similarity()` 分数降序，再按规范化名称的 `pg_unicode_fast` 稳定顺序升序，最后按稳定对象 UUID 升序；分页游标必须携带足以复现该顺序的层级、分数和次级键。活动状态、截止时间等既有条件在候选形成前作为领域筛选执行，不混入第三层分数；点击量、热度、历史选择次数、个性化信号和其他未经确认的业务权重均不得加入。该顺序只适用于第三层，不改变第一/第二层，也不允许第三层候选越过任何直接命中。
36. 第一、第二层内部排序采用方案 A：先完成授权、作用域和已有领域筛选，再沿用对应列表已经明确的领域内部排序；若该入口没有明确领域排序，则按规范化名称的 `pg_unicode_fast` 稳定顺序升序、稳定对象 UUID 升序兜底。稳定 ID 精确和名称精确处于同一第一层，不再细分优先级；第二层不按子串出现位置、名称长度、热度或其他新相关性信号重排。分页必须补足稳定 UUID 次级键，数据库未指定顺序、物理行顺序或 ORM 默认排序都不得成为合同。

2026-07-30 第一轮数据设计评审最终确认方案 A：上述逻辑设计整体关闭，具体表级规范化载体、GiST/GIN/无 trigram 索引选择，以及 PostgreSQL 18、`pg_trgm`、ICU 的部署兼容、迁移、查询计划、备份恢复和升级回归继续作为强制证据门禁。关闭设计问题不表示这些物理选择已经实施或验证；证据未通过时不得写迁移或上线，不能静默更换数据库版本、扩展、阈值、规范化算法、排序合同或搜索范围。

上述子项不改变 ADR-006 的 PostgreSQL 主数据库方向，不单独新建 ADR。拼音搜索和正文全文搜索都不是当前首版产品能力，未来新增时必须先回到产品事实并重开 `DATA-Q-009`；引入候选外扩展、外部搜索、改变权威排序或让应用侧成为规范化权威也必须重开。`btree_gist` 已由 `DATA-Q-010` 批准并回填；`DATA-Q-014` 已确认首版不安装 `pgcrypto`。

### 20.11 `DATA-Q-010` 关闭记录

2026-07-30 第一轮数据设计评审已确认总体方案 A：普通事务显式采用 `READ COMMITTED`，优先使用数据库约束、期望对象版本和固定顺序的定向行锁；只有无法由这些手段可靠表达的剩余事务谓词，才允许对登记过的完整业务命令使用 `SERIALIZABLE`。`REPEATABLE READ` 不作为独立基线，也不把所有写事务统一提升到 `SERIALIZABLE`。

### 20.13 `DATA-Q-012` 关闭记录

2026-07-30 第一轮数据设计评审由需求方确认接受“三个私有存储区”：每个相互隔离的 RanaMinder 部署环境分别使用待检查隔离区、权威原件区和临时派生区三个专用 Bucket。同一环境内所有社团及联合活动共享这三个存储区，不按社团、用户、业务模块或文件格式拆分；开发、测试/验收和生产不得共享 Bucket、凭据或备份。该确认只决定安全阶段的存储隔离，不新增人工内容审核，也不改变既有自动技术安全检查、附件权限或正式删除产品行为。

本轮在该确认及 ADR-008 边界内完成以下数据设计推导：

1. 待检查隔离区仅保存未完成、待检查、检查中、检查失败或待清理字节；权威原件区只接收检查通过并完成晋升核验的原件；临时派生区保存安全预览、水印、转码和临时导出。
2. 权威原件区纳入附件备份和恢复验收；隔离区不成为正式恢复源，临时派生区恢复后重建、重新生成或按到期状态清理。
3. Bucket 是同一 S3 兼容服务内的逻辑容器，不要求独立服务器或重复保存三份正式文件；官方单机和拆分部署保持同一逻辑边界。
4. 对象键由服务端密码学安全随机源生成不少于 128 位有效熵的定位符，使用版本化技术前缀，不包含数据库 UUIDv7、个人/社团信息、原始文件名、扩展名、权限或内容摘要，客户端不得决定或复用。
5. 所有对象键严格只写一次。单段上传、完成分段上传和跨 Bucket 晋升必须使用经目标实现验证的 create-only/目标不存在条件或等价机制；写前查询和 SDK 默认覆盖行为不构成并发保证。
6. 自动技术安全检查通过后，任务固定已检查的源对象状态，以新键晋升并核对目标大小和可信 SHA-256；只有 PostgreSQL 收口权威原件定位和文件版本就绪后才允许正式绑定。上传地址重放不得改变已检查或已晋升字节。
7. PostgreSQL 应用级不可变文件版本是唯一业务版本。三个在线 Bucket 禁用原生 Versioning 与 Object Lock；部署预检验证配置和历史版本不存在，版本控制“暂停”不等于清除旧版本。
8. 独立备份仓库可以使用版本、快照或不可变保护，但不能成为在线授权来源；任何恢复必须先重放正式删除清单并完成数据库—对象存储核验。
9. SHA-256 是可信全文件内容摘要；ETag、分段 ETag、对象键和供应商 Version ID 只作存储并发或诊断证据，不替代业务版本、授权、摘要或去重键。
10. PostgreSQL 权威任务决定上传/孤儿/派生物到期及正式删除并在执行前重验引用；对象存储 Lifecycle 仅作未完成分段上传和超长孤儿兜底。正式删除必须覆盖所有在线对象定位记录并逐项回读核验。
11. 首版不启用跨用户/跨作用域内容去重；相同摘要不合并业务引用和删除生命周期。
12. 具体 Bucket 名称、短链时长、上传大小、分段阈值、生命周期安全缓冲、对象存储静态加密产品/参数和供应商产品不由本问题决定，分别进入部署、接口、安全、`DATA-Q-011` 和兼容能力验证；应用托管秘密及其密钥引用遵守 `DATA-Q-014`。

候选方案审计结论为：单 Bucket＋前缀虽部署项较少，但把未检查、权威和临时对象置于共同凭据、备份与清理故障面；两 Bucket 仍混合权威原件和临时派生物；四个以上或按社团拆 Bucket 增加联合活动、备份、迁移和删除复杂度；内容寻址去重破坏独立引用生命周期；在线原生 Versioning 会引入非当前版本和删除标记的全版本清理责任。三个按信任/生命周期拆分的 Bucket 在当前单校规模、开源单机和拆分部署间具有最小充分复杂度，因此采用。

该决定细化 ADR-008 已接受的 S3 兼容对象存储、隔离检查、应用级文件版本、正式删除和联合恢复边界，没有改变供应商、部署故障域或产品能力，因此不新建 ADR。若目标实现无法证明 create-only、源状态固定、复制/校验、最小权限、Bucket 状态、删除回读、备份恢复和 RPO/RTO，须重开本问题；引入在线原生版本、对象锁、法定留置/WORM、跨环境共享或按租户物理 Bucket，且改变 ADR-008 权威、删除或恢复边界时建立补充/替代 ADR。

### 20.15 `DATA-Q-014` 关闭记录

2026-07-30，需求方确认采用“分层保护＋服务端应用层受控加密＋数据库外版本化密钥环＋强类型秘密引用”。本结论承接 `GOV-001`、`GOV-009`、`NTF-005`、`CFG-005`、`NFR-002`、ADR-010 和既有邮件故障恢复规则，不新增产品行为、SRS 编号或 `PRD-OPT-*`，也不改变宿主机管理员属于部署信任边界及邮件故障不回滚普通业务的结论。需求方后续的开工豁免只授权开发／测试环境实现，不开放生产迁移或真实数据。

确认后的数据合同如下：

1. 数据保护按类别分层：数据库、Casdoor、对象存储等部署凭据及应用秘密加密根密钥从 ADR-010 的数据库外受控配置入口或未来秘密提供器加载，数据库只保存引用、公开版本和状态；平台/社团管理员在系统内配置且运行时必须可还原使用的邮件密码、API Token 等应用托管秘密进入独立受控秘密记录；验证码、一次性令牌等只需验证、不需还原的值只保存不可逆摘要、用途、到期和尝试证据；普通内部/个人业务数据继续使用强类型列或受控 JSONB、逐请求授权、RLS、TLS、存储及备份保护，默认不做通用应用层列加密。
2. 只有数据目录和实现级威胁模型证明某个个人业务字段必须列加密，且同时定义查询、唯一性、外键、纠错、正式删除、备份恢复和密钥丢失行为时，才允许建立例外加密字段；例外不得扩张为未评审的“全部敏感字段加密”，也不得用密文规避既有强类型关系或授权。
3. 数据库托管的可恢复秘密统一使用服务端应用层 `AES-256-GCM`：密钥为密码学安全随机生成的 256 位值；每次加密生成独立随机 96 位 nonce，认证标签固定为 128 位；同一 `key_version` 下 nonce 不得重复，保存前必须拒绝已经占用的“密钥版本＋nonce”组合。浏览器、客户端、数据库函数、ORM hook 和普通业务模块不得决定算法、nonce、标签或密钥。
4. 认证附加数据使用版本化、长度安全且确定性的编码，至少绑定 `format_version`、`secret_id`、`secret_type`、`owner_scope_type`、`owner_scope_id` 和逻辑 `credential_version`。任一密文被替换到其他记录、秘密类型、平台/社团作用域或凭据版本时必须认证失败；AAD 不保存秘密正文。
5. 受控秘密逻辑记录至少表达 UUIDv7 `secret_id`、秘密类型、平台/社团作用域、逻辑凭据版本、密文格式版本、算法、公开 `key_version`、nonce、密文、认证标签、材料生命周期、测试结论、创建/测试/启用/替换/退役/销毁时间及替换关系。普通配置版本、通知、审计、任务载荷、错误和导出只保存受控 `secret_ref` 或必要的非秘密状态，不复制密文、秘密前后缀、可关联指纹或可还原派生值。
6. 秘密材料生命周期、测试结论和邮件渠道状态是三组正交事实：材料使用 `candidate → current → retired → destroyed`，测试使用 `untested / passed / failed / unknown`，渠道使用 `disabled / enabled / paused`。密钥提供器暂时不可用、认证标签失败或恢复门未通过属于运行可用性/恢复状态，不能把材料自动改写为已销毁，也不能遍历其他键或回退明文。
7. 新录入秘密先加密为 `candidate`，不影响既有 `current`。测试必须绑定完整发信配置版本与准确 `secret_id`；主机、端口、用户名、发件地址、秘密或其他参与测试的配置变化后，旧测试结论失效。超时和结果不确定不得记为通过；允许对同一候选版本幂等重试，失败只保存脱敏分类。
8. 只有与当前候选配置完全匹配的 `passed` 结果可以启用。启用事务必须原子切换配置当前指针、把候选材料改为 `current`、把原材料改为 `retired` 并保存必要审计/通知事实；每个“作用域＋秘密类型”最多一个 `current`。并发启用只有一个成功，失败继续完整使用旧配置，不得形成混合版本。
9. 已退役秘密不得通过普通配置回滚重新成为当前值；恢复能力只能重新填写或建立新的轮换候选。新投递尝试在执行时解析当前有效凭据；已经开始的旧尝试可按原尝试收口，但后续重试不得重新读取已退役材料。尝试记录可以保存实际使用的非明文秘密版本引用用于内部追踪，该引用不得进入普通页面或导出。
10. 人工停用只改变渠道状态，不销毁当前材料；明确退信、密钥失效或连续失败达到既有规则时只把对应渠道置为 `paused`，不自动借用其他社团账号或切换旧凭据。邮件暂停不改变业务结果和通知事实；重新启用必须使用当前秘密重新测试，或完成新的凭据轮换。
11. `retired` 后立即禁止新使用；确认没有仍需读取该材料的进行中尝试后，可以清除在线密文并保留不含秘密的最小版本、状态、责任和审计元数据。`destroyed` 只表示当前在线密文已清除，不冒充历史 WAL、有效备份或外部邮件服务凭据已经同步销毁；外部旧密码/Token 的撤销必须由相应外部系统可信确认，未知时不得写成成功。
12. 正式备份恢复采用需求方确认的恢复方案 A：所有数据库托管的应用秘密进入恢复暂停门，即使旧密文能够解密或自动测试成功，也不得自动启用。平台或对应社团的有权管理员必须重新录入或轮换凭据并测试成功，相关邮件/外部渠道才能恢复；平台邮件可优先恢复，社团邮件暂停不阻塞站内信与普通业务。该规则防止恢复点之后已轮换的旧凭据因旧备份复活。
13. 应用秘密密钥环位于数据库外：同一加密用途恰好一个 `encrypt_decrypt` 当前键，可以有多个 `decrypt_only` 旧键；解密严格按记录中的 `key_version` 精确取键，不允许逐键试解。应用秘密加密键不得复用于备份加密、TLS、签名、令牌 HMAC、数据库密码或其他用途；密钥材料不得由人工口令、学校名称或普通配置文本直接充当。
14. 正式启动必须校验当前加密键唯一、算法和长度正确、版本不重复、无空值/示例占位符、数据库仍引用的版本可定位及 ADR-010 的只读/权限边界；错误只允许显示缺失或非法的公开版本标识。普通业务模块只通过统一秘密服务使用受控 `secret_ref`，不得读取项目目录、直接解析密钥环或提供通用解密接口。
15. 计划根密钥轮换先引入新 `encrypt_decrypt` 键并把原键降为 `decrypt_only`，从此新密文只使用新键；后台任务按准确旧版本解密、使用新键重新加密、在受控内存中复核内容一致并创建新的加密修订，再原子切换引用。重新加密只改变技术加密修订，不改变逻辑邮件凭据、发信配置或渠道状态，因此不要求发送新的外部测试邮件；失败项继续引用仍可解密的旧修订，任务必须幂等且不得半切换。
16. 在线重新加密完成后必须扫描并证明所有仍保留在线密文的秘密记录不再引用旧键。只要任一在线密文、有效保留期内备份或经专项批准的例外加密字段仍依赖旧键，旧键就保持 `decrypt_only`；只有相关依赖消除、备份到期或被安全替代，并且恢复演练证明不再依赖后，才能退役并销毁。
17. 密钥环必须具有与数据库备份分离保护、且不只位于唯一在线主机的恢复材料。恢复材料须加密、限制访问、记录版本目录并做可读性/恢复演练；本问题不强制 Vault、HSM、云 KMS、双人托管或具体产品。备份加密键与应用秘密加密键继续分离，取得数据库备份解密能力不得自动获得字段秘密解密能力。
18. 密钥暂时不可用时，对应秘密能力失败关闭且不改密文；密钥永久丢失但无泄漏证据时，应用托管外部凭据按恢复方案 A 重新录入，经批准的例外加密字段形成明确恢复缺口；怀疑或确认根密钥泄漏时，所有受其保护的密文按可能泄露处理，暂停相关渠道、生成新键、处置例外字段并在外部系统撤销或轮换邮件密码/API Token。单纯重新加密数据库密文不得宣称泄漏处置完成。
19. 首版明确不安装 `pgcrypto`，不采用每秘密 DEK 的信封加密、确定性/可搜索秘密密文、通用解密 API、业务模块各自加密或自动回退明文。未来接入 KMS/HSM/Vault 时，应优先扩展统一秘密提供器并保持 `secret_ref` 和版本化密文合同；若改变 ADR-010 的官方单文件部署、ADR-012 的故障域或应用信任边界，须建立补充或替代 ADR。
20. 实施前证据门至少覆盖：随机数与“密钥版本＋nonce”不重复、标签篡改/AAD 跨作用域替换失败、无权模块和数据库读取只能得到密文、页面/通知/审计/日志/任务/导出无秘密、候选测试与并发启用、旧秘密不可回滚、渠道故障不改业务、恢复方案 A、根密钥轮换中断与幂等续作、含旧键备份恢复、密钥丢失/泄漏演练、配置占位符/权限/只读校验及开源发布秘密扫描。证据未通过时不得写迁移、上线真实秘密或宣称恢复可用。

`DATA-Q-014` 位于 ADR-010 已接受的数据库外配置入口、ADR-012 的恢复优先拓扑和现有配置/通知故障边界内，没有改变数据库布局、模块责任、产品权限或部署故障域，因此不新建 ADR。未来法规要求普遍个人字段列加密、学校要求 KMS/HSM/集中密钥审计、算法/库失效、密钥恢复无法满足 RPO/RTO，或多节点秘密提供器改变既有部署信任边界时，重开本问题；达到架构影响时补充或替代相应 ADR。
