权威顺序为：

## 3. `OPS-*` 编号与非目标

`OPS-*` 是下游部署运维编号，不是需求事实、SRS、`PRD-OPT-*`、ADR、`DATA-*`、`IFC-*`、`CAS-*`、`SEC-*` 或 `TST-*` 编号。它不得独立创建用户行为、权限、期限、性能数值或外部能力。

| 编号族 | 范围 |
|---|---|
| `OPS-TOPO-*` | 运行单元、拓扑和扩容边界 |
| `OPS-ID-*` | 普通、后台、迁移、维护和恢复身份 |
| `OPS-CFG-*` | 外置配置、秘密、传输与浏览器暴露边界 |
| `OPS-DB-*` | PostgreSQL、统一 Schema、RLS、连接上下文和扩展证据 |
| `OPS-JOB-*` | 权威任务、租约、幂等、至少一次执行和恢复 |
| `OPS-FIL-*` | 私有 Bucket、检查、预览、访问、删除和恢复 |
| `OPS-DEP-*` | 部署、启动、依赖就绪和能力阻断 |
| `OPS-UPG-*` | 升级、迁移、维护和回滚 |
| `OPS-LOG-*` | 日志、审计、追踪和内置状态 |
| `OPS-BKP-*`、`OPS-RCV-*` | 备份合同、恢复步骤、恢复门和批准 |
| `OPS-REL-*` | 开源发布与敏感信息检查 |
| `OPS-VER-*` | 部署、升级和恢复的实际验证入口 |
| `OPS-Q-*` | 尚待确认的部署级选择 |

本文不选择具体云厂商、对象存储产品、文件扫描器、密钥提供器、认证库、会话库、Casdoor SDK、ORM、迁移框架、限流组件、反向代理、证书产品、Cookie/CORS/CSP/响应头方案、观测平台或依赖版本，也不提供 SQL、迁移、配置、调用或命令样例。

## 4. 应用形态、运行单元与支持拓扑

### 4.1 模块化单体边界

`OPS-TOPO-001`：首版是领域驱动的模块化单体，不拆成微服务。12 个领域模块和 3 个平台支撑模块保持既有唯一责任；部署拆分不能改变模块所有权、状态机、事务边界、授权或数据权威。

`OPS-TOPO-002`：前端采用 Vue 3＋TypeScript，后端采用 NestJS＋TypeScript。框架默认认证、授权、校验、错误、会话、日志、缓存或重试行为都不是 RanaMinder 规则；具体版本和依赖在发布准备中经兼容与安全证据确定。

`OPS-TOPO-003`：HTTP 应用与后台任务使用独立启动入口，可以独立部署和扩容，但使用同一业务规则、模块边界、数据库结构和发布版本。后台任务不是第二套业务服务，不能绕过 HTTP 入口所依赖的当前授权、对象状态、版本和作用域规则。

| 运行单元 | 责任 | 可独立扩容 | 禁止事项 |
|---|---|---|---|
| 响应式 Web 前端 | 页面、交互、传输适配和安全错误展示 | 可随静态交付形态扩展 | 保存服务秘密、充当权限权威、形成独立业务状态 |
| HTTP 应用 | 认证上下文、命令/查询、领域事务、文件/外部意图和安全投影 | 是 | 使用框架默认值改变业务规则；把缓存当权威 |
| 后台任务单元 | 租约领取、外部调用、检查/预览、通知、对账、清理、删除和派生重建 | 是 | 旧租约提交、扩大任务范围、跳过当前条件复核 |
| PostgreSQL | 本地业务、历史、任务、通知、审计、文件元数据和删除清单权威 | 按既有部署能力扩展 | 按社团/模块拆库或拆业务 Schema；由缓存替代 |
| 对象存储 | 文件字节、经检查原件和临时派生字节 | 按产品能力扩展 | 充当文件授权、业务版本、删除或保留期限权威 |

### 4.2 官方支持的部署轮廓

`OPS-TOPO-004`：官方支持完整容器化单机部署，以及使用同一程序按需拆分 HTTP 应用、PostgreSQL、后台任务和对象存储。首版不强制 Kubernetes、自动故障切换、零停机升级或特定编排平台。

`OPS-TOPO-005`：单社团部署仍使用同一套代码和构建产物，只通过配置限制业务范围，不建立学校版、社团版或无法共同升级的源码分支。

| 参考轮廓 | 已确认参考，不是承载保证 | 强制证据 |
|---|---|---|
| 开发测试 | 4 核 8GB、100GB SSD 起 | 核心能力和依赖可运行；不使用真实数据或生产秘密 |
| 两社团试点 | 至少 4 核 8GB、200GB NVMe，附件独立存储 | 隔离、文件、通知、备份恢复和容量验证 |
| 单校经济型生产 | 8 核 32GB、500GB NVMe，500GB 至 1TB 可扩容对象存储 | 代表性数据、500 并发混合负载、恢复和依赖故障证据 |
| 完整设计容量 | 两台 4 核 8GB 应用节点、8 核 32GB PostgreSQL、4 核 8GB 后台/文件检查节点及独立对象与备份存储 | 最终承载能力仍以压力、长稳和恢复证据为准 |

资源可使用等效规格；不得把参考值变成固定云厂商采购要求，也不得在没有压力与恢复证据时声明正式承载能力。

## 5. 环境、依赖与数据权威

`OPS-TOPO-006`：每个隔离环境拥有独立外置配置、数据库、服务身份、三个私有文件 Bucket、日志边界和备份边界。开发、测试/验收和生产不得共享凭据、Bucket、数据库、恢复点或真实学生数据。

| 依赖 | 权威责任 | 部署前必须确认 | 不能假设 |
|---|---|---|---|
| 学校 Casdoor v3.108.0 | 当前账号和当前 Group 关系 | 实例指纹、身份/Group 字段、读写权限、写后可见性、MFA/auth_time/会话撤销等真实能力证据 | 官方源码或 SDK 默认等于学校实例已启用 |
| PostgreSQL | 本地业务与技术权威数据 | 受支持 PostgreSQL 18、必要扩展、统一业务 Schema、身份/RLS、备份和恢复能力 | ORM 自动同步、默认 Schema/search_path、默认事务或锁行为正确 |
| 对象存储 | 文件字节 | 三个私有 Bucket、只写一次、防覆盖、检查/预览、删除和恢复证据 | 对象键、ETag、Version ID 或 Bucket ACL 可替代业务授权 |
| 邮件 | 可选渠道与邮箱验证邮件 | 发件身份、目标范围、秘密引用、失败和轮换证据 | 邮件成功等于业务成功或用户已读 |
| 文件检查/预览 | 自动安全检查与派生预览 | 实际类型、内容、资源边界、失败关闭、版本绑定和恢复证据 | 扩展名可信、扫描失败可放行、预览可替代原件 |

搜索、统计、个人中心、工作台和缓存均为可重建派生数据，不能授权、覆盖 PostgreSQL/Casdoor 权威状态或在恢复中反向写回业务事实。

## 6. 运行身份、服务账号与特权边界

### 6.1 身份分层

| 身份 | 允许范围 | 禁止范围 |
|---|---|---|
| 普通 HTTP 应用身份 | 执行登记的业务读写、事务内设置最小作用域上下文 | 绕过 RLS、安装扩展、执行迁移、读取全部秘密或恢复材料 |
| 后台任务身份 | 按冻结任务意图、当前租约、最小作用域和当前条件执行 | 继承旧请求权限、扩大目标、无条件全表访问或使用旧租约提交 |
| 迁移身份 | 在受控升级窗口执行已批准、版本化迁移和必要扩展检查 | 承接普通请求、长期在线或成为业务运行身份 |
| 维护身份 | 在明确目标、范围和时窗内执行批准的诊断/维护 | 绕过业务形成新事实、长期复用或接入普通流量 |
| 恢复身份 | 在隔离恢复边界执行恢复、删除重放、附件核验和对账 | 直接对普通用户提供服务，或在恢复门前开放普通写入 |

`OPS-ID-001`：产品中的超级管理员不是数据库超级用户、对象存储全权身份或 Casdoor 服务账号。产品权限不能映射为基础设施无条件高权限。

`OPS-ID-002`：所有服务账号按环境、职责和允许/拒绝矩阵最小授权。读写职责是否拆分、凭据载体和轮换工具留待实现/部署评审；任何方案都不能因对账、SDK、调试或恢复方便而授予无关管理权限。

`OPS-ID-003`：特权、迁移、维护和恢复身份必须具有明确用途、目标环境、批准记录、开始/结束时间和结果证据；使用结束后不得继续承接普通请求或后台任务。

## 7. 外置配置、秘密与传输保护

### 7.1 单文件配置合同

`OPS-CFG-001`：部署目录使用一份外置配置文件表达环境差异，并以只读方式挂载到容器或等价运行边界。真实配置不得进入源码、镜像、示例、测试夹具、文档、截图或公开发布物。

启动前必须校验配置结构、环境标识、必需引用、版本兼容和互斥条件。未知字段、缺失必需项、正式环境学校硬编码或开发策略误用不得被框架默认值静默接受。本文不冻结配置字段名、文件路径、格式或加载库。

### 7.2 秘密生命周期

`OPS-CFG-002`：部署秘密通过数据库外受控配置入口或未来经评审的秘密提供器加载；数据库托管秘密沿用已确认的服务端应用层 AES-256-GCM、版本化 AAD、强类型秘密引用和数据库外版本化密钥环。首版不使用 `pgcrypto` 保存这些秘密。

`OPS-CFG-003`：根密钥只能通过外置版本化引用提供，不能与密文共同进入数据库备份、仓库或镜像。轮换必须保留新旧版本的受控过渡、失败回滚、撤销和恢复验证；已撤销版本不得继续解密或签发新内容。

`OPS-CFG-004`：根密钥丢失、引用不可解析、版本被撤销或完整性无法确认时，受影响能力失败关闭并进入恢复；不得把旧明文写回普通配置、日志或数据库作为回滚手段。恢复旧备份后按上游边界重新录入或轮换应用秘密。

`OPS-CFG-005`：浏览器、页面源、前端构建物、URL/可导航参数、通知、错误、日志、审计、任务载荷和状态页不得暴露服务秘密、令牌、私钥、长期对象凭据或完整外部响应。日志采用字段允许清单；疑似秘密在落盘前拒绝或移除，不能先写原文再清理。

### 7.3 HTTPS 与浏览器/传输控制

`OPS-CFG-006`：正式环境必须使用 HTTPS；非 HTTPS 正式配置必须明确阻止或警告并保持受保护能力关闭。传输保护必须覆盖认证证据、业务数据、文件访问、外部回调和运维入口。

具体代理、证书产品、Cookie、CORS、CSP、响应头、会话库和 CSRF 机制必须等待 API/会话/部署形态评审，不能由 Vue、NestJS、容器或代理默认值替代。部署证据必须证明选定机制满足安全设计第 16 节的 XSS、请求伪造、跨源、点击劫持、开放重定向、令牌泄漏和重放控制目标。

## 8. 部署前置检查与启动判定

### 8.1 证据基线

`OPS-DEP-001`：每次部署或升级前创建版本化证据基线，至少记录：

- 目标环境与拓扑、发布版本、构建来源和构建指纹；
- 配置结构版本和脱敏摘要，只记录秘密引用及其版本，不记录秘密值；
- PostgreSQL 大/小版本证据、必要扩展、数据库/Schema、排序与可选 ICU 能力；
- HTTP/后台运行身份、RLS/连接上下文和特权身份隔离结论；
- Casdoor 实例指纹、Claims/UserInfo/Group、服务账号、写后可见性、MFA/auth_time/会话撤销证据版本；
- 对象 Bucket 的私有性、版本控制/Object Lock、防覆盖、检查/预览和删除能力结论；
- 邮件、文件检查、备份、根密钥引用和 HTTPS 的状态；
- 上一可恢复发布、备份标识、恢复步骤版本、已知问题和阻断项。

证据只保存必要摘要和安全定位，不保存完整外部响应、真实账号、令牌、密钥、证书私钥或学校敏感配置。

### 8.2 PostgreSQL 前置检查

`OPS-DEP-002`：首版只支持 PostgreSQL 18；实际部署使用当时仍受支持的 18.x 小版本，并在每次更新前验证发布说明、迁移、扩展、RLS、备份恢复和关键查询。PostgreSQL 19 或其他大版本不能自动进入兼容范围。

前置证据至少覆盖：内置 `uuidv7()`、UTF-8、确定性 `pg_unicode_fast` 权威顺序、必要的 `pg_trgm` 与 `btree_gist`、无 `pgcrypto`、统一应用业务 Schema、普通/后台身份无扩展管理权限，以及已登记 ICU 展示排序的实际能力。缺少必要扩展时在预检或迁移阶段失败，不得运行后静默取消名称近似或时间不重叠约束。

### 8.3 Casdoor 实例前置检查

`OPS-DEP-003`：生产放行只能依赖学校实际 v3.108.0 实例证据。必须核对实例指纹、issuer/audience/subject、签名/密钥、时效、账号状态、Claims/UserInfo 字段、Organization/Group 映射、读写最小权限、写后可见性、分页/限流事实、MFA、auth_time、强制重新认证和会话撤销。

无法证明的能力标记为“未知”并按受影响风险失败关闭，不能用官方源码、最新文档、SDK 或开发实例代替。Webhook 默认关闭，不属于正确性或启动前置条件。

### 8.4 启动、能力阻断和降级分类

| 结果 | 含义 | 允许动作 |
|---|---|---|
| 启动阻断 | 配置无法解析、发布/迁移不兼容、数据库权威无法建立或基础安全证据不成立 | 不启动普通业务服务，保留脱敏失败证据 |
| 能力阻断 | 某项依赖或秘密只影响登记能力 | 应用可运行，但对应能力按 SRS 关闭，不得伪造健康或成功 |
| 明确降级 | 上游已有降级目录，如 Casdoor 15 分钟最小白名单、附件故障或邮件故障 | 只开放目录内能力，显示真实状态和时间 |
| 未知 | 结果、实例能力或状态无法可信确认 | 按风险失败关闭；状态页显示未知，不得按健康处理 |

全新启动时不存在可自动继承的“故障前可信会话”；Casdoor 不可确认时不得制造 15 分钟旧会话资格。应用或依赖恢复后仍须按当前账号、Group、对象和版本重新验证。

## 9. PostgreSQL、RLS 与连接上下文

`OPS-DB-001`：首版使用单个 PostgreSQL 数据库和统一应用业务 Schema，不按社团或领域模块拆库/拆 Schema。模块所有权通过代码边界、命名、访问规则、评审和测试保证；不得依赖 Schema 拆分改变既有事务。

`OPS-DB-002`：应用逐请求授权、数据库作用域约束和普通社团业务表选择性 RLS 共同生效。联合协作域使用独立关系和授权，不能通过放宽普通 `club_id` 过滤获得跨社团访问。

### 9.1 事务内上下文生命周期

每个受保护数据库操作必须：

1. 从可信服务端身份和业务对象重建最小单目标或登记式集合只读上下文；
2. 在事务边界内建立并验证上下文；
3. 使用与入口类型一致的读取或写入能力；
4. 在成功、回滚、异常、超时和取消后清理；
5. 连接归还池前证明不存在跨请求残留；
6. 缺失、污染、格式错误或上下文类型混用时失败关闭。

`OPS-DB-003`：集合只读上下文不能写入；客户端不能伪造或扩大集合。连接池复用、取消和错误路径必须进入部署前负向验证。

`OPS-DB-004`：普通应用和后台任务身份不得绕过 RLS。迁移、维护、恢复或特权连接必须与普通流量隔离，不得由产品超级管理员取得，也不得因故障临时切换给普通请求。

`OPS-DB-005`：扩展安装、迁移和结构变更只由受控迁移身份执行。不得依赖默认 `search_path`、ORM 自动同步或生产临时建索引；扩展对象、索引、排序和派生载体都必须具有版本、回滚/不可回滚边界和恢复证据。

## 10. PostgreSQL 权威任务、租约与幂等

`OPS-JOB-001`：后台工作以 PostgreSQL 持久任务/事务发件箱为权威。业务事实与必要任务意图按既有事务边界原子提交；队列、缓存、进程内调度或外部回调不能成为业务权威。

`OPS-JOB-002`：任务至少包含稳定业务意图、最小作用域、目标/相关版本、任务类型、幂等依据、状态、尝试、租约版本、父追踪和结果引用。任务载荷不得复制完整业务正文、秘密或完整外部响应。

`OPS-JOB-003`：任务按至少一次语义执行。每次尝试取得有期限的租约；重复领取、租约过期、续租失败、对象版本变化或作用域扩大时，旧持有者不得提交。重复尝试必须收敛到一份业务结果。

`OPS-JOB-004`：重试从当前认证/系统来源、授权、对象状态、版本、依赖状态和全部前置条件重新执行完整命令，复用原业务意图；不得只重放最后一条数据库语句或外部请求。响应未知时先读回，不盲目重放。

`OPS-JOB-005`：升级、维护和恢复期间必须按作业单明确哪些任务停止领取、等待完成、保持积压或在恢复后重验。恢复前的旧租约、旧请求权限、旧安全开关和旧短链全部失效；恢复只重新处理仍有效的权威任务。

## 11. 私有文件、检查、访问与删除

`OPS-FIL-001`：每个隔离环境使用三个私有 Bucket：待检查隔离区、权威原件区、临时派生区。环境之间不共享 Bucket、凭据或备份；同一环境不按社团拆 Bucket，租户隔离仍由 PostgreSQL 引用、当前授权和字段权限保证。

`OPS-FIL-002`：对象键由服务端生成不少于 128 位有效熵的随机定位符，只写一次、不覆盖、不复用，且不编码用户、学号、社团、业务对象、原始文件名、权限或内容摘要。具体 Bucket 名称、对象存储产品和防覆盖机制在部署证据中确认，不写入源码常量。

`OPS-FIL-003`：三个在线 Bucket 不启用对象存储原生 Versioning 或 Object Lock；仅“暂停”曾启用的版本控制不能视为满足。应用级不可变文件版本是唯一业务版本。备份仓库可使用独立快照或不可变保护，但不能改变在线删除与恢复门。

`OPS-FIL-004`：上传只进入隔离区。实际类型、大小、恶意内容和资源风险未由可信检查确认前，不得正式绑定、预览或下载。检查通过后仍须以新键晋升、核对大小和可信 SHA-256，并由 PostgreSQL 原子收口对象定位、文件版本状态和审计。

`OPS-FIL-005`：每次下载和预览重新校验当前主体、业务对象、字段、任务、社团/联合关系、检查和删除状态。短期地址不是长期授权；失权、社团停用、任务结束、字段收紧、删除开始或恢复后旧地址立即失效。

`OPS-FIL-006`：清理和正式删除先撤销访问，再推进数据库、原件、隔离副本、派生物、缓存、索引和未过期导出清单。任一步失败都不宣称完成、不恢复访问；恢复后依据数据库引用、文件版本、检查状态、删除清单和当前授权重验。

| 通知事实保存失败 | 直接权益业务整体回滚 | 原业务幂等键重试；渠道恢复不得补造业务 |

`OPS-DEP-004`：故障、超时、断连、未知、迟到响应和恢复都必须保留真实状态。应用仍可运行时，严重异常进入内置状态页和脱敏日志；应用或宿主机完全不可用时，RanaMinder 不承诺自动系统外发现、外部告警或送达。

### 12.1 Casdoor 正确性路径

`OPS-DEP-005`：当前账号/Group 正确性使用三条既有路径：周期全量对账、写后定向读回、高风险操作实时读回。普通缓存只能提高性能，不能授予新权限或覆盖可信读回。

`OPS-DEP-006`：Webhook 默认关闭。未来启用时仍仅能触发受控刷新或对账；缺失、重复、迟到、乱序、伪造和重放不得直接禁用账号、增删 Group、改变成员/职位、发布结论或恢复权限。没有可证明的签名、唯一标识或顺序能力时不得自行假定。

## 13. 标准部署与启动作业边界

`OPS-DEP-007`：具体作业单可以按实际编排实现以下逻辑阶段，但不得跳过证据门：

1. 确认目标环境、发布来源、支持的来源版本、拓扑和维护窗口；
2. 生成 `OPS-DEP-001` 证据基线，确认阻断项和上一可恢复点；
3. 准备外置只读配置和秘密引用，扫描学校信息与秘密暴露；
4. 验证 PostgreSQL 18、必要扩展、数据库/Schema、身份、RLS 和备份能力；
5. 验证 Casdoor、对象存储、邮件、文件检查、HTTPS 和内置状态依赖；
6. 仅由迁移身份执行已批准的结构初始化或版本化迁移；
7. 分别启动 HTTP 应用和后台任务入口，记录构建、配置和启动状态；
8. 执行合成数据核心冒烟、隔离/RLS 负向、任务租约、文件检查和外部读回验证；
9. 核对内置状态页、脱敏日志、追踪父子关系和业务幂等键分离；
10. 依据实际结果形成继续、保持关闭或恢复决定。

任何阶段结果未知、迁移状态不清、配置不兼容或核心权威无法建立时，保持普通业务关闭。不得通过手工改库、禁用 RLS、放宽 Bucket、复用生产秘密或跳过 Casdoor 回读完成部署。

## 14. 升级、迁移、维护与回滚

### 14.1 升级前置

`OPS-UPG-001`：每个正式版本必须声明支持的来源版本、配置变化、数据库迁移顺序、必要扩展、依赖兼容、已知问题、回滚步骤和不可安全回滚警告。不得跨越未声明来源版本直接升级。

升级前至少验证：构建来源、配置兼容、资源/空间条件、数据库与扩展、Casdoor/文件依赖、当前任务和租约、备份可定位且可读、恢复步骤与发布说明一致、敏感扫描和阻断项清零。

### 14.2 迁移与未知结果

`OPS-UPG-002`：迁移具有版本、顺序、已完成步骤识别、幂等重入边界和失败处置。迁移身份与普通运行隔离；不得使用 ORM 自动同步、框架启动副作用或未登记脚本改变生产结构。

`OPS-UPG-003`：升级作业必须明确 HTTP 写入、任务领取、现有租约和外部副作用在各阶段的处理。会导致状态分叉或旧版本写入不兼容的阶段必须关闭相应写入；不强制零停机。

`OPS-UPG-004`：迁移中断或结果不确定时，不盲目重跑、不把进程退出码单独当作状态权威。先核对迁移版本、已完成步骤、数据库/扩展和应用兼容，再按发布说明选择继续、修复、恢复或保持关闭。

### 14.3 回滚边界

`OPS-UPG-005`：只有发布说明明确证明应用、配置、数据库和文件格式均可安全回退时，才能执行回滚。无法安全回滚的迁移必须在变更前警告并提供恢复路径；不得承诺所有升级都可原地回滚。

不可变配置回滚通过基于旧版本创建并发布新版本表达，不覆盖历史版本；秘密回滚不能恢复旧明文或已撤销密钥；已经执行的正式删除步骤不能因回滚复原个人数据。

### 14.4 计划维护与完全不可用

`OPS-UPG-006`：计划维护只有至少提前 24 小时公告，并明确开始、结束和影响范围时，才可按上游口径排除公告窗口内实际不可用时间。超出窗口、紧急维护和未公告停机计入不可用；月报同时保留原始可用率、调整后可用率和排除分钟数。

RanaMinder 不承诺机器健康接口、独立监测进程、外部运维邮箱/Webhook 告警、应用宕机自动发现、指标/追踪导出或完整观测平台。部署者可以另行建设系统外能力，但不能把它写成 RanaMinder 首版产品保证或授权来源。

`OPS-LOG-001`：请求、后台任务和外部调用使用各自唯一追踪编号并保留父子关系；业务幂等键、任务尝试编号和追踪编号不得混同或编码个人信息。

`OPS-LOG-002`：业务审计与普通/网络/安全日志分层访问和保留。延长期限不能放宽内容排除；敏感标记扫描发现泄漏时必须阻止继续发布或按安全事件处置，不能只删除当前样本后声称通过。

`OPS-LOG-003`：内置状态页只提供技术事实和提示，不能改变申请、结论、邀请、成员、部门、职位、评价、权限或删除状态。状态过期、来源失败或结果未知时显示“未知”。

## 16. 备份合同

`OPS-BKP-001`：正式业务恢复点目标 RPO 不超过 15 分钟，核心登录、查询和写入恢复时间目标 RTO 不超过 4 小时。目标必须由实际部署、备份和全量恢复证据证明，不能只由配置或任务成功记录证明。

`OPS-BKP-002`：PostgreSQL 使用持续事务日志和每日完整备份；附件字节同步纳入恢复范围。正式删除执行清单、最小删除审计、必要配置/版本信息、迁移版本和文件引用必须可与恢复点一起定位。

`OPS-BKP-003`：备份在静态和传输中受保护，默认保留 30 天，可配置 30 至 60 天。备份期限只决定可选恢复点，不决定正式业务数据期限；正式业务不能把备份当长期档案或查询入口。

`OPS-BKP-004`：备份与生产故障域分离，不能直接对普通查询、导出或文件下载提供服务。根密钥不得与密文同处同一备份边界；恢复旧备份后应用秘密按既有规则重新录入或轮换。

`OPS-BKP-005`：每个备份周期保留目录、恢复点、事务日志覆盖、附件覆盖、加密状态、必要版本、到期清理和抽样可读性证据。只有“备份任务成功”而没有实际可读性和恢复验证，不通过。

`OPS-BKP-006`：至少每季度执行一次全量恢复演练并记录结果。演练使用隔离环境、合成验证数据和真实恢复材料边界，不得把生产恢复副本直接接入普通流量。

## 17. 恢复运行与普通写入开放门

### 17.1 恢复启动与隔离

`OPS-RCV-001`：恢复运行必须先记录事件/演练范围、目标环境、故障时间线、可选恢复点、预期数据缺口、责任人、发布/配置/结构版本和普通流量隔离状态。完全不可用可能由系统外人工发现；本文不伪造 RanaMinder 自动告警。

`OPS-RCV-002`：恢复身份和恢复副本与普通运行隔离。HTTP 普通写入保持关闭；旧 HTTP 会话、后台任务领取、旧租约、旧短链、旧导出下载和缓存不得因进程启动自动恢复。

### 17.2 恢复步骤

恢复作业必须按实际环境形成可执行清单，并至少证明：

1. 选择的恢复点、事务日志覆盖和预期 RPO 可说明；
2. PostgreSQL 18、必要扩展、统一 Schema、迁移版本和数据一致性可验证；
3. 权威原件区恢复，隔离区会话明确失败/重新上传，临时派生按源版本重建或清理；
4. 恢复点后仍应生效的正式删除清单全部可获得并重放；
5. 数据库文件引用与对象原件、预览、检查版本和删除状态逐项核对；
6. Casdoor 对当前账号和 Group 执行全量对账，差异进入同步异常，不直接覆盖本地历史；
7. 旧会话、旧 Group 快照、旧任务租约、旧短链、旧缓存、旧导出和已撤销密钥不复活；
8. 任务仅按当前对象版本、当前授权、当前安全开关和新租约重新处理；
9. 内置状态页、日志、追踪、通知和备份最近结果反映真实恢复状态；
10. 核心登录、查询和写入的 RTO 及数据点 RPO 有实际测量结论。

`OPS-RCV-003`：删除重放、附件一致性或 Casdoor 对账存在未确认差异时，不得宣称恢复完成。高风险与权限敏感能力继续失败关闭；差异必须进入同步异常、删除未完成或明确阻塞状态。

### 17.3 写入开放门

`OPS-RCV-004`：普通写入只能在以下证据均有明确结论后开放：恢复点/事务日志、数据库/结构、删除重放、附件一致性、Casdoor 全量对账、身份/RLS、任务租约、秘密/HTTPS、核心冒烟、RPO/RTO、未关闭阻断项和恢复批准。

读取是否在恢复期间提前开放必须基于当前授权、数据完整性和披露风险单独证明；本文不承诺只读降级一定安全。结果未知等同恢复门未通过。

`OPS-RCV-005`：开放普通写入是明确操作决定，不由“数据库可连接”“容器已启动”“最后一个步骤退出成功”或状态页显示自动触发。必须建立单一、版本化的恢复门汇总记录，引用各子系统原始证据并明确给出“开放/保持关闭”结论；汇总记录不得复制秘密或完整外部响应。

### 17.4 恢复后复核

恢复后继续验证删除清单最终收敛、文件派生重建、Casdoor 差异处置、通知渠道补投不重放业务、任务无重复副作用、旧权限不复活、日志/状态无敏感泄漏，并形成缺陷、纠正措施和复验记录。

### 19.2 证据安全

证据使用合成数据和合成敏感标记。不得保存真实令牌、密钥、证书私钥、服务账号秘密、完整 Casdoor/对象存储/邮件响应、学校敏感配置、学生正文或附件。必要外部证据只保留允许字段、分类、时间、指纹、版本和脱敏摘要。

失败证据不得被成功重跑覆盖；恢复或升级的每次尝试保留独立编号和父子关系。任何批准都不能替代上游权限、状态、版本、RPO/RTO、删除、附件和对账门。

## 22. `OPS-Q-001`：恢复门批准证据的汇总方式（已关闭：采用方案 A）

问题含义：恢复后开放普通写入需要一个明确批准决定；需要确认该决定是否必须有单一汇总门禁记录，统一引用恢复点、删除重放、附件、Casdoor、RLS、任务、秘密、RPO/RTO 和阻断项证据，还是允许只依赖各子系统分散记录。

推荐方案 A：建立单一、版本化的恢复门汇总记录，引用各子系统原始证据并给出“开放/保持关闭”结论。原始证据仍留在对应记录中，汇总不复制秘密或完整响应。

| 方案 | 优点 | 缺点 |
|---|---|---|
| A：单一汇总门禁记录（推荐） | 防止遗漏子门、便于审计和复盘、明确最终写入决定 | 需要维护汇总与原始证据引用的一致性 |
| B：仅保留分散子系统记录 | 每个团队/组件独立记录，形式更轻 | 容易出现各项局部成功却无人对整体写入开放负责，复核成本高 |

关闭记录：2026-07-31，需求方确认采用方案 A。恢复后开放普通写入必须具有单一、版本化的恢复门汇总记录，统一引用恢复点、删除重放、附件、Casdoor、RLS、任务、秘密、RPO/RTO 和阻断项的原始证据，并明确给出“开放/保持关闭”结论；原始证据仍保留在对应记录中，汇总不复制秘密或完整响应。

影响范围：恢复证据的组织、批准记录和普通写入开放作业。  
不影响范围：产品角色与权限、236 个需求事实、29 个状态机、8 类事务、13 条故障、54 条 NFR、RPO/RTO、删除/附件/Casdoor 恢复门、具体人员编制、部署产品、测试执行状态和代码开工门。
