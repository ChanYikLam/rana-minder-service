## 2. 目录与命名规范

`TEST-GUIDE-002`：

1. **文件命名**：`<subject>.spec.ts`，subject 使用 kebab-case，且必须能对应到测试规格中的 `TST-*` 入口族；如 `org-join.spec.ts`、`tx-003-casdoor.spec.ts`、`fail-005-postgres.spec.ts`。
2. **测试名**：`test('TST-XXX-NNN 中文主题：行为断言', ...)` 或 `test('中文主题', ...)`，中文主题必须能让评审人直接定位到测试规格入口；不写“test1”“case1”。
3. **describe 分组**：按状态机、事务族、故障规则、NFR 族或端点域分组；禁止按实现文件路径分组掩盖业务入口。
4. **每个文件自包含**：不依赖其他测试文件的执行顺序；共享夹具放入 `test/helpers/` 或 `test/fixtures/`，不得隐藏在用例内。
5. **异步清理**：使用 `test.after`/`test.afterEach` 或 `try/finally` 清理数据库、容器、临时文件；不得假设下一个用例会清理。

## 3. L1 单元测试编写规范

`TEST-GUIDE-010`：L1 覆盖领域规则：状态机守卫、校验、幂等、版本、事务边界逻辑（不经 HTTP 入口）。位置在 `src/modules/<module>/domain/**/*.spec.ts` 或 `src/common/**/*.spec.ts`；平台支撑模块已落地在 `src/platform/**/*.spec.ts`。

允许依赖：

- `node:test`、`node:assert/strict`；
- 被测的领域模型/服务/状态机/纯函数；
- 合成数据构造器（`SynDataBuilder` 稳定后可从 `test/helpers` 引入）。

禁止出现：

- `@nestjs/*`、TypeORM、数据库连接、HTTP 端口、真实 Casdoor/邮件/存储调用；
- 测试之间共享可变全局状态。

推荐模板：

```ts
import assert from 'node:assert/strict';
import { test } from 'node:test';
import { OrgJoinStateMachine } from './state-machines/org-join.state-machine';

test('TST-SM-004-R001-NOM 社团接入：规范路径下状态推进', () => {
  const sm = new OrgJoinStateMachine();
  const result = sm.apply({ state: 'DRAFT', command: 'SUBMIT', actor: 'club_leader' });
  assert.equal(result.next, 'PENDING');
});

test('TST-SM-004-R001-AUT 社团接入：非负责人提交被拒绝', () => {
  const sm = new OrgJoinStateMachine();
  assert.throws(
    () => sm.apply({ state: 'DRAFT', command: 'SUBMIT', actor: 'member' }),
    /FORBIDDEN/,
  );
});
```

L1 覆盖清单（按测试执行计划 §3）：

- 状态机：`NOM/AUT/STA/VER/CON/REV` 六分面逐行展开；
- 校验：必填、格式、范围、跨字段互斥；
- 幂等：同键同参不重复产生业务结果；同键异参拒绝或按上游规则处理；
- 版本：期望版本不匹配失败并携带当前版本数据。

## 4. L2 集成测试编写规范

`TEST-GUIDE-020`：L2 覆盖模块协作、数据库约束（唯一/RLS/btree_gist/JSONB）、任务租约与幂等、通知/审计原子性。文件放 `test/integration/**/*.spec.ts`。

环境合同：

- CI 阶段 5 启动 `postgres:18-alpine` 容器 `pg18-ci`，数据库 `ranaminder_test`，用户 `postgres`，密码 `ci`，端口 `5432`；
- 测试脚本可通过 `docker exec pg18-ci psql`（容器内直连）或以 `pg` 客户端经 TCP 连接；本仓库已登记 `pg` 与 `@types/pg`；
- 经 TCP 连接时，pg 容器以 `-p 5432:5432` 发布端口；dind 下 job 容器与 daemon 共享网络命名空间，CI 用 `DATABASE_HOST=127.0.0.1` 访问并导出 `DATABASE_PORT/NAME/USER/PASSWORD`（容器桥接 IP 在 dind 下不可达，勿用 `docker inspect` 取 IP），见 `.cnb.yml` 阶段 5；
- 本地运行：`docker compose -f docker-compose.dev.yml up -d postgres` 后执行 `pnpm run test:integration`。

推荐模板：

```ts
import assert from 'node:assert/strict';
import { test } from 'node:test';
import { Client } from 'pg';

test('TST-TX-001 本地业务状态转换：同一事务内原子提交', async (t) => {
  const client = new Client({
    connectionString:
      process.env.TEST_DATABASE_URL ?? 'postgresql://postgres:ci@127.0.0.1:5432/ranaminder_test',
  });
  await client.connect();
  t.after(async () => {
    await client.end();
  });

  await client.query('BEGIN');
  await client.query("SELECT set_config('app.current_club', 'club-1', false)");
  // ... 调用仓储/用例写入
  await client.query('ROLLBACK');
  assert.ok(true);
});
```

L2 覆盖清单：

- 数据库约束：唯一、外键、RLS 策略、`btree_gist` 时间不重叠、JSONB 快照还原；
- 任务租约：重复领取、租约到期、旧任务复活、并发单胜者；
- 事务：本地原子事实同成同败；外部副作用不得伪装为 PostgreSQL 分布式原子事务。

## 5. L3 契约测试编写规范

`TEST-GUIDE-030`：L3 覆盖 HTTP 级契约：信封、17 类错误码、分页、幂等/版本头、脱敏。文件放 `test/contract/**/*.spec.ts`。

执行方式：

- 首版优先使用 `node:test` + Node 内置 `fetch` 或 NestJS `Test.createTestingModule` + `supertest`（待依赖基线登记后启用）；
- 在 HTTP 入口实现前，允许先验证传输层运行时常量（错误码映射、路径常量），如当前 `test/contract/transmission-contracts.spec.ts`；
- 接口实现后必须覆盖测试执行计划 §3 的接口五类：正常 / 拒绝 / 同键重放 / 版本冲突 / 失权 / 脱敏。

推荐模板：

```ts
import assert from 'node:assert/strict';
import { test } from 'node:test';

test('TST-IFC-xxx 错误信封：未知路径返回 404 且 code=IFC-ERR-015', async () => {
  const res = await fetch('http://127.0.0.1:3000/api/not-exist');
  assert.equal(res.status, 404);
  const body = await res.json();
  assert.equal(body.code, 'IFC-ERR-015');
  assert.equal(typeof body.supportId, 'string');
});
```

L3 覆盖清单：

- 信封：成功 `code=0`、失败只允许 `code/message/supportId/fieldErrors`；
- 17 类错误码与 HTTP 状态一一对应；
- 分页：游标绑定入口/筛选摘要/作用域/排序，损坏或跨入口复用拒绝；
- 幂等与版本头：同键重放单胜者，版本冲突返回当前数据；
- 脱敏：错误、日志、响应中不泄露报名正文、内部评语、完整联系方式、令牌、密钥。

## 6. L4 故障测试编写规范

`TEST-GUIDE-040`：L4 覆盖 13 条 `SRS-FAIL-*` 的可信故障注入、失败关闭与恢复。文件放 `test/fault/**/*.spec.ts`（规划）。

每项必须满足：

- 至少一次可信故障注入（如停容器、改 DNS、超时、返回不确定结果）；
- 至少一次失败关闭验证（写入被拒、权限不扩大、不伪造成功）；
- 至少一次恢复验证（恢复后重放/对账/清理）。

推荐结构：

```ts
import { test } from 'node:test';
import { FaultInjector } from '../helpers/fault-injector';

test('TST-FAIL-005 PostgreSQL 不可用：写入停止且恢复后不冒充成功', async (t) => {
  const injector = new FaultInjector();
  await injector.stopPostgres();
  t.after(async () => {
    await injector.restorePostgres();
  });
  // 断言写入被拒绝
});
```
