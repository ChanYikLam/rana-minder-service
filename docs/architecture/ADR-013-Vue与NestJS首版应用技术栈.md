# ADR-013：Vue 与 NestJS 首版应用技术栈

> 状态：已接受  
> 决策日期：2026-07-30  
> 决策范围：系统架构后续技术决策  
> 上游基线：[系统架构总览 v1.0](系统架构总览-v1.0.md)；[ADR-001](ADR-001-首版应用形态与后台任务运行单元.md)、[ADR-002](ADR-002-逻辑模块与状态机唯一责任基线.md)、[ADR-003](ADR-003-八类事务边界基线.md)、[ADR-004](ADR-004-后台任务与可靠投递机制.md)  
> 产品行为变更：否  
> 代码编写授权：已按需求方 [`GOV-CODE-WAIVER-001`](../governance/代码开工前置跳过与风险接受记录-v1.0.md) 豁免开放；本 ADR 不表示验证或发布通过

## 1. 背景

RanaMinder 已确认采用领域驱动的模块化单体作为首版主要应用形态，以 12 个领域模块和 3 个平台支撑模块承载 29 个状态机的唯一写入责任，并让后台任务作为可独立运行、部署和扩容的执行单元。现有架构还要求官方支持低成本单机 Docker 部署和同一程序按需拆分，因此应用技术栈需要同时兼顾小团队开发效率、模块边界、后台运行入口、长期维护、安全更新和运行资源。

需求事实、PRD 和 SRS 没有指定应用语言或框架。需求方已明确长期维护偏好为 Vue 与 NestJS，并接受 Vue 3＋TypeScript 前端、NestJS＋TypeScript 后端及独立后台任务入口作为首版应用技术栈基线。本决策只收口实现技术，不新增用户可见能力。

## 2. 已接受决策

1. 首版浏览器端采用 Vue 3 与 TypeScript；服务端 API 和后台任务采用 NestJS 与 TypeScript，运行于受支持的 Node.js LTS 版本。
2. 具体 Node.js、Vue、NestJS 和 TypeScript 版本不得在本 ADR 中写成永久版本；在首批代码验证前必须按当时仍受支持的版本形成可复现锁定，记录兼容性、安全支持期和升级策略，生产发布不得使用浮动的“latest”。
3. 后端保持一个模块化单体代码基线，但至少提供 HTTP 应用与后台任务两个独立启动入口。后台任务入口使用不监听 HTTP 的 NestJS 应用上下文或等效方式复用应用层、领域层和基础设施适配，不因此拆成微服务。
4. NestJS 模块边界必须承接已经确认的 12 个领域模块与 3 个平台支撑模块。模块可以继续拆分内部子模块，但不得因框架默认目录、依赖注入便利或共享数据库而合并状态机责任、跨模块直接写入他域权威数据，或绕过已确认的依赖方向。模块对外只暴露明确的应用能力或查询边界。
5. 采用轻量级 DDD：业务不变量、状态转换、授权后的业务判定和事务意图放在领域层或应用层；Controller、Guard、Pipe、ORM 模型、HTTP 客户端、对象存储和 Casdoor SDK 属于入口或基础设施适配。是否使用聚合、值对象或领域事件以真实复杂度为准，不要求为每个对象套用完整 DDD 模式。
6. TypeScript 静态类型不能代替运行时验证。HTTP 输入、配置文件、Casdoor 回调与回读、后台任务载荷、文件元数据、数据库 JSONB 和其他跨信任边界数据必须在使用前执行运行时结构、范围和业务前置条件校验。
7. 后台入口不得假定 HTTP Guard、Pipe、Interceptor 或请求上下文会自动生效。后台任务执行时仍须在应用能力边界重新校验当前授权条件、对象状态、版本、租约、幂等和外部结果收口条件，具体规则继续以上游 SRS、ADR-003 和 ADR-004 为准。
8. 前后端同为 TypeScript 只用于降低维护与工具切换成本，不代表前端可以直接依赖服务端领域模型，也不代表共享类型就是接口契约。后续接口规格必须独立定义认证、作用域、输入输出、错误、版本、幂等和并发语义；前端状态和类型不得成为授权或业务权威。
9. 文件检查、预览生成和其他 CPU/内存密集或处理不可信内容的工作继续遵守独立后台/文件检查边界，不得因选择 Node.js 而塞入 API 请求事件循环或绕过 ADR-008 的隔离与可恢复提交要求。

## 3. 候选方案与取舍

| 候选方案 | 优点 | 主要问题 | 结论 |
|---|---|---|---|
| Vue 3＋TypeScript；NestJS＋TypeScript | 前后端语言统一，降低小团队切换和维护成本；NestJS 模块封装可承接逻辑模块；可用独立应用上下文运行后台任务；与现有 Docker 和模块化单体方向兼容 | TypeScript 类型在运行时消失；模块边界仍需工程规则约束；CPU 密集工作需要隔离 | 采用 |
| Vue 3＋TypeScript；Spring Boot＋Java | 事务、数据、安全和企业工程生态成熟；适合大型 Java 团队 | 前后端双语言；构建、镜像和团队维护成本相对更高；与当前维护偏好不符 | 首版不采用 |
| Vue 3＋TypeScript；Go | 运行资源较低，部署简单，并发执行能力清晰 | 复杂领域建模、依赖边界和应用基础设施需要更多团队约定；与当前维护偏好不符 | 首版不采用 |
| React＋TypeScript；NestJS＋TypeScript | 同样可以形成全栈 TypeScript | 相比已熟悉的 Vue 没有足以抵消学习和维护切换的产品或架构收益 | 不采用 |

本选择不是对所有项目的通用优劣结论，而是在 RanaMinder 已确认边界、低成本交付目标和当前长期维护能力下的首版取舍。

## 4. 对后续文档的约束

- 数据设计必须明确事务和连接上下文如何跨 NestJS 应用模块传递，证明 PostgreSQL 约束、选择性 RLS、JSONB 校验、租约和幂等不依赖 TypeScript 编译期类型；本 ADR 不指定 ORM。
- 接口契约必须独立于 Vue 组件和 NestJS DTO 存在，并覆盖 306 条状态转换所需的认证、作用域、版本、错误、幂等、并发、通知、审计、重试和补偿语义。
- 安全设计必须覆盖 HTTP 与后台两个入口，集中定义身份上下文、逐请求/逐任务授权、运行时验证、错误脱敏、依赖升级和供应链检查；不得只在前端隐藏按钮或只在 Controller Guard 中实施核心授权。
- 测试规格必须覆盖模块依赖规则、领域/应用层不经入口也能验证的业务规则、HTTP 输入验证、后台入口等价校验、前后端契约兼容、Node.js 事件循环阻塞风险和受支持版本升级。
- 部署运维规格必须为 HTTP 应用和后台任务提供独立进程/容器启动、资源限制、优雅停止、版本标识和内置状态证据，同时保持 ADR-010 的单文件只读配置和 ADR-012 的分级部署边界。

## 5. 不受本决策影响的边界

本 ADR 不改变：

- 236 条需求事实、40 个用户故事、27 条全局不变量、29 个状态机、306 条转换、13 条故障恢复规则和 54 条非功能验收规则；
- 12 个领域模块、3 个平台支撑模块、29/29 个状态机唯一责任和 8 类事务边界；
- PostgreSQL＋关系骨架与 JSONB 混合存储、三层混合隔离与选择性 RLS、权威库持久任务、S3 兼容对象存储、Casdoor 统一适配、单文件外置配置、内置最小观测和恢复优先部署；
- 服务端逐请求授权、外部副作用可恢复执行、文件隔离检查、通知/审计原子性、正式删除和故障恢复语义；
- 代码开工门状态。

本 ADR 不选择：

- ORM、数据库迁移工具、API 风格、HTTP 适配器或接口生成方式；
- Vue UI 组件库、路由、状态管理、表单库或 CSS 方案；
- 包管理器、仓库布局、构建器、测试框架、代码格式化工具或 CI 产品；
- 具体 Node.js/框架补丁版本、反向代理、容器编排或云产品。

这些实现选择必须在下游规格或实现准备中基于已接受边界作出；不得借技术栈默认值创造产品行为。

## 6. 重新评估条件

出现以下任一证据时，可以创建补充或替代 ADR：

- 维护团队和长期所有权发生实质变化，现有技术栈不再具有可持续维护能力；
- 压力、长稳或容量测试证明受控优化和运行单元拆分后仍无法满足既定性能、容量或可用性要求；
- Node.js、Vue、NestJS 或关键依赖的支持、安全或许可证状态无法满足开源发布与生产维护要求；
- 后台 CPU/内存密集工作经隔离后仍需要不同运行时，且能保持任务、事务、幂等和恢复契约不变；
- 模块边界、事务一致性或安全控制无法在当前框架内以可验证成本实现。

替代技术栈必须证明不会改变产品行为、状态机责任、数据权威、事务边界、接口契约和恢复语义。局部采用不同运行时不自动意味着改为微服务。

## 7. 结论

ADR-013 收口“前后端语言与框架”这一最后的第一轮开放架构项。首版采用 Vue 3＋TypeScript 前端、NestJS＋TypeScript 后端，并为 HTTP 应用和后台任务提供独立启动入口；具体依赖版本和配套工具留待实现准备按受支持基线锁定。该决策不新增产品行为，也不构成代码开工批准。
