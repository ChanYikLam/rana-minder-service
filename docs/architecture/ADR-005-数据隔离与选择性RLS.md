# ADR-005：数据隔离与选择性 RLS

> 状态：已接受  
> 决策日期：2026-07-30  
> 决策范围：系统架构后续技术决策  
> 上游基线：[系统架构总览 v1.0](系统架构总览-v1.0.md)、[ADR-002](ADR-002-逻辑模块与状态机唯一责任基线.md)、[ADR-003](ADR-003-八类事务边界基线.md)及 [SRS v1.0](../specification/SRS-v1.0.md)  
> 产品行为变更：否  
> 代码编写授权：已按需求方 [`GOV-CODE-WAIVER-001`](../governance/代码开工前置跳过与风险接受记录-v1.0.md) 豁免开放；本 ADR 不表示验证或发布通过

## 1. 背景与约束

RanaMinder 在同一套部署中服务多个平等自治社团。普通社团业务必须严格隔离，但联合活动又需要依据锁定参与关系、当前状态、角色、作者归属、对象关系和活动阶段进行受控跨社团协作。联合授权不能通过简单放宽普通 `club_id` 过滤实现，超级管理员能力也不能退化成普通请求绕过授权。

应用层逐请求授权是产品与 SRS 的强制行为，但只依赖应用查询条件会把隔离安全完全建立在每段代码都不遗漏作用域过滤的假设上。因此需要在不改变业务授权规则的前提下，引入数据库结构约束和选择性行级安全作为纵深防御。

主要上游来源：`ORG-031` 至 `ORG-038`、`JNT-003` 至 `JNT-007`、`JNT-022` 至 `JNT-031`、`GOV-007`，以及 `SRS-INV-002` 至 `SRS-INV-006`、`SRS-INV-021`、`SRS-INV-024`。

## 2. 已接受决策

1. 首版采用**应用层逐请求授权＋数据库结构性作用域约束＋普通社团业务表选择性 PostgreSQL RLS**的三层混合隔离策略。
2. 应用层始终负责基于当前用户、目标对象、操作、作用域和业务状态完成最终业务授权。RLS 只提供数据库纵深防御，不能代替对象加载、角色/任务判断、字段级权限、联合活动规则或拒绝原因。
3. 数据模型必须让每个受保护业务对象能够稳定解析所属普通社团、联合协作域或平台域。普通社团对象之间的引用、唯一性和写入关系必须通过携带作用域的数据库约束阻止跨社团误关联；具体键、字段和约束形式由数据规格决定。
4. 对直接保存普通社团受保护业务事实、且能够由单一普通社团作用域判定行归属的表，默认评估并选择性启用 RLS。任何不启用 RLS 的例外都必须在数据与安全规格中记录原因、适用访问路径和等效数据库约束，不能以开发便利作为唯一理由。
5. 联合协作数据必须使用独立的协作域模型和显式授权路径，不得复用或放宽普通社团的简单 RLS 策略。联合域表是否采用专用 RLS，必须按其参与关系和对象模型在数据与安全规格中独立证明；不能只检查当前工作空间或一个 `club_id`。
6. 平台级配置、公开派生数据、不可变审计、后台任务和其他非普通社团表必须逐类标注数据域、访问角色和数据库保护方式，不得因“不适用普通 RLS”而成为无作用域的通用读写入口。
7. RLS 使用的作用域上下文只能由服务端在完成认证和对象/工作空间解析后建立。客户端提交的社团标识、旧链接、角色标签或缓存值不能直接成为数据库会话上下文；上下文缺失、无效或不明确时必须拒绝受保护访问。
8. 连接池复用时必须保证作用域上下文按事务或等效安全边界设置并可靠清除，防止上一请求的社团上下文泄漏到下一请求。具体连接管理方式进入数据和安全设计。
9. 普通应用运行角色不得拥有常规绕过 RLS 的能力。迁移、备份恢复和受控运维需要的数据库高权限必须与普通业务连接分离；超级管理员和后台任务仍须通过明确、最小权限、可审计的应用路径执行，不因产品角色获得通用数据库绕过。
10. 搜索、缓存、统计、导出和读模型继续遵守源数据作用域与当前授权，RLS 不能被解释为派生数据可以脱离服务端授权或把缓存作为权限来源。

## 3. 候选方案与取舍

| 候选方案 | 优点 | 主要问题 | 结论 |
|---|---|---|---|
| 应用授权＋结构约束＋普通社团业务表选择性 RLS | 多层防护；应用漏写普通作用域条件时仍有数据库兜底；能为联合域保留独立模型 | 连接上下文、后台任务、迁移和测试复杂度提高；必须维护策略与模型一致性 | 首版采用 |
| 应用授权＋结构约束，不使用 RLS | 开发、调试和运维较直接 | 查询遗漏作用域时缺少数据库行级兜底；对严格多社团隔离的防御深度不足 | 不作为正式基线 |
| 所有业务表全面使用统一 RLS | 形式上覆盖面最大 | 联合域、平台数据、超管、后台任务和恢复路径无法由统一普通社团策略正确表达，容易误拒绝或错误放行 | 首版不采用 |
| 每个社团独立数据库 | 普通社团物理隔离直观 | 联合活动、平台管理、升级、备份、开源单机部署和多社团运维复杂度过高 | 不采用 |

## 4. 对后续文档的约束

- 数据规格必须给每张持久化表标注普通社团域、联合协作域、平台域、公开派生域或技术运行域，并记录作用域来源、结构约束、RLS 适用性及例外理由。
- 接口契约必须区分客户端请求的工作空间提示与服务端可信授权上下文，不能让客户端作用域直接决定数据库会话。
- 安全设计必须定义应用、后台、迁移、恢复和受控运维的数据库身份边界，以及连接上下文设置、清除、失败关闭和审计要求。
- 测试规格必须覆盖遗漏应用过滤、伪造作用域、连接池上下文残留、跨社团引用、普通域与联合域混淆、后台任务越域、超管误用、恢复路径和派生数据失效。
- 运维与迁移流程必须验证新表、新访问路径和策略变更没有产生无保护表、策略空洞或普通业务角色的意外绕过权限。

## 5. 不受本决策影响的边界

本 ADR 不改变任何角色、产品权限、联合活动规则、字段可见性、超级管理员前置条件、状态机、通知或审计要求。数据库允许访问不等于业务命令获准；应用层拒绝也不能由数据库直连或后台任务绕过。

本 ADR 不决定：

- 具体表名、字段名、主键、外键、索引、Schema 或迁移顺序；
- 每张表的具体 RLS Policy、SQL、会话变量、数据库角色名或连接池产品；
- 联合域专用 RLS 的最终表级清单；
- 前后端语言、ORM、查询框架或仓库结构；
- 搜索、缓存、对象存储、Casdoor 适配、观测产品和生产高可用拓扑。

## 6. 重新评估条件

若性能、连接管理、运维或数据库兼容性测试证明某类表无法安全使用 RLS，可以创建补充或替代 ADR 调整范围，但必须同时证明：

- 普通社团隔离仍有应用授权以外的数据库级防线；
- 跨社团引用和写入由结构约束阻止；
- 联合域没有借调整 RLS 放宽为普通 `club_id` 过滤；
- 后台、超管、迁移和恢复路径仍最小授权、可审计且可负向测试。

## 7. 结论

ADR-005 收口“数据隔离实现”开放项。首版以服务端逐请求授权为业务判定，以数据库作用域约束阻止跨域关联，并对普通社团业务表选择性使用 PostgreSQL RLS 提供纵深防御；联合协作域继续独立建模和授权。该决策为数据、安全、接口与测试规格提供强制输入，但不构成代码开工批准。
