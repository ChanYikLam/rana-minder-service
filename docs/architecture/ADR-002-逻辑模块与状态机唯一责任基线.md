# ADR-002：逻辑模块与状态机唯一责任基线

> 状态：已接受  
> 修订状态：“运维与可观测性”平台支撑模块责任已按 `PRD-OPT-055` 由 [ADR-011](ADR-011-内置最小观测边界.md) 收窄；12＋3 个模块数量和 29 个状态机唯一责任归属不变（详见第 7 节）  
> 决策日期：2026-07-30  
> 决策范围：系统架构设计第一轮  
> 上游基线：[系统架构总览 v1.0](系统架构总览-v1.0.md)、[SRS v1.0](../specification/SRS-v1.0.md)及[状态机转换明细](../specification/SRS-状态机转换明细-v1.0.md)  
> 产品行为变更：否  
> 代码编写授权：已按需求方 [`GOV-CODE-WAIVER-001`](../governance/代码开工前置跳过与风险接受记录-v1.0.md) 豁免开放；本 ADR 不表示验证或发布通过

## 1. 背景

RanaMinder 当前有 236 个需求事实、40 个用户故事、27 条全局不变量和 29 个状态机。首版应用形态已经由 [ADR-001](ADR-001-首版应用形态与后台任务运行单元.md) 确认为领域驱动的模块化单体，但应用形态本身不能回答每类业务规则由谁拥有、哪个模块可以推进状态，以及派生和执行能力能否反向改变领域事实。

本决策只收口逻辑责任和状态机写入所有权，不新增产品行为。

## 2. 已接受的逻辑模块基线

### 2.1 十二个领域模块

| 领域模块 | 核心责任 | 边界说明 |
|---|---|---|
| 身份与资料 | 身份绑定、资料门、邮箱验证、资料同步与第三值冲突 | Casdoor 账号状态仍为外部权威；本模块不管理组织关系 |
| 组织与授权 | 社团接入、Group 映射、职位模板、当前权限计算和预约关系命令 | 不拥有普通招新、联合活动或成员经历状态 |
| 普通招新 | 普通活动、报名通道、申请、部门路径、普通面试和结论 | 与联合活动保持独立对象、申请和权限域 |
| 联合活动 | 参与确认、锁定名单、联合申请、联合面试、参与社团结论和联合报名通道 | 跨社团能力只能来自联合协作域授权 |
| 邀请与成员激活 | 普通/联合邀请、常规入社邀请、接受事实和成员生效意图 | 不直接推进成员经历；实际成员状态由成员生命周期模块拥有 |
| 成员生命周期 | 成员经历、部门/职位关系、部门关系申请、任期、换届、退出和移除 | 当前关系以 Casdoor Group 回读为准，本地保存业务意图和不可变历史 |
| 动态表单 | 表单定义、不可变版本、提交、修订、字段权限和业务快照 | 动态答案不得替代身份、权限、状态、关系和审批等固定骨架 |
| 文件 | 上传、检查、隔离、绑定、授权访问、清理和正式删除执行 | 未检查文件不得进入正式提交或访问 |
| 通知 | 通知事实、收件人快照、站内信和渠道投递 | 通知和已读状态不得成为业务状态权威 |
| 纠错、审计与数据生命周期 | 事实纠错、不可变业务审计、归档、正式删除和删除清单 | 不通过覆盖历史实现纠错或删除完成假象 |
| 统计与导出 | 权限内统计、异步导出、下载授权、失权、过期和产物生命周期 | 统计和导出不得授予访问或改变源业务事实 |
| 配置与发布 | 平台/社团默认值、活动快照、学年、模板和安全开关版本 | 已发布版本不可原地覆盖；不拥有使用配置的领域状态 |

### 2.2 三个平台支撑模块

| 平台支撑模块 | 核心责任 | 禁止边界 |
|---|---|---|
| 派生入口与读模型 | 公开目录、全局个人中心和当前社团管理工作台的可重建投影 | 不保存可独立推进的业务状态，不从缓存或投影授权 |
| 后台任务与批量编排 | 到期、重试、对账、通知、导出、删除、重算和受控批量执行 | 不替代领域模块作出业务决定；每个批量单项仍调用责任领域命令 |
| 运维与可观测性 | 健康、指标、运行日志、备份恢复状态和系统外告警 | 不保存人员业务结论，不把运行日志当业务审计或权限来源 |

这些是模块化单体内部的逻辑边界，不是微服务、独立数据库、独立仓库或独立团队边界。

## 3. 二十九个状态机的唯一责任

| 唯一责任模块 | 状态机 | 数量 |
|---|---|---:|
| 身份与资料 | SRS-SM-IDN-001、SRS-SM-IDN-002、SRS-SM-IDN-003 | 3 |
| 组织与授权 | SRS-SM-ORG-001、SRS-SM-ORG-002、SRS-SM-ORG-003 | 3 |
| 后台任务与批量编排 | SRS-SM-ORG-004 | 1 |
| 普通招新 | SRS-SM-REC-001、SRS-SM-REC-002、SRS-SM-REC-003、SRS-SM-REC-004、SRS-SM-REC-005 | 5 |
| 联合活动 | SRS-SM-JNT-001、SRS-SM-JNT-002、SRS-SM-JNT-003、SRS-SM-JNT-004、SRS-SM-JNT-005、SRS-SM-JNT-006 | 6 |
| 邀请与成员激活 | SRS-SM-INV-001、SRS-SM-MEM-004 | 2 |
| 成员生命周期 | SRS-SM-MEM-001、SRS-SM-MEM-002、SRS-SM-MEM-003 | 3 |
| 动态表单 | SRS-SM-FORM-001、SRS-SM-FORM-002 | 2 |
| 文件 | SRS-SM-FILE-001 | 1 |
| 通知 | SRS-SM-NTF-001 | 1 |
| 纠错、审计与数据生命周期 | SRS-SM-AUD-001 | 1 |
| 统计与导出 | SRS-SM-EXP-001 | 1 |
| 合计 | SRS 9.1 全部状态机 | 29 |

唯一责任意味着：

1. 只有责任模块可以校验并提交对应状态转换。
2. 其他模块只能通过明确的应用命令请求转换，或消费提交后的事实；不得直接更新该模块拥有的状态。
3. 跨状态机原子联动仍严格服从 SRS 转换明细中的原子副作用，不能因模块分开而改成最终一致或反向补造。
4. 后台任务只能推进已可靠持久化且当前仍合法的业务意图；不能凭任务存在绕过状态、版本、权限或业务前置条件。
5. 派生入口、搜索、统计、缓存、通知和运维数据均不能覆盖状态机当前状态或授予访问。

## 4. 直接影响

- 数据规格必须为每个权威对象和状态标明所属模块及唯一写入责任。
- 接口契约必须标明目标模块、应用命令、授权上下文、期望状态和版本；跨模块查询不能演变为跨模块写入。
- 代码结构和依赖检查必须阻止领域模块越权修改其他模块状态，即使底层暂时使用同一 PostgreSQL 实例。
- 测试规格必须覆盖跨模块命令、错误责任模块、直接写入绕过、派生状态陈旧和后台任务越权推进等负向场景。
- 后续若增加新的强类型业务对象或状态机，必须先确定责任模块；无法归属时先评审模块边界，不得由实现者临时选择。

## 5. 非目标与未决定事项

本 ADR 不决定：

- 前后端语言、框架、ORM、包结构、类名或仓库布局；
- 数据表、Schema、外键、行级安全、模块独立数据库或迁移方案；
- API 风格、URL、RPC、消息主题、错误码或序列化格式；
- 后台任务使用数据库持久任务、消息队列或其他可靠投递机制；
- 是否为某个顶层模块建立内部子模块；
- 团队组织、代码所有者或发布审批流程。

模块内部可以根据复杂度继续分层或建立子模块，但不得改变顶层责任和状态机唯一所有权。需要合并、拆分或转移顶层责任时，必须建立新的替代 ADR，并重新检查数据、接口、安全、测试和追踪影响。

## 6. 后续评审

ADR-002 接受时，第一轮架构尚须确认 8 类事务边界是否完整且可作为数据与接口设计基线；该事项现已由 [ADR-003](ADR-003-八类事务边界基线.md) 确认。系统架构总览中的 8 个技术开放项仍未收口。ADR-002 与后续 ADR-003 均不构成代码开工批准。

## 7. 后续收口说明

2026-07-30，[ADR-011](ADR-011-内置最小观测边界.md) 按 `PRD-OPT-055` 收窄“运维与可观测性”平台模块：当前责任为脱敏运行日志、追踪关联、内置只读状态摘要和备份/恢复最近结果展示，不再承担主机机器健康、完整指标平台或系统外运维告警。12＋3 个模块数量和 29 个状态机唯一责任归属不变。

## 8. 第一轮开放项收口说明

2026-07-30，ADR-003 已确认 8 类事务边界，ADR-004 至 ADR-013 已完成其余第一轮技术决策。第 6 节的“8 个技术开放项仍未收口”只记录 ADR-002 接受时的状态；当前第一轮开放架构项为 0。12＋3 个模块及 29/29 个状态机唯一责任继续作为下游数据、接口、安全和测试设计的固定输入。

## 9. 候选方案与取舍

| 候选方案 | 优点 | 主要问题 | 结论 |
|---|---|---|---|
| 维持当前草案的 12＋3 模块与 29 个状态机归属作为首版基线 | 与 SRS 状态机明细、接口契约和既有需求事实直接对应；模块责任覆盖完整、无重复归属；是唯一经过第一轮架构评审逐项确认的归属 | 需要持续执行模块依赖规则和状态机唯一写入检查，防止退化为无边界写入 | 采用 |
| 由实现者按代码目录或临时便利自行划分归属 | 初期无需评审约束 | 模块与状态机缺乏统一语言和边界，跨模块写入、状态机越权与派生反向修改风险不可控 | 不采用 |
| 按部署单元或数据库边界划分模块（如每模块独立服务或独立 Schema） | 物理边界直观 | 与 ADR-001 的模块化单体形态和 ADR-014 的单数据库统一 Schema 决策冲突；增加跨模块一致性成本 | 首版不采用 |
| 对全部业务强制套用完整战术 DDD（聚合、领域事件、事件溯源） | 形式统一 | 简单查询、配置读取和无复杂不变量的功能不产生对应收益，过度设计增加维护成本 | 不强制；按真实复杂度决定 |

该取舍与 ADR-001 的模块化单体、ADR-014 的统一 Schema 及本 ADR 第 2 节“轻量级 DDD”表述保持一致，不构成新决策，只补齐本 ADR 决策时的方案比较记录。

## 10. 重新评估条件

出现下列任一证据时，应新建补充或替代 ADR，而不是由实现者临时调整模块或状态机归属：

- 出现新的强类型业务对象或状态机无法归属到现有 12＋3 个模块，且模块边界评审无法闭环；
- 压力、长稳、故障或恢复测试证明某模块需要独立部署、独立数据生命周期或独立发布节奏（与 ADR-001 的拆分条件联动）；
- 需求方经需求基线确认模块合并、拆分或顶层责任转移；
- 状态机唯一责任归属与 SRS 状态机转换明细或接口契约的原子副作用发生冲突。

替代决策必须重新检查数据、接口、安全、测试和追踪影响，并证明不会削弱状态机唯一所有权、事务边界和跨模块协作规则。

## 11. 结论

ADR-002 确认 12 个领域模块、3 个平台支撑模块及 29 个状态机的唯一责任归属，作为后续数据、接口、代码结构和测试设计的固定输入；模块内部允许按复杂度分层或建立子模块，但顶层责任和状态机所有权不得由实现者临时改变。该决策不构成代码开工批准。
