# ADR-009：Casdoor 统一适配与事件对账机制

> 状态：已接受  
> 决策日期：2026-07-30  
> 决策范围：系统架构后续技术决策  
> 上游基线：[系统架构总览 v1.0](系统架构总览-v1.0.md)、[ADR-002](ADR-002-逻辑模块与状态机唯一责任基线.md)、[ADR-003](ADR-003-八类事务边界基线.md)、[ADR-004](ADR-004-后台任务与可靠投递机制.md)及 [SRS 第三轮规范性明细](../specification/SRS-故障恢复安全通知与质量约束-v1.0.md)  
> 产品行为变更：否  
> 代码编写授权：已按需求方 [`GOV-CODE-WAIVER-001`](../governance/代码开工前置跳过与风险接受记录-v1.0.md) 豁免开放；本 ADR 不表示验证或发布通过

## 1. 背景与约束

`IDN-001` 至 `IDN-020` 要求 RanaMinder 使用 Casdoor 统一认证、核验账号状态、在固定字段白名单内双向同步资料，并处理并发、第三值冲突、禁用、故障和可信恢复；`ORG-001` 至 `ORG-003` 要求当前社团、部门和职位 Group 关系以 Casdoor 为权威，同时由 RanaMinder 承载业务操作入口和不可变历史；`ORG-027` 要求 Group 写入进入处理中，只有写入成功且可信回读确认后才正式生效，响应不确定时先回读再重试。

Casdoor 的实际版本、Claims/UserInfo、管理 API、事件/Webhook、服务账号权限、修改规则和分页/限流能力尚须通过真实环境验证。架构既不能假设事件绝不丢失，也不能因为能力未验证而把 Casdoor 调用散落到各领域模块或建立本地当前关系后门。

## 2. 已接受决策

1. 首版建立**统一 Casdoor 适配模块**，作为浏览器登录/回调之外所有 Casdoor 资料读取、账号状态核验、Group 查询与写入、事件接收和周期对账的唯一应用边界。领域模块和后台任务不得直接依赖具体 Casdoor SDK、HTTP 端点或响应结构。
2. 该适配边界属于模块化单体内的统一平台能力，可由独立后台运行单元执行异步任务；本决策不要求把它部署成独立微服务，也不改变身份、组织和成员模块对业务状态及历史的责任。
3. 由 RanaMinder 发起的 Casdoor 写入继续遵守 ADR-003/004：领域事务先持久化业务意图、幂等依据和任务；后台执行前重新鉴权并检查当前业务条件；对超时、断连或响应不确定结果必须先可信回读，再决定成功收口或幂等重试，不能以 HTTP 成功、事件到达或本地期望值替代可信回读。
4. 适配模块返回规范化的外部结果、当前值、版本/时间依据和错误分类；具体结果是否推进资料同步、Group 关系、任期、邀请、审批或其他状态，仍由拥有该状态机的领域模块根据上游规则决定。适配模块不得直接创造角色、权限或业务结论。
5. 对 Casdoor 外部变化采用**事件通知优先、周期性对账兜底**。经实测可用并完成真实性校验的事件用于降低发现延迟，但事件只触发可信刷新或对账，不直接作为账号、字段或 Group 当前值的最终权威快照。
6. 所有事件必须按可用事件标识和规范化对象幂等处理，并容忍重复、乱序、迟到和遗漏。事件缺失、接收失败或实际版本不提供所需事件时，周期对账仍必须能够发现账号禁用/删除、受信任资料变化、Group 人工变化和其他应同步差异。
7. 周期对账从 Casdoor 读取当前账号和 Group 关系，与本地同步状态、待处理意图及不可变历史比较。差异不得直接覆盖本地历史；应按字段权威、第三值冲突、Group 状态机、禁用和故障规则进入相应领域处置。范围、游标、分页、频率、并发、限流和全量/增量方式由集成与运维规格决定。
8. 登录、增强认证、高风险操作、故障恢复和权限敏感路径需要的实时可信核验，不得只依赖事件、周期快照或缓存。Casdoor 不可用时继续执行 `IDN-009` 和 `SRS-FAIL-001` 的最小降级及 15 分钟边界，不能由适配模块自行放宽。
9. 适配模块必须统一处理服务账号凭据、请求签名/认证、超时、限流、重试、熔断、错误脱敏、追踪和审计关联。凭据只保留在服务端，普通用户、前端和业务日志不得获得管理权限或秘密。
10. 在数据模型、接口或业务代码实施前，必须对拟支持的实际 Casdoor 版本完成强制能力验证。验证至少覆盖登录与 Claims、UserInfo/账号状态、Group 层级与成员读写、服务账号最小权限、写后可见性、事件能力、禁用/删除、MFA、`auth_time`、限流、分页及人工修改场景；未验证能力不得写成已存在接口。

## 3. 候选方案与取舍

| 候选方案 | 优点 | 主要问题 | 结论 |
|---|---|---|---|
| 统一适配＋事件优先＋周期对账＋写后可信回读 | 变化发现较快；事件遗漏可修复；外部协议集中；与结果不确定和恢复规则一致 | 需要维护事件幂等、对账游标、差异状态和限流，实施复杂度高于单一路径 | 首版采用 |
| 统一适配但只依赖事件/Webhook | 延迟低，持续轮询请求少 | 事件可能重复、乱序、遗漏或不覆盖所有对象；实际版本能力尚未验证，无法作为正确性唯一保障 | 不采用 |
| 统一适配但只做周期轮询 | 不依赖事件能力，控制路径直接 | 禁用和外部变化发现延迟较高；大规模账号和 Group 对账负载更大 | 作为事件不可用时的可运行退化，不作为首选完整方案 |
| 各领域模块直接调用 Casdoor | 初始封装较少 | 协议、凭据、错误、重试和回读逻辑散落；难以统一验证、升级、降级和审计 | 不采用 |

## 4. 对后续文档的约束

- Casdoor 集成契约必须记录实际支持版本、能力验证证据、规范化对象与错误、读写语义、事件真实性、重复/乱序/遗漏、对账范围、限流和服务账号最小权限。
- 数据模型必须区分 Casdoor 当前值的可信观测、本地业务意图、同步尝试、冲突快照、Group 待处理状态、不可变历史、事件收件和对账游标，不能让同步技术记录反向授予权限。
- 接口契约必须为写入、回读、对账和人工重试定义幂等、版本、超时、结果不确定、处理中和最终收口，不得把适配器错误直接冒充业务拒绝或成功。
- 安全设计必须覆盖回调/事件伪造、重放、服务账号越权、秘密泄露、SSRF/目标地址配置、Claims 信任、普通用户 Casdoor 修改规则绕过及日志脱敏。
- 测试规格必须覆盖写成功响应丢失、写失败、读回旧值/新值/第三值、重复/乱序/迟到/遗漏事件、轮询分页变化、限流、禁用账号、Group 人工修改、Casdoor 故障与恢复对账。
- 运维设计必须监控事件延迟与失败、对账游标和陈旧度、差异积压、写入重试、读回结果、限流、服务账号错误和降级窗口，并支持从事件路径退化到对账路径。

## 5. 不受本决策影响的边界

本 ADR 不改变 Casdoor 的账号与当前 Group 权威、资料字段权威与冲突裁决、15 分钟故障白名单、禁用立即生效、Group 写入处理状态、历史保留、服务端逐请求授权或无本地放权后门等产品行为，不新增需求或 `PRD-OPT` 编号。

本 ADR 不决定：

- Casdoor 的具体版本、部署方式、SDK、端点、Webhook 名称、事件载荷、Claims 字段或分页协议；
- 事件是否覆盖全部对象，以及实际部署最终使用事件＋对账还是因能力不足退化为对账＋实时回读；
- 对账频率、批量大小、游标结构、重试间隔、超时、限流参数和告警阈值；
- 具体表、字段、消息格式、API、服务账号名称和秘密管理产品；
- 前后端语言、ORM、仓库结构、观测/告警产品和生产高可用拓扑。

## 6. 重新评估条件

出现以下任一情况时，可以创建补充或替代 ADR：

- 实际 Casdoor 版本不提供可验证事件能力，需要长期采用对账与实时读回；
- 事件或对账接口无法在最小权限下取得所需账号、字段和 Group 当前值；
- 目标规模下对账无法满足同步时延、限流或容量要求；
- Casdoor 升级改变事件、字段、认证、Group 或管理 API 语义；
- 安全测试发现事件入口、服务账号或适配边界不能满足信任与隔离要求。

重新评估可以调整技术适配方式，但不得降低 Casdoor 当前权威、写后可信回读、差异可见、故障失败关闭、幂等恢复和无本地后门等既有边界。

## 7. 结论

ADR-009 收口“Casdoor 适配方式”开放项。首版使用模块化单体内统一 Casdoor 适配边界，写入采用持久意图、幂等执行和可信回读，外部变化采用经验证事件优先与周期对账兜底；实际接口与事件能力继续作为首批强制技术验证项。该决策为集成、数据、接口、安全、测试和运维设计提供边界，不构成具体 SDK/API 选择或代码开工批准。

## 8. 后续收口说明

2026-07-30，[ADR-011](ADR-011-内置最小观测边界.md) 收窄首版观测范围。Casdoor 事件、对账、写入和读回的最近结果、更新时间、积压与最近异常进入内置状态和脱敏日志；对账频率、批量和重试参数仍由后续规格决定，但不再要求外部指标导出、告警阈值或系统外运维告警。Casdoor 权威、事件优先、周期对账兜底和写后可信回读结论不变。

## 9. `DATA-Q-013` 后续验证结论

2026-07-30，数据设计评审确认首版精确兼容学校既有 Casdoor `v3.108.0`；官方源码核验基线为标签 `v3.108.0`、提交 `a4a5184d0b5c4a570f0cd07283ff928f56d81548`。该版本虽提供可配置 Webhook、静态请求头、投递记录、重试和重放，但未建立接收方可验证的逐次消息签名、时间戳、nonce 和稳定外部事件 ID 契约，故不满足本 ADR 第 2 节所称“经实测可用并完成真实性校验的事件”条件。

首版 `v3.108.0` 兼容模式因此采用本 ADR 已允许的退化路径：周期全量对账、每次外部写后的定向读回，以及登录、增强认证、高风险操作和权限敏感请求的实时读回构成正确性路径；Webhook 默认关闭，部署方启用时也只能作为受 HTTPS、独立静态秘密和限流保护的非权威刷新提示，不能直接改变业务状态、关系或权限。外部事件 ID、签名、单调版本、分页快照游标和独立 Group UUID 均不得作为数据或接口必备条件。

该结论是 ADR-009 既有“事件能力不足时退化到对账＋实时读回”边界的具体落地，不补充或替代本 ADR。学校真实实例仍须完成运行指纹、Claims/UserInfo、Group 读写、最小权限、分页、限流、写后可见性、禁用/删除、MFA、`auth_time` 和人工修改场景验证；学校补丁、升级或实测差异只有在改变统一适配、Casdoor 当前权威、写后可信读回、失败关闭或恢复边界时，才触发补充/替代 ADR。
