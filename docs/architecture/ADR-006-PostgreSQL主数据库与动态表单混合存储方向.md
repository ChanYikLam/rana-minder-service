# ADR-006：PostgreSQL 主数据库与动态表单混合存储方向

> 状态：已接受  
> 决策日期：2026-07-30  
> 决策范围：系统架构后续技术决策  
> 上游基线：[系统架构总览 v1.0](系统架构总览-v1.0.md)、[ADR-002](ADR-002-逻辑模块与状态机唯一责任基线.md)、[ADR-003](ADR-003-八类事务边界基线.md)、[ADR-005](ADR-005-数据隔离与选择性RLS.md)、[SRS v1.0](../specification/SRS-v1.0.md)及[SRS 第三轮规范性明细](../specification/SRS-故障恢复安全通知与质量约束-v1.0.md)

> 代码编写授权：已按需求方 [`GOV-CODE-WAIVER-001`](../governance/代码开工前置跳过与风险接受记录-v1.0.md) 豁免开放；本 ADR 不表示验证或发布通过

## 1. 背景与约束

需求事实已经在 `NFR-002`、`NFR-004` 和 `NFR-007` 中把 PostgreSQL 纳入备份恢复、参考容量和官方部署基线，[ADR-005](ADR-005-数据隔离与选择性RLS.md) 又确认普通社团业务表选择性使用 PostgreSQL RLS。数据库重新选型评审进一步比较了 PostgreSQL 与 MariaDB，重点核验二者承载 RanaMinder 动态表单的适配度。

动态表单不是无模式业务数据。`FORM-001` 至 `FORM-012` 要求固定业务骨架与动态字段分离，发布版本不可覆盖，稳定字段标识跨版本迁移，正式提交和重新提交形成可还原快照，字段权限只能收紧上游授权，附件及核心业务对象保持独立生命周期。数据库选择必须支持这些规则，但不能替代表单引擎的服务端校验、授权、状态机和版本语义。

## 2. 已接受决策

1. 首版继续使用 **PostgreSQL 作为本地权威主数据库**；MariaDB 不作为首版默认或并行支持的主数据库。
2. 动态表单采用**关系骨架与 JSONB 混合存储方向**。用户、学号、社团、部门、职位、业务状态、审批结果、任期、邀请、权限、操作时间、表单版本关系及其他固定业务骨架必须保持强类型关系建模，不得埋入任意 JSONB 后失去引用完整性或状态机约束。
3. 发布后的表单定义与版本必须不可变；动态答案按其稳定字段标识、表单版本和提交修订保存可还原快照。JSONB 是动态答案快照的首选承载能力，不等于允许覆盖历史版本、跳过字段类型校验或把客户端 JSON 直接作为可信业务事实。
4. 附件、人员、社团、部门及其他具有独立权限、生命周期或引用完整性要求的对象必须保持独立关系和受控引用；JSONB 中的显示值、名称或对象编号不能成为这些对象的权威副本。
5. JSONB 的通用查询、包含和数组能力可服务低频或字段集合不稳定的动态筛选。需要稳定范围查询、排序、统计或容量保障的高频字段，可以在后续数据规格中选择表达式索引、受控关系投影或其他可重建读模型；不得无证据地为每个自定义字段建立永久物理列。
6. JSONB 和数据库 RLS 都不自动实现动态字段权限。应用层必须在当前用户、对象、操作、作用域、状态和表单版本授权之后，按字段规则生成读取、导出和修改结果；内部评价或管理字段继续使用独立表单或记录。
7. PostgreSQL JSONB、GIN 或表达式索引只确定能力方向。具体 Schema、表、列、索引、分区、查询、锁、ORM 映射、迁移步骤和容量阈值必须在数据模型、性能验证及后续规格中决定。

## 3. 候选方案与取舍

| 候选方案 | 优点 | 主要问题 | 结论 |
|---|---|---|---|
| PostgreSQL＋关系骨架＋JSONB 动态答案 | 保留强关系约束；原生 JSONB 查询、JSONPath、GIN 和表达式索引适合字段集合随表单版本变化；与选择性 RLS 及既有部署/恢复基线一致 | 需要明确关系与 JSONB 边界；范围排序仍可能需要针对性索引或投影；字段权限不能交给 JSONB | 首版采用 |
| MariaDB＋关系骨架＋JSON 动态答案 | 保存、回显、JSON 函数和 `JSON_TABLE` 能覆盖基本表单能力；团队熟悉时运维成本可能较低 | JSON 为文本类型别名；高效路径查询通常更依赖生成列和定向索引，面对各社团、各版本不断变化的字段会增加结构演进负担；还需替代既有 RLS 方案并重开恢复/部署基线 | 首版不采用 |
| PostgreSQL＋全部动态答案关系行化 | 单字段类型和普通索引可以显式表达，适合少数受控投影 | 完整提交还原、重复子表、跨字段统计和版本迁移会引入大量行、连接及聚合复杂度 | 不作为唯一存储模型；可按证据用于受控投影 |
| 全部业务数据 JSONB 化 | 初始结构灵活、写入模型表面统一 | 削弱核心对象引用、唯一性、事务、状态和授权约束，与 `FORM-001` 的固定骨架要求冲突 | 排除 |

技术能力判断参考 PostgreSQL 官方的 [JSON 类型与 JSONB 索引](https://www.postgresql.org/docs/current/datatype-json.html)及 [JSON 函数与 JSONPath](https://www.postgresql.org/docs/current/functions-json.html)，以及 MariaDB 官方的 [JSON 类型](https://mariadb.com/docs/server/reference/data-types/string-data-types/json)、[`JSON_TABLE`](https://mariadb.com/docs/server/reference/sql-functions/special-functions/json-functions/json_table)和[生成列](https://mariadb.com/docs/server/reference/sql-statements/data-definition/create/generated-columns)说明。外部产品能力仍须在首批技术验证时以实际选定版本复核。

## 4. 对后续文档的约束

- 数据模型必须逐类标明哪些内容属于固定关系骨架、动态定义、不可变发布版本、答案修订、独立附件/对象引用及可重建查询投影，并证明历史提交可以按原版本还原。
- 数据规格必须定义稳定字段标识、值类型、空值、条件隐藏、不兼容类型变更、并发修订、JSONB 结构校验和高频字段索引提升规则；本 ADR 不预先指定物理实现。
- 安全设计必须证明 RLS 行级隔离与应用字段级授权各自生效，JSONB 查询、统计、导出和历史读取不能绕过当前对象权限或字段收紧规则。
- 测试规格必须覆盖跨版本迁移、旧提交还原、重复子表、对象引用校验、字段权限、隐藏答案不随本次提交、JSONB 查询语义、索引退化和容量边界。
- 部署与恢复手册必须继续承接 PostgreSQL 的事务日志、备份、恢复、升级和兼容检查要求，并验证动态答案、关系骨架与附件引用在恢复后保持一致。

## 5. 不受本决策影响的边界

本 ADR 不改变动态表单的字段类型、角色权限、版本迁移、本人回看、附件访问、归档、纠错、删除或导出行为，不新增任何需求事实或 `PRD-OPT` 编号。

本 ADR 不决定：

- 具体表名、字段名、JSONB 文档结构、主外键、索引、分区和迁移；
- ORM、查询框架、前后端语言、API 风格和仓库结构；
- 搜索引擎、独立缓存、对象存储、文件检查/预览、Casdoor 适配、观测产品和生产高可用拓扑；
- 是否把某个高频动态字段提升为表达式索引、关系投影或派生读模型；
- PostgreSQL 的具体版本、扩展、托管产品或部署供应商。

## 6. 重新评估条件

出现以下任一情况时，可以创建替代 ADR 重新评估，但不能由实现静默切换数据库：

- 实际版本和目标规模验证证明，JSONB 加受控索引/投影仍无法满足已确认的性能、恢复或运维约束；
- 开源部署环境无法稳定获得满足安全更新、备份恢复和兼容要求的 PostgreSQL；
- 替代数据库能够同时证明事务、引用完整性、动态查询、隔离、升级、RPO/RTO 和迁移成本更优；
- 产品范围发生经需求基线确认的重大变化，使动态表单不再需要当前版本、查询或历史能力。

替代 PostgreSQL 时，必须同步重开 `NFR-002`、`NFR-004`、`NFR-007`、ADR-005 及所有依赖 PostgreSQL 能力的后续数据、安全、部署和测试结论。

## 7. 结论

ADR-006 在重新比较 MariaDB 后确认 PostgreSQL 继续作为首版权威主数据库，并固定动态表单采用关系骨架与 JSONB 混合存储的能力方向。它补足已有需求与 ADR-005 的实现选择依据，但不收口系统架构总览第 13.2 节列出的 6 个开放项，也不构成数据模型完成或代码开工批准。
