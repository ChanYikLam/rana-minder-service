# ADR-010：单文件外置配置与 Docker 只读挂载

> 状态：已接受

## 1. 背景与约束

RanaMinder 的官方部署目标是：部署者取得正式镜像和部署文件后，填写自己的 Casdoor、PostgreSQL、对象存储、邮件、域名和学校配置，即可通过 Docker 完成单机部署；同一套程序还必须支持后续拆分部署，不能把真实学校、账号或秘密打入镜像和源码。`NFR-007`、`NFR-008` 及 `SRS-NFR-030` 至 `SRS-NFR-039` 已冻结这些部署和开源边界。

强制部署 Vault 或云秘密管理服务会提高首版私有部署门槛；把大量配置全部转成环境变量又不利于人工填写、审阅和版本升级。需求方确认首版可以在部署项目目录集中填写一个本地配置文件，但真实内容不得因此进入代码仓库、发布包或镜像。

## 2. 已接受决策

1. 官方部署材料提供 Docker Compose 或等效单机编排文件，以及一份**不包含真实秘密的示例配置**。部署者在部署项目目录中复制并填写一个本地 `config.yaml` 或等效单文件，再启动指定版本的 RanaMinder 镜像。
2. 本地配置文件可以集中包含普通运行配置和数据库、Casdoor、对象存储、邮件、签名/加密等秘密。首版不强制把每个秘密拆成单独文件，也不强制部署 Vault、云 Secret Manager 或其他外部秘密管理服务。
3. 真实配置文件位于部署宿主机的项目目录中，但在信任边界上属于**镜像外运行配置**：不得提交到 RanaMinder 源码仓库，不得打入容器镜像，不得进入官方部署包、示例、测试夹具、截图、日志或公开诊断材料。
4. 官方仓库或发布材料只保留字段结构完整、秘密留空或使用明确无效占位符的示例配置；仓库忽略规则必须排除约定的真实配置文件。仅依赖忽略规则仍不免除发布前秘密扫描和人工复核。
5. Docker 部署将本地配置文件以只读方式挂载到容器内的固定受控位置。应用不得覆盖、补写或通过管理页面下载该文件；容器重建、镜像升级和应用扩容不得要求把真实配置复制进镜像层。
6. 部署文档必须要求使用操作系统文件权限限制部署管理员和运行账号之外的读取，并防止配置进入公开备份、普通支持包和无保护的文件同步。拥有宿主机管理员权限者仍属于部署信任边界，本 ADR 不声称能够对其隐藏秘密。
7. 应用通过统一配置读取边界加载并校验配置，业务模块不得各自扫描任意路径、重复解析秘密或把原值写入错误信息。正式环境缺少必要配置、仍使用明确无效占位符或结构无法解析时，不得以半配置状态继续提供业务服务。
8. 日志、追踪、健康信息、启动摘要和错误响应只能说明配置项是否存在、是否合法及来自哪个受控配置入口，不得输出密码、令牌、私钥、访问密钥或可还原秘密的派生值。
9. 发布说明必须列出新增、废弃、重命名、默认值变化和需要人工迁移的配置项；升级前保留受保护的现行配置副本并执行兼容检查。具体配置版本、迁移和回滚方式进入部署运维规格。
10. 未来若部署者需要容器 Secrets、Vault、操作系统凭据库或云秘密服务，可以通过补充 ADR 扩展统一配置读取边界；首版业务模块不得以直接读取项目目录文件的方式阻止这种演进。

## 3. 候选方案与取舍

| 候选方案 | 优点 | 主要问题 | 结论 |
|---|---|---|---|
| 部署目录单个配置文件＋只读挂载 | 符合拉取镜像、填写配置、Docker 部署的使用方式；配置集中、易审阅；不增加外部秘密服务 | 单文件泄漏会暴露全部秘密；必须严格控制仓库、文件权限、日志、诊断和备份 | 首版采用 |
| 全部使用环境变量 | 容器平台普遍支持，不需要解析秘密文件 | 配置项多时填写与审阅困难；可能进入编排输出、进程诊断或故障信息 | 不作为官方单机默认；后续可作为兼容入口评估 |
| 每个秘密单独只读文件 | 泄漏和轮换范围更细，接近容器 Secrets 模型 | 首版文件数量、挂载和文档复杂度较高 | 首版不强制 |
| 强制 Vault 或云秘密管理服务 | 轮换、审计和集中治理能力较强 | 增加部署依赖和学习成本；不适合所有高校私有环境 | 首版不强制 |
| 把真实配置提交仓库或打入镜像 | 拉取后无需额外文件 | 真实秘密进入版本历史或镜像层，无法安全开源和轮换 | 排除 |

## 4. 对后续文档的约束

- 配置规格必须区分普通配置和秘密字段，定义配置结构、必填条件、正式/开发环境差异、无效占位符、兼容版本及脱敏展示规则。
- 部署文档必须提供示例配置、复制填写流程、只读挂载、文件权限、忽略规则、启动前检查、升级备份和配置迁移步骤，并明确“项目目录内”不等于“可提交仓库”。
- 安全设计必须覆盖路径穿越、符号链接/挂载替换、过宽文件权限、日志与异常回显、诊断包、镜像构建上下文、Git 历史、备份和支持人员访问。
- 测试规格必须验证镜像和正式发布物无真实秘密、缺少/占位秘密时正式启动失败、配置只读、日志脱敏、镜像升级保留宿主机配置，以及不同虚构学校配置无需修改源码即可运行。
- 运维规格必须说明配置变更是热加载还是重启生效、凭据轮换顺序、回滚限制、文件丢失恢复和配置副本的安全保管方式；本 ADR 不提前决定这些机制。

## 5. 不受本决策影响的边界

本 ADR 不改变认证、授权、数据隔离、文件访问、邮件、审计、故障恢复或其他产品行为，不新增需求或 `PRD-OPT` 编号。

本 ADR 不决定：

- 最终配置字段名、完整 YAML Schema、默认值、文件名和容器内绝对路径；
- 是否支持环境变量覆盖、配置分层、热加载及覆盖优先级；
- Vault、容器 Secrets、云秘密服务或其他未来提供器；
- 前后端语言、配置框架、镜像构建工具和容器编排产品；
- 日志、指标、追踪、运维看板、系统外告警和生产高可用实现。

## 6. 重新评估条件

出现以下任一情况时，可以创建补充或替代 ADR：

- 多节点、多环境或集中轮换使单文件配置无法安全管理；
- 安全审计要求凭据集中托管、访问审计或不落宿主机明文；
- 配置数量、组织或升级兼容性使单文件人工维护错误率不可接受；
- 容器平台提供更安全且不显著增加部署门槛的标准秘密机制；
- 发生配置泄漏、误提交、错误备份或诊断输出事故。

替代决策不得把真实秘密重新放入源码、镜像、公开发布材料、日志或客户端，也不得破坏拉取同一程序后通过外部配置完成单机和拆分部署的边界。

## 7. 结论

ADR-010 确认官方单机部署采用“部署项目目录内单个本地配置文件＋Docker 只读挂载”的首版方式，允许在该受保护文件中集中填写普通配置和秘密，但禁止真实内容进入仓库、镜像和公开发布物。该决策只收口配置与秘密部署方式；观测和系统外告警仍受 `NFR-006` 约束并保持开放，不构成代码开工批准。
