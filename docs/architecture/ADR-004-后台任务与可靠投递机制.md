# ADR-004：后台任务与可靠投递机制

> 状态：已接受  
> 修订状态：第 4 节运维观察中“应用外告警”要求已按 `PRD-OPT-055` 由 [ADR-011](ADR-011-内置最小观测边界.md) 收窄，改为内置只读状态页与脱敏日志承接（详见第 8 节）  
> 决策日期：2026-07-30  
> 决策范围：系统架构后续技术决策  
> 上游基线：[系统架构总览 v1.0](系统架构总览-v1.0.md)、[ADR-001](ADR-001-首版应用形态与后台任务运行单元.md)、[ADR-003](ADR-003-八类事务边界基线.md)及 [SRS v1.0](../specification/SRS-v1.0.md)  
> 产品行为变更：否  
> 代码编写授权：已按需求方 [`GOV-CODE-WAIVER-001`](../governance/代码开工前置跳过与风险接受记录-v1.0.md) 豁免开放；本 ADR 不表示验证或发布通过

## 1. 背景与约束

RanaMinder 的 Casdoor 写入与回读、通知投递、文件检查与预览、导出、截止任务、正式删除、派生重算和对账都需要脱离 Web 请求生命周期可靠执行。[ADR-001](ADR-001-首版应用形态与后台任务运行单元.md) 已确认后台任务可以作为独立运行、部署和扩容的执行单元；[ADR-003](ADR-003-八类事务边界基线.md) 已确认外部副作用开始前，业务意图、任务、幂等依据和必要状态必须可靠持久化。

本 ADR 只决定首版可靠任务的权威来源、领取语义及未来消息基础设施的边界，不新增任何用户可见行为，也不选择具体任务库、消息产品或物理表结构。

主要上游来源：`NFR-003`、`NFR-006`、`SRS-FAIL-003` 至 `SRS-FAIL-013`、`SRS-NFR-004`、`SRS-NFR-015`、`SRS-NFR-018`、`SRS-NFR-030`、`SRS-NFR-031`，以及 29 个状态机转换中的任务、租约、幂等、回读和恢复约束。

## 2. 已接受决策

1. 首版采用**权威业务库中的持久任务/事务发件箱＋独立后台执行单元**作为后台任务与可靠投递机制。
2. 当已确认事务边界要求业务事实与执行意图同成同败时，两者必须在同一本地数据库事务中持久化。不得先提交业务、再依赖内存回调、进程内队列或一次普通网络调用补建任务。
3. 持久任务记录是待执行意图、领取状态、尝试过程和最终收口的技术权威。由哪个领域模块拥有业务意图和最终业务解释，继续遵守 [ADR-002](ADR-002-逻辑模块与状态机唯一责任基线.md)；后台任务与批量编排模块只提供领取、租约、调度和执行编排能力，不得反向拥有其他模块的领域状态。
4. 后台执行单元通过可竞争租约领取任务，并按**至少一次执行**设计。多个执行单元并发、执行中崩溃、租约过期和恢复重放都可能导致同一任务再次被领取，因此不能假设技术层天然“恰好一次”。
5. 每份业务意图和每个外部操作使用稳定幂等依据。重复领取、客户端重试、人工重试、外部回调和恢复重放必须汇聚到同一业务意图，最终至多形成一份有效业务结果。
6. 执行前必须按任务类型重新检查适用的对象状态、版本、当前权限或系统任务授权、安全开关和业务前置条件。过期、失权、已取消、已替换、已删除或版本落后的任务不得复活旧业务。
7. 外部结果不确定时必须先进行可信回读或查询，再决定成功、重试、补偿或异常收口；不得用盲目重复调用换取表面成功。
8. 首版不把独立消息队列作为业务正确性所必需的基础设施。若未来引入消息队列，它默认只承担唤醒、分发或削峰，消费者仍须回到持久任务记录领取并核验；队列确认不能替代业务完成状态。
9. 数据、接口和运维设计必须能区分待执行、执行中、可重试失败、结果不确定、不可自动重试或需人工处置以及已完成等必要语义，但具体状态名、字段和停止条件留待下游规格决定。

## 3. 候选方案与取舍

| 候选方案 | 优点 | 主要问题 | 结论 |
|---|---|---|---|
| 权威业务库持久任务/事务发件箱＋租约执行 | 与本地业务事务自然衔接；部署组件少；任务可查询、审计和恢复；适合开源单机与拆分部署 | 必须控制轮询、竞争和积压对数据库的影响；极高吞吐与复杂广播能力有限 | 首版采用 |
| 事务发件箱＋独立消息队列作为必经分发路径 | 吞吐、路由、广播和消费者隔离能力更强 | 仍需发件箱解决数据库与队列的一致性；增加关键基础设施、重复状态和恢复复杂度；当前缺少必要性证据 | 首版不作为必需依赖；满足重新评估条件时可引入 |
| 仅依赖消息队列或内存任务 | 表面实现直接 | 无法与本地业务事实形成可靠原子边界；进程或消息故障可能静默丢失业务意图 | 不采用 |
| 在用户请求内同步完成全部外部调用 | 流程表面简单 | 长调用、超时和不确定结果可能产生假成功、重复副作用或请求资源耗尽 | 已由 ADR-003 排除 |

## 4. 实现面对的约束

- 数据模型必须表达任务与来源业务意图的稳定关联、适用作用域、源对象及版本、幂等依据、租约、尝试、可执行时间、脱敏失败信息和最终结果引用；是否使用通用表、模块专用表或组合方式由数据规格决定。
- 接口契约必须延续已受理、处理中、失败、结果不确定和最终完成的既有语义，并定义重复请求如何返回同一业务意图；本 ADR 不决定 HTTP 状态码或响应结构。
- 安全设计必须为后台执行身份实施最小权限，证明领取任务不能绕过领域模块、当前作用域、状态、字段范围或安全开关。
- 测试规格必须覆盖业务提交前后崩溃、重复领取、双执行单元竞争、租约过期、外部成功但本地记录前崩溃、迟到响应、回读、停止重试、恢复重放和消息加速层丢失等场景。
- 运维设计必须能够观察不同任务类型的积压、等待时间、租约、尝试、结果不确定、人工处置和最终收口，并对持续失败提供应用外告警。
- 单机部署可以在同一主机运行应用与后台进程；拆分部署可以按任务类型和积压独立扩展后台执行单元。所有运行角色继续使用同一兼容发布版本和领域规则。

## 5. 不受本决策影响的边界

本 ADR 不改变需求事实、PRD、SRS、29 个状态机、12＋3 个模块责任、8 类事务边界或 13 条故障恢复规则，也不把后台执行单元变成微服务、独立仓库、独立数据库或独立产品。

本 ADR 不决定：

- PostgreSQL Schema、表、字段、索引、分区、锁、隔离级别或行级安全；
- 使用何种任务框架、ORM、SQL 写法或进程管理方式；
- 轮询周期、租约时长、并发数、优先级、重试次数、退避、超时或人工处置阈值；
- API 风格、消息格式、主题划分或供应商产品；
- 前后端语言与框架、缓存、搜索、对象存储、Casdoor 具体适配、观测产品或生产高可用拓扑。

## 6. 重新评估条件

出现下列任一可复现证据时，可以评估引入独立消息基础设施：

- 持久任务的领取、竞争或状态更新持续影响权威数据库的业务请求目标，且索引、分区、批量领取和执行单元扩容仍不能满足；
- 已确认吞吐、延迟、广播、跨语言消费者或故障隔离目标无法由数据库持久任务满足；
- 压力、长稳、故障或恢复测试证明当前机制无法达到已确认的 SRS 非功能规则；
- 运维能力能够承担新增消息基础设施的备份、升级、监控、安全和故障恢复责任。

引入消息队列必须创建补充或替代 ADR，明确其是否只是加速层。只要本地业务事实与外部执行意图仍需同成同败，可靠持久化边界和幂等收口就不得被队列确认替代。

## 7. 结论

ADR-004 收口“后台任务与可靠投递机制”开放项。首版以权威业务库持久任务为执行权威，以独立后台运行单元进行可竞争租约领取和至少一次执行，并通过幂等、当前条件复核、可信回读和恢复重放取得至多一份有效业务结果。该决策可以指导后续数据、接口、安全、测试和运维设计，但不构成代码开工批准。

## 8. 后续收口说明

2026-07-30，[ADR-011](ADR-011-内置最小观测边界.md) 按 `PRD-OPT-055` 取消应用外运维告警要求。本 ADR 的任务状态、积压、尝试、结果不确定和人工处置可见性继续有效，并通过内置只读状态页和脱敏日志承接；不得再据本 ADR 创建系统外告警任务。可靠投递、幂等和恢复结论不变。
