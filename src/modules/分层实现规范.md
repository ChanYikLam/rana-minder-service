# modules · 模块分层实现规范

> 更新日期：2026-08-12
> 目录位置：src/modules/
> 权威依据：[系统架构总览 v1.0](../../docs/architecture/系统架构总览-v1.0.md)（§5.1 分层、§5.4 依赖方向）、[ADR-002](../../docs/architecture/ADR-002-逻辑模块与状态机唯一责任基线.md)、[ADR-013 §2.6](../../docs/architecture/ADR-013-Vue与NestJS首版应用技术栈.md)、[接口契约 v1.0](../../docs/specification/接口契约-v1.0.md)

## 核心职责

`src/modules/` 承载全部 15 个逻辑模块（12 领域模块 + 3 平台支撑模块，ADR-002 §2.1/§2.2）。每个模块内部使用**统一四层结构**：`interfaces/`、`application/`、`domain/`、`infrastructure/`；`application/` 下再分 `commands/` 与 `queries/`，`domain/` 下再分 `models/`、`services/`、`state-machines/`。本文统一定义这 6 类层目录的准入规则、依赖方向与命名约定，供全部 15 个模块共同遵守，避免各模块自行发明分层习惯。

关键不变量：

- 依赖方向单向：`interfaces → application → domain`，`infrastructure` 只被 `application` 和 `interfaces` 调用，任何层不得反向依赖。
- `domain/` 是纯规则层：不依赖框架、数据库、浏览器、邮件、对象存储或具体队列产品。
- 跨模块写入只能经目标模块的应用命令；禁止共享表更新或直接修改他域状态制造隐式耦合（架构总览 §5.4）。
- 一个状态机只由其责任模块写入（29 个状态机唯一责任归属，架构总览 §5.3）。

## 关键组件

| 层目录 | 允许内容 | 禁止内容 | 组件类型命名 |
|---|---|---|---|
| `interfaces/` | HTTP Controller、DTO、路由与请求适配、入参校验 | 授权结论、业务决策、直接访问数据库/缓存 | `XxxController`（后缀 Controller） |
| `application/commands/` | 应用命令用例：建立授权上下文、调用领域规则、划定事务边界、编排外部任务 | 领域规则实现、直接 SQL、外部 SDK 调用 | `XxxUseCase` / `XxxCommand`（后缀 UseCase/Command） |
| `application/queries/` | 查询用例：组装授权上下文、派生查询、只读返回 | 写业务状态、绕过状态机、把外部成功当本地成功 | `XxxQueryService` / `XxxQuery` |
| `domain/models/` | 领域模型、值对象、聚合根、实体定义 | 框架依赖、持久化细节、外部 SDK | `Xxx`（领域对象名）/ `XxxModel` |
| `domain/services/` | 纯规则服务：不变量、拒绝条件、派生与校验规则 | 持有连接/客户端/日志实例，读写存储 | `XxxRules` / `XxxPolicy` / `XxxDomainService` |
| `domain/state-machines/` | 状态机定义：状态枚举、转换门、收口分类（纯规则） | 副作用、外部调用、持久化 | `XxxStateMachine` |
| `infrastructure/` | 仓库实现、持久化访问、外部适配调用（Casdoor/S3/邮件）、任务登记 | 业务结论、状态机定义、自行决定录取/任免/权限结果 | `XxxRepository` / `XxxAdapter` / `XxxWriter` |

## 使用与准入规则

- **interfaces**：唯一面向 HTTP 的入口；Controller 必须执行当前服务端授权校验（在应用能力边界），不保存可覆盖领域对象的页面状态；DTO 与入参校验使用 `common/RuntimeValidators` 原语。平台支撑模块 job 为例外：其 interfaces 层无 HTTP 入口，承载任务类型注册与处理器装配（`TaskProcessorRegistry`），不视为 Controller。
- **application**：命令与查询用例以目标对象为锚点建立授权上下文；命令按接口契约 8 类事务边界（IFC-TX-001~008）划定本地原子提交；需要外部副作用时先持久化意图并登记 job 任务，不直接异步写库。
- **domain**：承载业务对象、状态机、不变量与拒绝原因；不依赖浏览器、邮件、对象存储或具体队列产品；可独立单测；状态枚举与 `common/StateMachineConstants` 保持一致，不二次定义。
- **infrastructure**：实现领域端口与外部适配；不携带业务结论；外部结果统一使用 `ExternalResult<T>` / `ExternalError` 公共类型（见 `src/adapters/基础设施适配文档.md`）。
- **跨模块协作**：领域模块之间的调用经目标模块应用命令（如 recruitment 经 `InvitationPort`）；平台模块 job 只编排已获授权且已持久化的业务意图，每次取得租约和提交结果时仍执行状态/版本/权限复核。
- **命名约定**：类名 PascalCase，组件类型后缀统一（Controller/UseCase/StateMachine/Repository/Adapter/Rules/Policy/Port）；文件名与类名一致（`xxx.controller.ts`、`xxx.use-case.ts`、`xxx.state-machine.ts`）。跨模块调用端口使用 `XxxPort` 后缀（如 `InvitationPort`），定义在消费方模块边界。

## 核心逻辑摘要

- **依赖方向**：交互入口只调用应用用例，不能直接写数据库、对象存储或 Casdoor；应用用例组织命令/查询、建立授权上下文、调用领域规则、划定事务、编排外部任务；领域层不依赖任何框架或外部产品。
- **事务与状态机**：本地业务事实、不可变历史、关键审计与必要任务意图在同一本地事务提交（IFC-TX-001）；Casdoor 外部写入、邮件、文件处理等按对应事务类别提交后可恢复执行；状态机转换只能由责任模块提交，其他模块只能经应用命令请求转换。
- **授权与安全**：每次受保护请求执行当前服务端授权，缓存命中不得跳过用户、对象、操作、作用域和状态检查；拒绝条件按接口契约映射 IFC-ERR-001~016 错误分类；错误对象与运行日志不得携带报名正文、内部评语、附件内容、完整联系方式、令牌或密钥。
- **脱敏与审计**：关键成功、失败、权限和特权访问必须审计，关键审计失败时业务不得成功（AUD-003）；业务幂等键与追踪编号不得混同。

## 典型调用链

HTTP 请求 → `interfaces` Controller（入参校验、当前授权判定）→ `application/commands` 应用命令（建立授权上下文、划定 IFC-TX 事务边界）→ `domain/services` 纯规则校验（不变量、拒绝条件）→ `domain/state-machines` 状态机推进 → 本地事务原子提交（业务事实＋历史＋关键审计＋通知事实＋任务意图）→ `infrastructure` 仓库持久化；需要外部副作用时经 job 模块登记任务。后台任务侧：job 领取租约 → 复核前置条件 → 调用责任领域模块应用命令 → 执行外部写入（Casdoor/S3/邮件）→ 可信回读收口 → 更新任务状态（SRS-SM-ORG-004）。

## 模块 README 统一模板

每个模块 README 必须遵循本节定义的统一模板，保证 15 个模块文档结构与质量一致。模板采用「必填段＋按需段」混合式：必填段是信息底线，所有模块必须具备；按需段「已有则保留、不强求新增」，避免为凑结构破坏已成熟的文档。

### 头块（标题与元信息）

标题统一为「`# 模块类型 · 模块名`」，模块类型分两类：

- **领域模块**：`# 领域模块 · 身份与资料`、`# 领域模块 · 组织与授权` 等。头块含「更新日期」「状态机（SRS-SM-* 与 IFC-SM-* 引用）」。
- **平台支撑模块**：`# 平台支撑 · 后台任务与批量编排`（job）、`# 平台支撑 · 运维与可观测性`（ops）、`# 平台支撑 · 派生入口与读模型`（read-model）。头块含「模块定位（ADR-002 §2.2）」「职责」「上游权威（ADR/接口契约/数据模型相对链接）」。

注：`src/common/`、`src/shared/`、`src/config/`、`src/adapters/`、`src/database/` 等总目录开发指导文档沿用各自的「`# 目录名 · 一句话定位`」头块与「目录位置」「权威依据」元信息，不强制套用模块 README 的段结构，但 §4 权威与边界、相关文档链接两项要求同等适用。

### 段清单

| 段 | 必填 | 内容 |
|---|---|---|
| §1 定位与责任 | ✅ | 一句话职责，紧跟「关键不变量」列表。领域模块的不变量即其边界约束 |
| §2 关键组件 | ✅ | `组件 / 类型 / 职责` 三列表，类型标注所在分层（Controller/application/commands/domain/state-machines/infrastructure 等） |
| §3 对外接口与依赖 | ✅ | HTTP 路由前缀＋外部适配依赖＋关键外部调用。无对外 HTTP 入口的模块（如 job）显式说明承载方式 |
| §4 权威与边界 | ✅ | 两种等价写法：(A) 列入 §1 的「关键不变量」并附加「相关文档」链接段；(B) 独立「可以 / 禁止」两列表＋核心不变量。任一即可 |
| §5 运行形态 | 按需 | HTTP/worker 入口形态、单机/拆分部署、消息加速层边界。job/ops/read-model 已有 |
| §6 分层落位 | 按需 | interfaces/application/domain/infrastructure 四行落位约定，可独立单测的说明 |
| §7 开发必须遵守的规则 | 按需 | 模块特有的硬约束。job/ops/read-model 已有；identity 等领域模块的硬约束并入 §1 不变量 |
| §8 与相邻模块协作 | 按需 | `协作对象 / 关系` 两列表 |
| §9 测试要求 | 按需 | 测试要点列表 |
| §10 相关文档 | ✅ | 指向上游权威 ADR/SRS/接口契约/数据模型的相对链接列表。必填，不可省略 |
| 附：典型调用链 | ✅ | 文末一段箭头链，串联 Controller → UseCase → 领域校验 → 事务 → infrastructure/外部收口 |

### 两种允许的内联范式

- **A 式（领域模块）**：§1 核心职责＋关键不变量（边界以不变量表达）→ §2 关键组件 → §3 对外接口 → §4 核心逻辑摘要 → §5 典型调用链 → 末尾「相关文档」链接段。适用于 12 个领域模块，绝大多数已具备此结构，仅需补齐末尾「相关文档」段。
- **B 式（平台支撑模块）**：§1 定位与责任 → §2 关键组件 → §3 权威与边界（可以/禁止表）→ §4 运行形态 → §5 分层落位 → §6 开发规则 → §7 相邻协作 → §8 测试要求 → §9 相关文档。适用于 job/ops/read-model，三者已基本齐全，仅需统一编号与段名。

### 文件与链接约定

- 「相关文档」段只放指向 `docs/` 下权威文件的相对链接，不在模块 README 内新写规格内容；模块文档只做「引用＋摘要」。
- 相对链接按文档实际层级回溯：模块 README 在 `src/modules/<m>/README.md` 用 `../../../docs/...`；总目录文档在 `src/<dir>/xxx文档.md` 用 `../../docs/...`。
- 「更新日期」在内容实质变更时更新，纯格式整理不必改动。
- 禁止以「等实现后再补」为由留空段或占位句；按需段若无内容直接不出现，不得写「待补充」。
