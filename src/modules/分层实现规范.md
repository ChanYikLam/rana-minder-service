## 1. 四层职责边界

`src/modules/<module>/` 内部按四层分目录组织；每层只承担本层职责，不替代相邻层。

| 层 | 目录 | 唯一职责 | 关键产物（建议命名） |
|---|---|---|---|
| **interfaces** | `interfaces/` | HTTP/RPC/CLI 等传输适配；请求解析、参数校验、响应封装、错误转译为信封 | `*Controller`（路由控制器）、`*HttpDto` / `*Request` / `*Response`（传输 DTO）、`Guard`、`Pipe`、`Filter`（仅做传输级处理，不承载业务规则） |
| **application** | `application/commands/`、`application/queries/` | 应用用例编排：划定事务边界、组织跨实体协同、调用领域服务与基础设施端口、登记副作用任务 | `*UseCase`（命令/查询用例）、`*Service`（应用层组合服务）、`*Port`（依赖倒置端口接口） |
| **domain** | `domain/models/`、`domain/services/`、`domain/state-machines/` | 业务规则与不变量：实体与值对象、状态机、领域服务、领域事件；不依赖任何外部技术栈 | `*Aggregate` / `*Entity` / `*ValueObject`、`*StateMachine`、`*Policy` / `*Rule`（领域服务）、`DomainEvent` |
| **infrastructure** | `infrastructure/` | 持久化与外部适配：TypeORM/Repository 实现、对象存储/Casdoor/Mail/Job 等适配器实现；提供 application 层声明的 Port 实现 | `*Repository`（仓储实现）、`*Adapter`（外部适配实现）、`Mapper`（仅在 infrastructure 与 domain 间做实体↔领域模型转换） |

关键不变量（承接 [后端工程约定 v1.0](../../docs/engineering/后端工程约定-v1.0.md) §1 ENG-001、ADR-002 §3）：

- **interfaces** 只把传输协议映射到 application 用例；不持有状态、不做业务校验、不直接读写数据库。
- **application** 是事务边界与编排入口；定义 Port、登记副作用任务、调用 domain；不写 SQL、不直接依赖 NestJS/TypeORM/任何适配器。
- **domain** 是业务规则的唯一归属地；状态机门、唯一性、不可变、版本/期望版本校验、并发竞争裁决都在此层。
- **infrastructure** 实现 application 声明的 Port；不持有业务状态、不决策业务推进，只做"动作并报告结果"。

## 2. 禁止调用关系

依赖方向严格自上而下，禁止反向依赖，禁止跨层穿透。

| 调用方 ↓ / 被调用方 → | interfaces | application | domain | infrastructure | 外部适配目录 `src/adapters/` |
|---|---|---|---|---|---|
| **interfaces** | — | ✅ 唯一允许；调用 `*UseCase` 与应用层服务 | ❌ 禁止直接调用 domain 实体/服务 | ❌ 禁止 | ❌ 禁止 |
| **application** | ❌ 禁止反向 | — | ✅ 允许；编排领域服务与状态机 | ❌ 禁止直接 `new` 仓储/适配器；只通过 Port 引用，由 NestJS 容器注入 | ❌ 禁止直接依赖 |
| **domain** | ❌ 禁止 | ❌ 禁止 | — | ❌ 禁止 | ❌ 禁止 |
| **infrastructure** | ❌ 禁止 | ❌ 禁止 | ✅ 允许（实现 Port 时引用领域模型与值对象做映射） | — | ✅ 允许；本层可依赖 `src/adapters/` 已声明的适配边界 |

明确的硬性禁令（违反即视为破坏分层）：

1. **domain 层禁止** `import` 自 `@nestjs/*`、`typeorm`、`class-validator`、`zod`、`reflect-metadata`、`src/adapters/*`；不得出现 `@Injectable()`、`@InjectRepository()`、装饰器元数据或框架运行时类型。
2. **domain 层禁止** 直接持有、构造或使用 ORM 实体类（`@Entity()` 装饰的类）作为领域模型；ORM 实体仅在 infrastructure 层存在，并通过 `Mapper` 与领域模型互转。
3. **application 层禁止** 出现 SQL 片段、TypeORM `Repository<>`、NestJS `@Inject` 取出的具体仓储；只能通过在 application 声明的 Port 取得能力，由基础设施层实现并注入。
4. **interfaces 层禁止** 承载业务规则：状态机门、唯一性、并发竞争、副作用登记、事务划分都不在此层；Controller/Guard/Pipe 不得调用 `EntityManager` 或直接访问仓储。
5. **infrastructure 层禁止** 改变业务状态决策：仓储 save / 适配器调用不得自行决定是否推进状态机；是否提交由 application 用例在事务内依据领域规则裁决。
6. **跨层穿透禁止**：`Controller → Repository`、`UseCase → TypeORM Entity`、`Domain → Adapter` 这三种穿透均视为架构违规，由代码评审与 lint 规则共同把关。
7. **跨模块调用禁止** 直接写他域权威表（ADR-002 §3）；跨模块协作只走"目标模块的应用命令/查询用例"，由 application 层经本模块 Port 或 NestJS 注入的目标模块 `*UseCase` 触发；不得在 infrastructure 层跨模块访问。

## 3. 跨层数据流（DTO ↔ 领域模型 ↔ 实体 ↔ 数据库行）

四类对象各司其职，转换集中在 application 入口与 infrastructure 出口，**不在 domain 内部做框架级映射**。

```
HTTP/外部输入
  └─[ interfaces 解析+校验 ]─> Transport DTO（*HttpDto / *Request）
       └─[ application 入口 ]─> Command / Query 输入对象
            └─[ 构造/取回 ]─> 领域模型（Aggregate/Entity/ValueObject）
                 └─[ infrastructure 持久化 ]─> TypeORM Entity（@Entity）
                      └─[ DB ]─> 数据库行（PostgreSQL）
```

| 阶段 | 对象类型 | 归属层 | 职责 | 关键约束 |
|---|---|---|---|---|
| ① 传输入参 | Transport DTO（`*HttpDto`、`*Request`） | interfaces | 反序列化、字段级校验、默认值填充 | 不得直接进入 application；`class-validator`/Pipe 错误统一映射为 `422 IFC-ERR-005`；不带 `expectedVersion` 等业务字段的业务校验（`IFC-ERR-006`） |
| ② 用例入参 | Command / Query 输入对象（`*Command`、`*Query`） | application | 接收已校验入参、补充 `actor`/`supportId`/当前作用域 | 不可变；构造后不得被调用方再修改；与 Transport DTO 解耦，避免外部结构反向污染用例 |
| ③ 领域对象 | Aggregate / Entity / ValueObject | domain | 承载业务规则、不变量、状态机、领域事件 | 不被任何装饰器或框架类型污染；不可变值对象在构造时完成所有规则校验；可变聚合根在每次状态变更时同步发出领域事件 |
| ④ 持久化对象 | TypeORM Entity（`@Entity`） | infrastructure | 反映数据库行结构；负责列映射、关系加载、JSONB 序列化 | 严格按 [数据模型与约束 v1.0](../specification/数据模型与约束-v1.0.md) 的列与表命名；不得跨模块表 JOIN 后写回；JSONB 动态答案字段统一命名 `answers`（参见 ADR-006） |
| ⑤ 数据库行 | PostgreSQL 行 | DB | 权威持久化 | 由 TypeORM 实体经 Repository 写入；RLS 上下文由 application/transaction 控制（[后端工程约定 v1.0 §6](../../docs/engineering/后端工程约定-v1.0.md)、ADR-005） |

转换规则（`Mapper` 的归属与边界）：

- **Transport DTO → Command/Query**：在 interfaces 层边缘完成（建议命名 `*Mapper.toCommand(input, actor)`）；用例构造器只接收 Command/Query，不接收 DTO。
- **Command/Query → 领域模型**：在 application 层完成（构造或通过仓储 `find` 取回）；不可绕过仓储直接 `new` 实体后 save。
- **领域模型 ↔ TypeORM Entity**：在 infrastructure 层完成（建议命名 `*Mapper.toDomain(entity)` / `toEntity(aggregate)`）；领域层不感知 Entity 存在。
- **读路径（Query）**：可不经过聚合根构造；Query 用例可调用只读仓储直接产出读模型 DTO，但**不绕过领域服务做业务校验**；读模型 DTO 的字段允许与 Transport DTO 共用。
- **写路径（Command）**：必须构造/取回聚合根 → 调领域服务（含状态机）→ 触发领域事件 → 仓储保存 Entity → 提交后由 application 登记副作用任务（事务边界与外部副作用的关系见 [后端工程约定 v1.0 §5](../../docs/engineering/后端工程约定-v1.0.md)）。
- **跨层类型传递禁止**：`Entity` 不得出现在 `application/` 与 `interfaces/` 的入参/出参类型上；`Aggregate` 不得出现在 `infrastructure/` 的 SQL/列名上下文与 interfaces 的响应类型上；违反视为分层穿透。
- **不可变值对象**（如 `Money`、`DateRange`、`Email`）在 domain 构造时校验；不得从数据库列直接反序列化为 `string` 后穿过 application/interface。
- **可重建投影/读模型**（ADR-007 §2、[派生入口与读模型](../后端模块分类总览-v1.0.md) §3）不进入本规范四层；其构造与刷新在 `src/modules/read-model/` 内部按其目录规范执行。

## 4. 模块目录结构模板

每个领域模块在 `src/modules/<module>/` 下采用统一布局；`README.md` 是模块入口必读文档。`src/modules/<module>/` 与 `src/modules/<module>/*` 的目录命名沿用英文小写或中线（kebab-case），子目录名固定为四层英文单数。

```
src/modules/<module>/
├── README.md                  # 模块入口文档（核心职责、关键组件、对外接口、核心逻辑、典型调用链）
├── interfaces/                # 传输适配层
│   ├── http/                  # HTTP 控制器、Guard、Pipe、Filter
│   │   ├── <module>.controller.ts
│   │   ├── <module>-admin.controller.ts
│   │   ├── dto/               # *HttpDto / *Request / *Response
│   │   └── guards/            # 控制器级 Guard（仅做传输级检查）
│   └── mappers/               # *HttpDto ↔ Command/Query 的转换
├── application/               # 应用用例层
│   ├── commands/              # 写路径用例：*UseCase
│   ├── queries/               # 读路径用例：*UseCase
│   ├── services/              # *Service（应用层组合服务；非领域服务）
│   ├── ports/                 # *Port（依赖倒置接口；由 infrastructure 实现）
│   └── mappers/               # Command/Query ↔ 领域模型 的轻量转换（如必要）
├── domain/                    # 领域层
│   ├── models/                # Aggregate / Entity / ValueObject / DomainEvent
│   ├── services/              # *Policy / *Rule（领域服务）
│   └── state-machines/        # 状态机：*StateMachine
├── infrastructure/            # 基础设施适配层
│   ├── persistence/           # TypeORM Entity、Repository 实现、Mapper
│   ├── adapters/              # 外部系统适配器实现（Casdoor / Storage / Mail / Job 等）
│   └── mappers/               # 领域模型 ↔ TypeORM Entity 转换
└── .gitkeep                   # 占位文件；模块根与每个子目录按需保留
```

模板规则：

1. **必须有 `README.md`**，按 [recruitment 模块 README](../../src/modules/recruitment/README.md) 既有结构书写：核心职责、关键组件表、对外接口、核心逻辑摘要、典型调用链。
2. **子目录按需存在**：尚未实现某层时只保留 `.gitkeep` 占位；不允许在四层之外另立新顶层目录（除非有 ADR 变更）。
3. **跨模块文件位置**：跨模块复用的 Port 接口放调用方模块的 `application/ports/`；跨模块复用的领域模型放拥有该模型的模块 `domain/models/`，由其他模块经 application 用例引用，不直接 import 对方 infrastructure。
4. **测试目录约定**（与 [后端工程约定 v1.0 §7](../../docs/engineering/后端工程约定-v1.0.md) 同步）：单元测试在 `test/unit/modules/<module>/`，集成/契约测试在 `test/integration/modules/<module>/`；不写在模块内部以保持四层清晰。
5. **平台支撑模块**（`read-model/`、`job/`、`ops/`）同样按此四层布局，但 `domain/` 通常只保留"读模型聚合 / 任务意图"等轻量对象；`infrastructure/` 承担事件消费、任务领取、运行日志落盘等执行职责。

## 5. 命名约定

按 [后端工程约定 v1.0 §1 ENG-001](../../docs/engineering/后端工程约定-v1.0.md) 与 [实体与表清单草案 v1.0](../../docs/engineering/实体与表清单草案-v1.0.md) 统一；本节列具体拼写规则与反例。

| 类别 | 风格 | 示例 | 反例 |
|---|---|---|---|
| 类（Controller / UseCase / Aggregate / StateMachine / Repository / Adapter / Port / Mapper / DomainEvent） | **PascalCase** | `RecruitmentsController`、`PublishRecruitmentUseCase`、`RecruitmentAggregate`、`ChannelStateMachine`、`RecruitmentRepository`、`CasdoorAdapter`、`InvitationPort`、`RecruitmentMapper`、`ApplicationSubmittedEvent` | `recruitments_controller`、`publishRecruitmentUseCase`、`recruitmentAggregate` |
| 方法（用例、领域服务、仓储、适配器） | **camelCase** | `submitApplication`、`chooseInterviewSlot`、`voidInterview`、`loadById`、`syncGroup` | `Submit_Application`、`choose_interview_slot`、`loadbyid` |
| 私有方法、回调、变量、函数参数 | **camelCase** | `currentVersion`、`expectedVersion`、`supportId`、`idempotencyKey` | `CurrentVersion`、`current_version` |
| 常量（含枚举值、状态机字面量、错误码、配置键） | **SCREAMING_SNAKE_CASE** | `MAX_APPLICANTS_PER_CHANNEL`、`STATUS_PUBLISHED`、`IFC_ERR_006`、`SUPPORT_ID_HEADER` | `MaxApplicants`、`STATUS_PUBLISH` |
| 枚举（`enum`/`const enum`） | PascalCase，成员 SCREAMING_SNAKE_CASE | `enum RecruitmentStatus { DRAFT = 'draft', PUBLISHED = 'published' }` | `enum recruitmentStatus { draft = 'draft' }` |
| 类型别名 / 接口 | PascalCase；接口**不加** `I` 前缀 | `Recruitment`、`RecruitmentQuery`、`RecruitmentList` | `IRecruitment`、`recruitmentQuery` |
| 泛型参数 | 单字母大写或 PascalCase 简写 | `<T>`、`<TEntity extends AggregateRoot>` | `<t>`、`<entity>` |
| 装饰器（NestJS 装饰器参数） | 字符串字面量用 kebab-case 或小写 | `@Controller('recruitments')`、`@Get('application-channels')` | `@Controller('Recruitments')` |
| 文件名（`*.ts`） | kebab-case 为主；类名与文件名通过后缀对应 | `recruitment.controller.ts`、`publish-recruitment.use-case.ts`、`channel.state-machine.ts`、`recruitment.mapper.ts` | `RecruitmentController.ts`、`publishRecruitmentUseCase.ts` |
| 目录名 | kebab-case（与文件名风格一致） | `application/commands/`、`domain/state-machines/`、`infrastructure/persistence/` | `Application/Commands/` |
| 数据库表名 | snake_case（与既有数据库规范一致） | `recruitment`、`recruitment_application`、`recruitment_interview` | `Recruitment`、`recruitmentApplication` |
| 数据库列名 | snake_case | `expected_version`、`published_at`、`club_id` | `expectedVersion`、`PublishedAt` |
| JSONB 字段（动态答案） | snake_case 单数 | `answers` | `Answers`、`answer_list` |
| 领域事件名 | 过去时 PascalCase，文件用 `.event.ts` 后缀 | `ApplicationSubmittedEvent`、`ChannelPausedEvent` | `SubmitApplicationEvent` |
| 测试用例编号 | `TST-*` / `TST-IFC-*`（与 [测试规格与验收追踪 v1.0](../specification/测试规格与验收追踪-v1.0.md) 对齐） | `TST-REC-007`、`TST-IFC-006` | `test_rec_007` |
| `supportId` / `idempotencyKey` / `expectedVersion` 等横切键 | camelCase；header 一律 `X-Trace-Id` / `X-Support-Id` 形式 | `supportId`、`idempotencyKey`、`X-Trace-Id` | `SupportId`、`idempotency_key` |

补充规则：

- **导入路径别名**：跨层 import 一律使用相对路径（`./`、`../`），不使用 `@/modules/...` 别名跨层穿透；NestJS 容器注入按类型，不依赖路径别名。
- **包级 README**：本规范自身（`src/modules/分层实现规范.md`）是模块集合的总入口；任何对四层边界的扩展须先在本文件登记并提交评审，不得在子模块 README 中临时变更规则。
- **同义命名收敛**：禁止同一概念在不同层使用不同名字（如 `Application` 同时指 HTTP 应用与招新申请）；必要时通过类型命名空间或后缀消歧（如 `RecruitmentApplication` vs `NestApplication`）。
- **破坏性变更**：命名规则的调整属于破坏性变更，须随 ADR 一并提交评审；不得在普通 PR 中以"风格统一"为由批量重命名既有跨模块公共类型。
